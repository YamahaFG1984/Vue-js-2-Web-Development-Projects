项目 1 · 第一阶段 · 状态思维

番茄钟

第一个项目故意选得很小：一个专注 25 分钟、休息 5 分钟的计时器。代码不到两百行， 但从需求到代码的每一步都会摊开写：怎么从草图找出状态，怎么区分状态和派生数据， 为什么“剩余时间”不该是状态，按钮为什么不该用两个布尔值控制。 这些问题想清楚了，后面六个项目都是同一套路。

本篇目标

  • 学会第一件设计工具：设计卡（状态、派生、事件、副作用）
  • 学会从静态原型反推状态：原型里每一个写死的值都要问“它从哪里来”
  • 理解存事实，不存结果：存结束时刻，而不是存剩余秒数
  • 用状态机代替一堆布尔值，让不可能出现的状态根本写不出来
  • Vue 3：ref、computed、watch 的清理函数、watchEffect、props / emit、defineModel、组合式函数

注意计时中的 timer：它只记了一个 endAt（结束时刻），并不记“还剩多少秒”。 剩余时间是每次用 endAt − now 算出来的。为什么这样设计，第 5 步会专门讲，这是本篇最重要的一个设计决定。

Django 对照

在 Django 里，你不会在 User 表上存“年龄”这一列，而是存“出生日期”，年龄用的时候再算，否则每过一天数据就错一天。 番茄钟的 endAt 就是“出生日期”，剩余时间就是“年龄”。存不会过时的事实，算会变的结果， 这条你在数据库设计里早就会的规则，在前端一样适用。

第 1 步：需求与草图

先用大白话写下用户能做的事，不要想代码：

  • 点“开始”，专注 25 分钟倒计时；中途可以暂停、继续、重置

第 2 步：设计卡（第一版）

大多数人第一次填状态格，会把草图上每个会变的东西都列进去：阶段、剩余秒数、进度百分比、按钮文字、是否在计时、是否暂停、完成个数…… 然后逐个过一遍：它能不能由别的状态算出来？能算出来的，就从状态格划掉、挪到派生格：

草图上的东西能算出来吗？放哪一格
① 哪个阶段高亮不能，它是“现在处在哪一段”这个事实本身状态 phase
② 圆环进度能：1 − 剩余 / 总时长派生 progress
③ 剩余时间第一版先当作状态（第 5 步会推翻这个决定）状态 remaining
④ 下一段是什么能：由当前阶段和已完成个数决定派生 nextPhase
⑤ 按钮文字能：由“计时中 / 暂停 / 空闲”决定直接写在模板里
“是否在计时”“是否暂停”不能，但用两个布尔值表示有问题（5.3 节）状态（待改进）
⑥ 实心点个数能：completed % 4派生
⑥ 今天完成几个不能状态 completed

注意事件格的写法：左边是“发生了什么”，右边是“状态怎么变”。这和 Django 的 urls.py 一模一样： 左边是 URL，右边是处理它的视图。区别只是这里的“请求”来自按钮、键盘和时间，而不是浏览器地址栏。

还要注意“每过 1 秒”这一行：时间流逝也是一种事件。后端很少这样想，因为请求结束进程就不管了； 但前端应用一直活着，时间、网络消息、窗口尺寸变化，都会像用户点击一样触发状态变化。

“开始 / 暂停 / 继续”其实是一个状态机

设计卡 v1 用 running 和 paused 两个布尔值表示计时状态。先把它们画成图，看看用户到底能处在哪几种状态，以及能怎样在它们之间转换：

三种状态。可两个布尔值能组合出四种情况，多出来的那种 running = false, paused = true（“没在计时但处于暂停”）是什么意思？ 没有意思，但代码允许它出现。哪天某个事件处理函数漏改了一个值，界面就会进入这个“不可能的状态”，按钮显示错乱，而且很难排查。 5.3 节会用一个更好的写法让它根本写不出来。

Django 对照

订单的 status 字段（待支付 → 已支付 → 已发货 → 已完成）就是状态机。你不会给订单加 is_paid、is_shipped 两个布尔字段， 因为“已发货但未支付”这种组合会让业务出错；你可能还用过 django-fsm 来限制只允许合法的转换。前端的界面状态也该这样设计。

第 3 步：组件拆分

番茄钟很小，一个组件也写得下。但借这个小项目，正好练习拆组件时最重要的一个问题：状态放在谁那里？

拆组件时，按这三条来判断：

  1. 状态放在“所有用到它的组件”的最近公共祖先上。 timer 既要被 TimerRing 用来显示时间，又要被 TimerControls 用来决定按钮文字，所以只能放在它们共同的父组件 App 里。
  2. 子组件只通过 props 读数据，通过事件报告操作，不直接修改父组件的状态。 TimerControls 被点击时并不自己去改 timer，而是 emit('pause')，由 App 决定怎么改。 这样，所有改状态的代码都集中在持有状态的地方，出了问题只需要查一处。
  3. 纯展示的组件越多越好。 TimerRing 和 SessionDots 只接收数据、不发事件，就像一个函数：给什么输入就画什么。这样的组件最容易复用和测试。
Django 对照

子组件有点像 {% include "ring.html" with progress=progress %}：父模板把数据传进去。 但 include 的模板只能“读”，而组件还能“说话”：它通过事件告诉父组件“用户点了暂停”。 这就像子模板里的表单提交到父级的视图，只不过不需要发 HTTP 请求。

第 5 步：逐步实现

从这里开始写代码。每一小步只加一个需求，并且严格按照这个顺序：需求 → 先看设计卡要不要改 → 再写代码。 工程用 npm create vue@latest 创建，或者直接用仓库里的 examples/design/p01-pomodoro。

5.1 能倒计时（朴素版）

需求：点开始后倒计时→设计卡 v1，不用改→代码

照着设计卡 v1 直接翻译：remaining 是状态，用 ref；display 是派生，用 computed；事件是普通函数。

<script setup>
import { ref, computed } from 'vue'

const remaining = ref(25 * 60) // 状态：剩余秒数
const running = ref(false)
let id = null

const pad = (n) => String(n).padStart(2, '0')
const display = computed(() => `${pad(Math.floor(remaining.value / 60))}:${pad(remaining.value % 60)}`)

function start() {
  running.value = true
  id = setInterval(() => {
    remaining.value-- // 每秒减 1
    if (remaining.value === 0) pause()
  }, 1000)
}
function pause() {
  clearInterval(id)
  running.value = false
}
</script>

<template>
  <div class="time">{{ display }}</div>
  <button v-if="running" @click="pause">暂停</button>
  <button v-else @click="start">开始</button>
</template>

运行起来，一切正常。很多教程写到这里就结束了。但请做两个实验：

  1. 点开始，然后切到别的标签页待几分钟，再切回来。和手机上的秒表对比一下。
  2. 点开始，过一会儿刷新页面。

撞墙：计时变慢了，刷新就丢了

第一个实验，你会发现番茄钟慢了。浏览器为了省电，会给后台标签页里的定时器限流： 回调可能每秒才跑一次，Chrome 在页面隐藏 5 分钟后甚至可能一分钟才跑一次。而我们的代码是“每跑一次回调就减 1 秒”， 回调少跑了多少次，计时就慢了多少。

第二个实验更直接：刷新以后 remaining 回到 25:00，因为状态只存在内存里。就算把 remaining 存进 localStorage 也不行， 刷新前后那段时间里定时器没在跑，存下来的数字已经过时了。

两个问题是同一个根源：remaining 是一个会随时间自己变化的值，我们却把它当成状态存了起来， 然后靠定时器手动“维护”它。只要定时器有一次没跑，它就和事实对不上了。

5.2 存事实，不存结果

问题：计时不准→改设计卡→代码

换个思路：什么东西点了“开始”以后就再也不会变？答案是“结束的时刻”。25 分钟后的那个时间点是固定的， 无论定时器跑了几次、页面刷新了几次，它都不变。剩余时间则可以随时用“结束时刻 − 现在”算出来。

设计卡 v2 · 改动部分绿色为新增，灰色划线为删除
状态
phase
remaining  剩余秒数
endAt      结束的时刻（时间戳），不会变
now        当前时刻，由时钟刷新
running / paused
completed
派生
remaining  = endAt − now
progress / display / nextPhase 不变
事件
点“开始”  → endAt = 现在 + duration
每过 1 秒 → remaining − 1
时钟滴答  → now = 现在的时间
副作用
计时中要有一个时钟，只负责刷新 now

注意 now 也成了状态。这初看很怪：当前时间还要“记住”？但想一想，界面要随时间变化，而 Vue 只会对响应式数据的变化做出反应， Date.now() 不是响应式的。所以要把“现在”放进一个 ref，由时钟定期刷新它；所有依赖它的派生数据和界面就会自动更新。 时钟的职责从“维护剩余时间”降级成了“告诉大家现在几点”，它少跑几次也不会出错，最多是界面晚一点刷新。 

const MINUTE = 60_000
const endAt = ref(null)      // 状态：结束时刻
const now = ref(Date.now())  // 状态：当前时刻

// 派生：随时都能算出来，永远不会“过时”
const remaining = computed(() => Math.max(0, endAt.value - now.value))
const display = computed(() => {
  const s = Math.ceil(remaining.value / 1000)
  return `${pad(Math.floor(s / 60))}:${pad(s % 60)}`
})

function start() {
  endAt.value = Date.now() + 25 * MINUTE
  id = setInterval(() => {
    now.value = Date.now() // 时钟只负责报时
  }, 250)
}
为什么每 250 毫秒报一次时，而不是 1 秒？

定时器的触发时刻和“整秒”不对齐。如果每秒刷新一次，显示的秒数最多会比真实时间晚将近 1 秒，偶尔还会看到某一秒被跳过。 刷新得更勤一些，显示就会平滑。反正每次都是按真实时间计算，多刷几次不会让结果出错。

5.3 暂停和继续：用状态机代替布尔值

需求：可以暂停、继续、重置→改设计卡→代码

有了 endAt，暂停就要多想一步：暂停的时候没有“结束时刻”了，因为时间不再流逝。暂停时需要记住的是“还剩多少”。 于是三种计时状态各自需要不同的数据，正好对应图 1-2 方框下面写的内容：

  • 空闲：什么都不用记，剩余时间就是这一段的总时长；
  • 计时中：记住结束时刻 endAt；
  • 已暂停：记住暂停时还剩多少 left。

如果继续用布尔值，就会有 running、paused、endAt、left 四个变量，可以组合出一大堆没有意义的情况。 更好的做法是把它们合成一个状态，每种形态只带自己需要的字段：

✗ 四个独立的变量
const running = ref(false)
const paused = ref(false)
const endAt = ref(null)
const left = ref(null)
// running=true 却 endAt=null？
// paused=true 却 left=null？
// 都能写出来，都是 bug
✓ 一个状态，三种形态
// { status: 'idle' }
// { status: 'running', endAt }
// { status: 'paused',  left }
const timer = ref({ status: 'idle' })

// “计时中却没有结束时间”
// 根本写不出来

每个事件处理函数就是一次整体替换：从一种形态换成另一种形态，旧形态的字段自然消失。剩余时间则按形态分别计算： 

const timer = ref({ status: 'idle' })
const status = computed(() => timer.value.status)
const duration = computed(() => 25 * MINUTE)

const remaining = computed(() => {
  const t = timer.value
  if (t.status === 'running') return Math.max(0, t.endAt - now.value)
  if (t.status === 'paused') return t.left
  return duration.value // idle
})

function start() {
  // 空闲和暂停都能开始：remaining 已经替我们区分了两种情况
  timer.value = { status: 'running', endAt: Date.now() + remaining.value }
}
function pause() {
  timer.value = { status: 'paused', left: Math.max(0, timer.value.endAt - Date.now()) }
}
function reset() {
  timer.value = { status: 'idle' }
}

看 start：它不需要判断“是从空闲开始还是从暂停继续”，因为 remaining 这个派生数据已经把两种情况算好了。 派生数据设计得好，事件处理函数就会变短，这是一个很好的信号。

模板里的按钮也直接由 status 决定，不需要额外的状态：

<button v-if="status === 'running'" @click="pause">暂停</button>
<button v-else @click="start">{{ status === 'paused' ? '继续' : '开始' }}</button>
<button class="ghost" :disabled="status === 'idle'" @click="reset">重置</button>

5.4 专注与休息交替

需求：专注结束自动进入休息→设计卡 v1 已有，不用改→代码

这一步需要的 phase、completed、nextPhase 在设计卡 v1 里就有了，直接翻译。先把 nextPhase 的规则画出来： 

const DURATION = { focus: 25, shortBreak: 5, longBreak: 15 }
const LONG_EVERY = 4

const phase = ref('focus')
const completed = ref(0)

const duration = computed(() => DURATION[phase.value] * MINUTE)
const nextPhase = computed(() => {
  if (phase.value !== 'focus') return 'focus'
  return (completed.value + 1) % LONG_EVERY === 0 ? 'longBreak' : 'shortBreak'
})

function switchTo(next) {
  phase.value = next
  timer.value = { status: 'idle' }
}
function skip() {
  switchTo(nextPhase.value) // 跳过的番茄不计数
}
function finish() {
  const ended = phase.value
  const next = nextPhase.value // 必须先取！
  if (ended === 'focus') completed.value++
  switchTo(next)
}
function tick() {
  now.value = Date.now()
  if (status.value === 'running' && remaining.value === 0) finish()
}
小心：派生数据会“立刻”跟着变

finish 里必须先取出 nextPhase，再给 completed 加一。 computed 是实时的：completed 一变，下一次读 nextPhase 就是按新值算的结果。 例如第 3 个番茄结束时，completed 还是 2，nextPhase 按 2 + 1 = 3 算出“短休息”，正确； 如果先把 completed 加到 3 再读，就会按 3 + 1 = 4 算出“长休息”，提前进入长休息。 nextPhase 的含义是“如果当前这一段完成了，下一段是什么”，所以要在“完成”发生之前读它。 同一个事件里先读后写，是处理派生数据时的通用习惯。

5.5 副作用：时钟、标题栏、通知

需求：标题栏显示时间、结束时通知→设计卡副作用格→代码

到目前为止，时钟是在 start 里 setInterval、在 pause 里 clearInterval 的。 现在 reset、skip、finish 也会让计时停下，难道每个函数里都要记得清一次定时器？漏一个就是 bug。

换个角度想：时钟什么时候该存在？当且仅当 status 是 running。这是一条关于状态的规则，跟“是哪个事件让它变成 running 的”无关。 所以不要在事件里管理它，而是声明一个副作用，让它跟着状态走： 

import { watch, watchEffect } from 'vue'

// 1. 时钟：status 变成 running 就启动；status 再变，或者组件卸载，就清理
watch(status, (s, _old, onCleanup) => {
  if (s !== 'running') return
  tick()
  const id = setInterval(tick, 250)
  onCleanup(() => clearInterval(id))
}, { immediate: true })

// 2. 标题栏：用到哪些响应式数据，哪些一变就重新执行
watchEffect(() => {
  document.title = `${display.value} · ${LABEL[phase.value]}`
})

这段代码有三个要点：

  • onCleanup：传给它的函数会在下一次回调执行前、或者侦听器停止时（组件卸载时会自动停止）被调用。 “启动”和“清理”写在一起，再也不会忘记清定时器。现在 start、pause 这些事件函数只改状态，一行定时器代码都没有了。
  • immediate: true：创建时立刻执行一次。现在看起来没必要（初始是 idle），但第 6 步“刷新后恢复计时”时，它会让恢复出来的 running 状态自动启动时钟，不用写一行额外代码。
  • watch 和 watchEffect 怎么选：要明确“盯着谁”、需要新旧值或清理时用 watch； 像标题栏这样“用到什么就跟踪什么”的简单同步，用 watchEffect 更省事。

系统通知稍微特殊：它不是“状态变了就同步”，而是“某件事发生时通知一下”，所以直接在 finish 里触发。 另外，浏览器只允许在用户操作里请求通知权限，所以请求权限要放在“开始”按钮的点击处理里（见第 7 步的完整代码）。

Django 对照

watch 很像 post_save 信号：你不在每个修改订单的视图里都写一遍“发邮件”，而是声明“订单保存后发邮件”。 区别是信号只“触发”，而 watch 还管“清理”：状态离开 running 时，它负责把时钟关掉。这一点后端很少需要，在前端却非常重要， 因为页面不会在每次请求后清空，忘了清理的定时器、事件监听会一直跑下去。

第 6 步：需求变更演练

好的设计，好在改需求的时候。下面来两个真实项目里一定会遇到的变更，每次都先改设计卡，看看改动有多大。

变更一：时长可以自己设置

先问设计卡：时长现在是常量 DURATION，现在要让用户改，而且要记住。它算不出来，所以是状态：

设计卡 · 变更一只动了两格
状态
settings  { focus, shortBreak, longBreak, longEvery }
派生
duration = settings[phase] × 1 分钟
设置面板是否可用 = status === 'idle'
事件
修改设置 → settings = 新设置
副作用
不变

remaining、progress、display 一个都不用改，因为它们本来就是从 duration 派生的。 这就是“能派生就不存”的回报：源头一改，下游全部自动正确。

还有一个问题要决定：计时中改了时长怎么办？与其写一堆特殊处理，不如只允许在空闲时修改，这也是一条派生规则。 设置面板用 defineModel 实现双向绑定： 

<script setup>
// defineModel：父组件写 v-model="settings"，这里拿到的就是那个可读写的 ref
const settings = defineModel({ type: Object, required: true })
defineProps({ disabled: Boolean })

const FIELDS = [
  ['focus', '专注', 1, 90],
  ['shortBreak', '短休息', 1, 30],
  ['longBreak', '长休息', 1, 60],
  ['longEvery', '几个一轮', 2, 8],
]

function update(key, value, min, max) {
  const n = Math.round(Number(value))
  if (!Number.isFinite(n)) return
  // 生成一个新对象交回去，而不是直接改父组件对象的字段：数据只从持有它的一方修改
  settings.value = { ...settings.value, [key]: Math.min(max, Math.max(min, n)) }
}
</script>

<template>
  <fieldset class="settings" :disabled="disabled">
    <legend>设置{{ disabled ? '（计时中不可修改）' : '' }}</legend>
    <label v-for="[key, text, min, max] in FIELDS" :key="key">
      {{ text }}
      <input type="number" :min="min" :max="max" :value="settings[key]"
             @change="update(key, $event.target.value, min, max)">
    </label>
  </fieldset>
</template>

<SettingsPanel v-model="settings" :disabled="status !== 'idle'" />
defineModel 是什么

组件上的 v-model="settings" 是两件事的简写：传入 prop modelValue，监听事件 update:modelValue。 Vue 3.4 起，子组件里一行 defineModel() 就能拿到一个 ref：读它就是读 prop，给它赋值就是发事件。 数据仍然是“往下传、事件往上报”，只是写起来省事了。

变更二：刷新页面不丢进度，完成数每天清零

这是检验设计的关键一刻。回想 5.1 的朴素版：剩余秒数存下来也会过时，刷新后根本没法正确恢复。现在呢？

设计卡 · 变更二状态几乎不动，只加一个副作用
状态
启动时从 localStorage 读出
settings / phase / timer / completed
completed 只在“是今天存的”时才恢复
派生
不变
事件
不变
副作用
上述状态一变 → 存进 localStorage（带上日期）

因为计时中存的是 endAt（一个绝对时刻），刷新后把它原样读回来，remaining = endAt − now 立刻就是对的； 就算关掉页面半小时再打开、这一段早已结束，第一次 tick 就会发现 remaining === 0 并调用 finish。 而时钟呢？5.5 里的 watch(status, …, { immediate: true }) 看到恢复出来的状态是 running，自动就启动了。 这个需求几乎没写新逻辑，全靠前面的两个设计决定：存事实不存结果、副作用跟着状态走。 

const STORAGE_KEY = 'pomodoro-v1'
const today = () => new Date().toLocaleDateString('sv') // 形如 2026-11-05

function load() {
  try {
    return JSON.parse(localStorage.getItem(STORAGE_KEY)) ?? {}
  } catch {
    return {}
  }
}

const saved = load()
const settings = ref({ ...DEFAULT_SETTINGS, ...saved.settings })
const phase = ref(saved.phase ?? 'focus')
const timer = ref(saved.timer ?? { status: 'idle' })
const completed = ref(saved.day === today() ? saved.completed : 0)

watch([settings, phase, timer, completed], () => {
  localStorage.setItem(STORAGE_KEY, JSON.stringify({
    settings: settings.value, phase: phase.value, timer: timer.value,
    completed: completed.value, day: today(),
  }))
}, { deep: true })
只存状态，不存派生数据

存进 localStorage 的只有状态格里的东西。remaining、progress 这些派生数据不存，读回状态后自然会重新算出来。 这和数据库只存原始字段、不存可以计算的列是同一个道理。设计卡的状态格，同时也就是“需要持久化的清单”。

第 7 步：收尾，把逻辑搬进组合式函数

现在 App.vue 里塞满了状态、派生、事件、副作用，模板反而只剩几行。最后一步，把所有逻辑搬进一个组合式函数 usePomodoro， 按设计卡的四格分段组织。你会发现，这个文件的结构就是设计卡本身： 

import { ref, computed, watch, watchEffect } from 'vue'

export const PHASE_LABEL = { focus: '专注', shortBreak: '短休息', longBreak: '长休息' }

const STORAGE_KEY = 'pomodoro-v1'
const DEFAULT_SETTINGS = { focus: 25, shortBreak: 5, longBreak: 15, longEvery: 4 }
const MINUTE = 60_000

const today = () => new Date().toLocaleDateString('sv') // 形如 2026-11-05

function load() {
  try {
    return JSON.parse(localStorage.getItem(STORAGE_KEY)) ?? {}
  } catch {
    return {}
  }
}

/**
 * 番茄钟的全部逻辑。组件只负责“画”，不关心计时细节。
 * @param {{ onFinish?: (ended: string) => void }} options
 */
export function usePomodoro({ onFinish } = {}) {
  const saved = load()

  // ---------------- 状态：必须记住、而且算不出来的东西 ----------------
  const settings = ref({ ...DEFAULT_SETTINGS, ...saved.settings })
  const phase = ref(saved.phase ?? 'focus') // 'focus' | 'shortBreak' | 'longBreak'
  // 三种形态，各自只带自己需要的字段，“计时中却没有结束时间”这种状态根本写不出来
  //   { status: 'idle' } | { status: 'running', endAt } | { status: 'paused', left }
  const timer = ref(saved.timer ?? { status: 'idle' })
  const completed = ref(saved.day === today() ? saved.completed : 0)
  const now = ref(Date.now()) // “当前时间”也是状态：它在变，界面要跟着变

  // ---------------- 派生：都由上面的状态算出来 ----------------
  const status = computed(() => timer.value.status)
  const duration = computed(() => settings.value[phase.value] * MINUTE)
  const remaining = computed(() => {
    const t = timer.value
    if (t.status === 'running') return Math.max(0, t.endAt - now.value)
    if (t.status === 'paused') return t.left
    return duration.value
  })
  const progress = computed(() => Math.min(1, Math.max(0, 1 - remaining.value / duration.value)))
  const display = computed(() => {
    const s = Math.ceil(remaining.value / 1000)
    const mm = String(Math.floor(s / 60)).padStart(2, '0')
    const ss = String(s % 60).padStart(2, '0')
    return `${mm}:${ss}`
  })
  const nextPhase = computed(() => {
    if (phase.value !== 'focus') return 'focus'
    return (completed.value + 1) % settings.value.longEvery === 0 ? 'longBreak' : 'shortBreak'
  })

  // ---------------- 事件：每个函数只做一件事——改状态 ----------------
  function start() {
    // 空闲和暂停都能开始：remaining 已经替我们区分了两种情况
    timer.value = { status: 'running', endAt: Date.now() + remaining.value }
  }
  function pause() {
    timer.value = { status: 'paused', left: Math.max(0, timer.value.endAt - Date.now()) }
  }
  function reset() {
    timer.value = { status: 'idle' }
  }
  function switchTo(next) {
    phase.value = next
    timer.value = { status: 'idle' }
  }
  function skip() {
    switchTo(nextPhase.value) // 跳过的番茄不计数
  }
  function finish() {
    const ended = phase.value
    const next = nextPhase.value // 必须先取：completed 一变，nextPhase 就会跟着变
    if (ended === 'focus') completed.value++
    switchTo(next)
    onFinish?.(ended)
  }
  function tick() {
    now.value = Date.now()
    if (status.value === 'running' && remaining.value === 0) finish()
  }

  // ---------------- 副作用：把状态同步到“外面的世界” ----------------
  // 1. 时钟：只在计时中运行；状态一变或组件卸载，onCleanup 负责关掉旧的定时器
  watch(status, (s, _old, onCleanup) => {
    if (s !== 'running') return
    tick()
    const id = setInterval(tick, 250)
    onCleanup(() => clearInterval(id))
  }, { immediate: true })

  // 2. 标题栏：切到别的标签页也能看到剩余时间
  watchEffect(() => {
    document.title = `${display.value} · ${PHASE_LABEL[phase.value]}`
  })

  // 3. 持久化：刷新页面后一切照旧（endAt 是绝对时间，所以计时也能接上）
  watch([settings, phase, timer, completed], () => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify({
      settings: settings.value,
      phase: phase.value,
      timer: timer.value,
      completed: completed.value,
      day: today(),
    }))
  }, { deep: true })

  return {
    // 状态（设置面板要双向绑定，所以给出 ref 本身）
    settings, phase, completed,
    // 派生（只读）
    status, remaining, progress, display, nextPhase,
    // 事件
    start, pause, reset, skip,
  }
}

<script setup>
import { computed } from 'vue'
import { usePomodoro, PHASE_LABEL } from './composables/usePomodoro'
import TimerRing from './components/TimerRing.vue'
import TimerControls from './components/TimerControls.vue'
import SessionDots from './components/SessionDots.vue'
import SettingsPanel from './components/SettingsPanel.vue'

const {
  settings, phase, completed,
  status, progress, display, nextPhase,
  start, pause, reset, skip,
} = usePomodoro({ onFinish: notify })

const isBreak = computed(() => phase.value !== 'focus')

// 系统通知也是副作用，但它属于“这个界面怎么提醒用户”，所以放在组件里而不是组合式函数里
function notify(ended) {
  if (!('Notification' in window) || Notification.permission !== 'granted') return
  const text = ended === 'focus' ? '专注结束，休息一下吧' : '休息结束，开始下一个番茄'
  new Notification('番茄钟', { body: text })
}

function onStart() {

  if ('Notification' in window && Notification.permission === 'default') {
    Notification.requestPermission()
  }
  start()
}
</script>

<template>
  <main class="pomodoro">
    <nav class="tabs">
      <span v-for="(text, key) in PHASE_LABEL" :key="key" :class="{ on: key === phase }">{{ text }}</span>
    </nav>

               :is-break="isBreak" />

    <TimerControls :status="status" @start="onStart" @pause="pause" @reset="reset" @skip="skip" />

    <SessionDots :completed="completed" :long-every="settings.longEvery" />

    <SettingsPanel v-model="settings" :disabled="status !== 'idle'" />
  </main>
</template>

这就像 Django 社区常说的“胖模型、瘦视图”或者 service 层：业务规则放在模型或服务里，视图只负责接收请求、调用、返回。 这里 usePomodoro 是“模型”，组件是“视图”。好处也一样：逻辑可以单独测试，同一套逻辑可以换一个完全不同的界面来用。

判断题

先自己想答案，再点开看。

“今天完成了几个番茄”的文字，是状态还是派生？

文字本身是派生（由 completed 拼出来的字符串，甚至不用写 computed，直接写在模板里）；completed 这个数字是状态。区分“数据”和“它的展示形式”。

要加一个功能：专注时圆环是红色，休息时是青色。需要新增状态吗？

不需要。颜色由 phase 决定，是派生：模板里写 :class="{ break: phase !== 'focus' }" 就够了。想加状态之前，先问“能不能由已有状态算出来”。

如果用 remaining 当状态、每秒减 1，再在 visibilitychange 事件里“补上”后台丢失的时间，这样设计好吗？

能用，但这是在给一个错误的设计打补丁：补丁要算“丢了多少”，本质上还是要知道真实的开始或结束时刻。直接存 endAt，补丁就完全不需要了。遇到“需要补偿”的代码时，回头检查是不是存了结果而不是事实。

“设置面板是否可点”应该用一个 ref 存起来，在 start 里设为 false、reset 里设为 true 吗？

不应该。它完全由 status 决定，存起来就要在每个改 status 的地方同步维护，漏一处就错。写成 :disabled="status !== 'idle'"。

为什么定时器要放在 watch 里，而不是在 start 里启动、在 pause 里清除？

因为“有没有时钟”是由状态决定的规则，而让状态变化的入口有很多：开始、暂停、重置、跳过、时间到，还有刷新后从存储恢复。放在事件里，每个入口都要记得处理；放在 watch(status) 里，只写一次，并且自动清理。

后端出身容易踩的坑

  • 想“手动更新界面”：“时间变了，我去把那个 div 的文字改掉”。在 Vue 里你只改状态，界面会自己跟上；需要手动改 DOM，通常说明漏了一项状态。
  • 把派生数据存成状态：进度、按钮文字、是否可点……存起来就要手动保持同步，迟早对不上。和数据库存冗余列是同一种错误。
  • 把会随时间变的值当状态：剩余时间、“3 分钟前”、是否过期。存不变的时刻，变化的部分实时算。
  • 用多个布尔值表示一个状态：先画状态机，数清楚有几种状态，再用一个字段表示。
  • 忘记清理：后端每个请求结束一切都释放了，前端不会。启动了什么，就要想好在什么时候关掉它。
本篇的方法清单
  1. 写需求、画草图，圈出所有会变的地方。
  2. 填设计卡：每个会变的东西都问“要记住，还是能算出来”。
  3. 会随时间变化的值，找出它背后不变的事实来存。
  4. 几个互相牵制的布尔值，换成一个状态机。
  5. 静态原型和设计卡互相校对：每个写死的值都要有来源。
  6. 状态放在最近公共祖先；props 往下，事件往上。
  7. 副作用跟着状态走，并且写好清理。
  8. 来了新需求，先改设计卡，再改代码。

练习

每道题都请先改设计卡，再写代码。

  1. 自动开始休息：加一个开关，打开后专注结束直接开始休息倒计时，不用再点“开始”。设计卡哪几格要改？（提示：只需要改一个事件。）
  2. 键盘快捷键：按空格开始或暂停。它是事件还是副作用？监听器应该在什么时候添加、什么时候移除？
  3. 最近 7 天统计：显示过去 7 天每天完成了几个。completed 还够用吗？新的状态应该长什么样，才能既算出“今天几个”又算出“7 天柱状图”？
  4. 多个标签页：同时打开两个番茄钟标签页，在一个里点开始，另一个也要跟着变。（提示：storage 事件。想一想：为什么存 endAt 让这件事变得容易？）
