项目 2 · 第一阶段 · 状态思维

记账本

番茄钟只有一个计时器，状态屈指可数。记账本是第一个真正“有数据”的应用：一条条记录、一组分类、按月汇总、按天分组、按分类筛选。 这一篇会是整个系列里最像 Django 的一篇：两张“表”，加上一串“查询”。你的数据建模经验会在这里派上大用场， 但也会看到，前端多出了一类后端几乎不用操心的状态：界面状态。

本篇目标

  • 区分两类状态：领域数据（记录、分类）和界面状态（看哪个月、筛选什么、正在编辑哪条）
  • 把派生数据组织成一条派生链，就像串起来的 QuerySet
  • 前端也要规范化：记录只存分类 id，金额用整数“分”，日期用日历字符串
  • 表单草稿和已保存的数据分开；状态放在离使用者最近的地方
  • Vue 3：v-for 与 key、表单 v-model、用 key 重置组件、事件逐层转交、多个组合式函数协作

Django 对照

如果用 Django 写记账本，你会建两个 Model：Category 和 Record，Record.category 是外键； “本月按天分组”是一条 filter().values('date').annotate(Sum('amount'))；编辑用 ModelForm(instance=record)。 这一篇在前端做的是同一件事：同样的两张表、同样的查询、同样的“表单与模型分离”，只是全部发生在浏览器内存里。

第 2 步：设计卡（第一版）

照例把草图上的 6 处逐个过一遍，问“要记住，还是能算出来”：

草图上的东西能算出来吗？放哪一格
全部记录、全部分类不能，这是用户录入的数据本身状态：领域数据
① 正在看哪个月不能，用户切换的状态：界面状态 month
② 收入、支出、结余能：本月记录求和派生 totals

④ 各分类支出占比能：本月支出按分类求和派生 categoryStats
⑤ 按天分组的列表能：本月记录按日期分组派生 dayGroups
⑥ 正在编辑哪一条不能状态：界面状态 editingId

这次的状态明显分成了几类，值得停下来看清楚：

领域数据

记录、分类。换一个界面（比如手机 App）它们也还在，需要持久化。相当于 Django 的数据库。

界面状态

看哪个月、筛选哪个分类、正在编辑哪条。只关乎“现在怎么看”，刷新后回到默认值也无妨。相当于 request.GET 里的参数。

表单草稿

用户正在输入、还没提交的内容。可能不完整、不合法，提交前和领域数据毫无关系。相当于 Django 的 Form 实例。

后端出身的人设计状态时，往往只想到第一类，因为在 Django 里另外两类“不用存”：request.GET 随请求来去，表单随 POST 提交。 但前端应用一直活着，这两类状态也必须有个地方放，而且它们放在哪，直接决定了组件怎么拆（第 3 步）。

派生链：一串 QuerySet

派生格里的四项不是各算各的，它们有依赖关系：先从全部记录里挑出本月的，再从本月的算出合计、构成和分组。把依赖画出来：

每一环都能对应到一句 Django 查询：

前端 computedDjango 里大致相当于
recordsRecord.objects.all()
monthRecords.filter(date__startswith='2026-11')
totals.values('category__type').annotate(Sum('amount'))
categoryStats.filter(category__type='expense').values('category').annotate(total=Sum('amount')).order_by('-total')
visibleRecords.filter(category_id=filter_id)（有筛选时）
dayGroups.values('date').annotate(...)，再在模板里用 {% regroup %}

区别在于：Django 的 QuerySet 每个请求重新求值一次；而 computed 会缓存结果，只有它依赖的东西变了才重算。 切换月份时，monthRecords 和下游全部重算；只改了筛选时，monthRecords、totals、categoryStats 都不会重算，只有 visibleRecords 和 dayGroups 会。 这条依赖链画清楚了，性能和正确性都有保证。

第 3 步：组件拆分

上一篇的规则是“状态放在所有用到它的组件的最近公共祖先上”。这一篇补上另一半：也不要放得比需要的更高。 表单草稿只有表单自己用，那它就该是表单组件自己的状态，App 根本不需要知道用户正在敲什么。

和番茄钟相比，这里多了三个值得注意的地方：

  1. 草稿放在 RecordForm 里。用户每敲一个键，只有表单自己重新渲染；只有点“保存”时，表单才通过 submit 事件交出一份完整、合法的数据。 App 拿到的永远是“干净”的结果，这就是“状态放在离使用者最近的地方”。
  2. 事件可以逐层转交。“删除”按钮在 RecordItem 里，但删除操作要由持有 records 的 App 来做。 RecordItem 发出 remove，RecordList 收到后原样再发一次，App 才收到。层数多了这会很啰嗦，后面的项目会介绍 provide / inject 和 Pinia；但两三层以内，老老实实转交最清楚。
  3. RecordItem 接收的是查好的分类对象，而不是整个 categoryById。子组件只拿自己需要的东西，接口越窄越好复用。

5.1 记一笔，显示列表

需求：能记一笔、看到列表和合计→设计卡 v1，不用改→代码

先不拆组件，全部写在 App.vue 里，照着设计卡 v1 翻译：

<script setup>
import { ref, computed } from 'vue'
import { today } from './utils/date'

const CATEGORIES = ['餐饮', '交通', '购物', '工资']
const records = ref([])
const draft = ref({ type: 'expense', amount: 0, category: '餐饮', date: today(), note: '' })

const expense = computed(() => records.value
  .filter((r) => r.type === 'expense')
  .reduce((sum, r) => sum + r.amount, 0))

function addRecord() {
  records.value.push({ id: crypto.randomUUID(), ...draft.value })
  draft.value = { ...draft.value, amount: 0, note: '' } // 保留类型、分类、日期，方便连续记账
}
</script>

<template>
  <form @submit.prevent="addRecord">
    <select v-model="draft.type"><option value="expense">支出</option><option value="income">收入</option></select>
    <input v-model.number="draft.amount" type="number" step="0.01">
    <select v-model="draft.category"><option v-for="c in CATEGORIES" :key="c">{{ c }}</option></select>
    <input v-model="draft.date" type="date">
    <input v-model="draft.note" placeholder="备注">
    <button>保存</button>
  </form>
  <p>支出合计：{{ expense }}</p>
  <ul>
    <li v-for="r in records" :key="r.id">{{ r.date }} {{ r.category }} {{ r.amount }} {{ r.note }}</li>
  </ul>
</template>

注意 v-for 上的 :key="r.id"：它告诉 Vue 每一行对应哪条记录。以后删除中间某条、或者列表重新排序时，Vue 靠 key 认出“这一行还是那条记录”， 而不是按位置复用 DOM，从而避免输入框内容错位等怪问题。key 要用数据自己的 id，不要用数组下标，这也是记录需要一个 id 字段的原因之一。

撞墙一：0.1 + 0.2 = 0.30000000000000004

记两笔支出：0.1 元和 0.2 元。合计显示：

支出合计：0.30000000000000004

这不是 Vue 的问题，而是所有使用 IEEE 754 浮点数的语言都会有的问题：0.1 和 0.2 在二进制里都是无限循环小数，存进去就已经有误差了。 Python 里 0.1 + 0.2 也是这个结果，所以 Django 里存钱用的是 DecimalField。 JavaScript 没有内置的十进制数类型，通行做法是：用整数“分”存储和计算，只在输入和显示时换算成“元”。 整数在 253 以内是精确的，加减永远不会出错。

输入框也要跟着改。v-model.number 会把输入立刻转成浮点数，“12.” 这种输入到一半的内容会被转成 12，用户输入的原样文本也就丢了。 草稿里应该保留用户敲的原始文本 amountText，提交时再解析成分： 

// 金额一律用“分”（整数）存储和计算，只在输入和显示时与“元”互相转换。
// 原因：0.1 + 0.2 === 0.30000000000000004，浮点数不适合表示钱。

/** 把用户输入的“元”文本转成分；格式不对返回 null。'12.5' → 1250 */
export function parseYuan(text) {
  const m = /^\s*(\d{1,9})(?:\.(\d{1,2}))?\s*$/.exec(text)
  if (!m) return null
  return Number(m[1]) * 100 + Number((m[2] ?? '').padEnd(2, '0'))
}

/** 分 → 便于编辑的“元”文本。1250 → '12.50' */
export function centsToText(cents) {
  return `${Math.floor(cents / 100)}.${String(cents % 100).padStart(2, '0')}`
}

const fmt = new Intl.NumberFormat('zh-CN', { style: 'currency', currency: 'CNY' })
/** 分 → 显示用的金额。1250 → '¥12.50' */
export const formatCents = (cents) => fmt.format(cents / 100)

日期也有同样的陷阱

“哪一天”是日历上的日期，不是时间轴上的某个时刻。new Date('2026-11-06') 会被当成 UTC 零点解析， 在美洲的时区里显示出来就是 11 月 5 日。所以记录的 date 直接存 '2026-11-06' 这样的字符串 （正好也是 <input type="date"> 的值格式），比较大小、按月过滤都用字符串操作。 这和 Django 区分 DateField 与 DateTimeField 是一个道理。 

// “哪一天”用 'YYYY-MM-DD' 字符串存储：它是日历上的日期，不是某个时刻，
// 存成时间戳或 Date 会被时区换算成前一天或后一天。

/** 本地时区的今天，形如 '2026-11-06' */
export const today = () => new Date().toLocaleDateString('sv')

/** '2026-11-06' → '2026-11' */
export const monthOf = (date) => date.slice(0, 7)

/** 月份加减：shiftMonth('2026-01', -1) → '2025-12' */
export function shiftMonth(month, delta) {
  const [y, m] = month.split('-').map(Number)
  const d = new Date(y, m - 1 + delta, 1)
  return `${d.getFullYear()}-${String(d.getMonth() + 1).padStart(2, '0')}`
}

const WEEK = '日一二三四五六'
/** '2026-11-06' → '11月6日 周五' */
export function formatDay(date) {
  const [y, m, d] = date.split('-').map(Number)
  return `${m}月${d}日 周${WEEK[new Date(y, m - 1, d).getDay()]}`
}

5.2 按月查看，按天分组

界面状态 month 是一个普通的 ref。切换月份的小组件用 defineModel，父组件写 v-model="month" 就行：

然后把派生链一环一环写成 computed（这里还是 v1 的数据结构，记录上有 type）：

const month = ref(monthOf(today()))

const monthRecords = computed(() => records.value.filter((r) => monthOf(r.date) === month.value))

const totals = computed(() => {
  let income = 0
  let expense = 0
  for (const r of monthRecords.value) {
    if (r.type === 'income') income += r.amount
    else expense += r.amount
  }
  return { income, expense, balance: income - expense }
})

const dayGroups = computed(() => {
  const groups = new Map()
  for (const r of monthRecords.value) {
    if (!groups.has(r.date)) groups.set(r.date, { date: r.date, items: [], income: 0, expense: 0 })
    const g = groups.get(r.date)
    g.items.unshift(r) // 同一天里后记的在前
    if (r.type === 'income') g.income += r.amount
    else g.expense += r.amount
  }
  return [...groups.values()].sort((a, b) => b.date.localeCompare(a.date))
})

模板里用两层 v-for 渲染分组：

<div v-for="g in dayGroups" :key="g.date">
  <h4>{{ formatDay(g.date) }} <small>支 {{ formatCents(g.expense) }}</small></h4>
  <ul>
    <li v-for="r in g.items" :key="r.id">{{ r.category }} {{ formatCents(r.amount) }}</li>
  </ul>
</div>
一个 computed 只做一件事

也可以写一个大 computed，一次循环把过滤、求和、分组全做完。但拆成一环一环有两个好处：每一环都能单独看懂、单独测试； 而且缓存的粒度更细，某一环的输入没变，它就不会重算。这和把一个复杂 SQL 拆成几个有名字的子查询是同一种思路。

5.4 编辑与删除：草稿和数据分开

需求：每条记录可以编辑、删除→细化设计卡→代码

编辑最省事的写法，是让表单直接 v-model 到那条记录的字段上，Markdown 笔记本就是这么做的。但记账本这样做会出问题：

笔记本可以直接绑定，是因为“边打字边保存”正是它想要的行为，而且任何文本都合法。记账本的记录要经过校验，修改也需要能取消，所以要用草稿。 判断标准很简单：数据有没有“提交”这个动作？有，就需要草稿。

Django 对照

这正是 Django 里 Form 和 Model 的关系：form = RecordForm(request.POST, instance=record)， 用户提交的数据先进 Form，is_valid() 通过了才 form.save() 写回 Model。 你从来不会让 HTML 输入框直接改数据库，前端也一样。

设计卡里还要定两件事：

  • 编辑状态存 id，不存副本：editingId 只是一个 id，“正在编辑的记录”由它派生：records.find(r => r.id === editingId)。 这又是规范化：如果把整条记录复制一份存成 editingRecord，就有了两份数据。而且派生的写法还有一个附带的好处：正在编辑的记录被删掉时，它自动变成 null，表单自动关闭，不用写任何同步代码。
  • 草稿属于表单组件：RecordForm 接收 initial（要编辑的记录，新增时为 null），自己复制出草稿，校验通过后 emit('submit', 数据)。
<script setup>
import { ref, computed } from 'vue'
import { parseYuan, centsToText } from '../utils/money'
import { today } from '../utils/date'

const props = defineProps({
  categories: { type: Array, required: true },
  initial: { type: Object, default: null }, // 编辑时传入原记录；新增时为 null
})
const emit = defineEmits(['submit', 'cancel'])

// ---- 草稿：表单自己的局部状态，提交之前和记录本身毫无关系 ----
function toDraft(r) {
  if (!r) {
    const first = props.categories.find((c) => c.type === 'expense')
    return { type: 'expense', amountText: '', categoryId: first?.id ?? '', date: today(), note: '' }
  }
  const type = props.categories.find((c) => c.id === r.categoryId)?.type ?? 'expense'
  return { type, amountText: centsToText(r.amount), categoryId: r.categoryId, date: r.date, note: r.note }
}
const draft = ref(toDraft(props.initial))
const submitted = ref(false) // 点过“保存”之后才显示错误，别一打开就满屏红字

// ---- 派生：可选的分类、解析后的金额、校验错误 ----
const options = computed(() => props.categories.filter((c) => c.type === draft.value.type))
const amount = computed(() => parseYuan(draft.value.amountText))
const errors = computed(() => {
  const e = {}
  if (amount.value === null) e.amount = '请输入金额，最多两位小数'
  else if (amount.value === 0) e.amount = '金额不能为 0'
  if (!options.value.some((c) => c.id === draft.value.categoryId)) e.category = '请选择分类'
  if (!draft.value.date) e.date = '请选择日期'
  return e
})

// ---- 事件 ----
function setType(type) {
  draft.value.type = type
  // 切换收支后，原来选的分类不再可选，自动换成第一个
  if (!options.value.some((c) => c.id === draft.value.categoryId)) draft.value.categoryId = options.value[0]?.id ?? ''
}
function onSubmit() {
  submitted.value = true
  if (Object.keys(errors.value).length) return
  const { categoryId, date, note } = draft.value
  // 交出去的是“记录”的形状：金额是分，没有 type（type 由分类决定）
  emit('submit', { amount: amount.value, categoryId, date, note: note.trim() })
  if (!props.initial) {
    // 连续记账：保留收支、分类和日期，只清空金额和备注
    draft.value = { ...draft.value, amountText: '', note: '' }
    submitted.value = false
  }
}
</script>

<template>

    <h3>{{ initial ? '编辑记录' : '记一笔' }}</h3>

    <div class="chips" role="radiogroup" aria-label="分类">
      <button v-for="c in options" :key="c.id" type="button" role="radio"
              :aria-checked="c.id === draft.categoryId" :class="{ on: c.id === draft.categoryId }"
              :style="{ '--c': c.color }" @click="draft.categoryId = c.id">{{ c.icon }} {{ c.name }}</button>
    </div>
    <span v-if="submitted && errors.category" class="err">{{ errors.category }}</span>

    <label>备注 <input v-model="draft.note" maxlength="40" placeholder="可不填"></label>
    <div class="actions">

      <button v-if="initial" type="button" class="ghost" @click="emit('cancel')">取消</button>
    </div>

几个要点：

  • 校验错误是派生数据：errors 由草稿算出来，草稿一改就实时更新。另一个状态 submitted 决定“要不要显示”：用户还没点保存，就别一打开表单就满屏红字。
  • 表单交出去的是“记录的形状”：金额已经是分，没有 type，备注去掉了首尾空格。App 收到的数据不需要再加工。
  • 草稿只在创建组件时从 initial 复制一次。那么从编辑 A 直接点到编辑 B 时，草稿怎么更新？看 App 里的用法：
<script setup>
const editingId = ref(null) // 只存 id
const editingRecord = computed(() => records.value.find((r) => r.id === editingId.value) ?? null)

function onSubmit(data) {
  if (editingRecord.value) updateRecord(editingId.value, data)
  else addRecord(data)
  editingId.value = null
  month.value = monthOf(data.date) // 记到别的月份时跳过去，否则用户会以为没保存
}
</script>

<template>
  <!-- key 变了，Vue 会销毁旧表单、创建新表单，草稿随之重置 -->
  <RecordForm :key="editingId ?? 'new'" :categories="categories" :initial="editingRecord"
              @submit="onSubmit" @cancel="editingId = null" />
</template>

key 不只能用在 v-for 里。给组件一个 key，当 key 的值变化时，Vue 会把它当成一个全新的组件：销毁旧的，创建新的。 从编辑 A 切到编辑 B，key 从 A 的 id 变成 B 的 id，新表单用 B 的数据初始化草稿。不需要在表单里写 watch(initial) 去手动同步。 这是“重置一个组件的局部状态”的标准做法。

“记到别的月份时跳过去”是一个设计决定

假设现在看的是 11 月，用户补记了一笔 9 月的账。保存后列表里没有它，用户会以为没保存成功。所以 onSubmit 里顺手把 month 切到记录所在的月份。 这类“事件发生后界面该停在哪里”的决定，也应该写进设计卡的事件格。

5.5 持久化：只存领域数据

需求：刷新后数据还在→设计卡副作用格→代码

把领域数据和修改它们的操作收进一个组合式函数 useLedger。存进 localStorage 的只有 records 和 categories： month、filterId、editingId 是界面状态，刷新后回到“本月、不筛选、不编辑”正合适。 这个区分本身就是一个设计决定：如果产品要求“刷新后停在上次看的月份”，那就把 month 也存起来，或者放进 URL（第 6 个项目会讲“URL 即状态”）。 

import { ref, computed, watch } from 'vue'

const STORAGE_KEY = 'ledger-v1'

const DEFAULT_CATEGORIES = [
  { id: 'food', name: '餐饮', icon: '🍜', color: '#e8590c', type: 'expense' },
  { id: 'transport', name: '交通', icon: '🚇', color: '#1c7ed6', type: 'expense' },
  { id: 'shopping', name: '购物', icon: '🛍️', color: '#ae3ec9', type: 'expense' },
  { id: 'home', name: '居家', icon: '🏠', color: '#2f9e44', type: 'expense' },
  { id: 'fun', name: '娱乐', icon: '🎮', color: '#f08c00', type: 'expense' },
  { id: 'salary', name: '工资', icon: '💼', color: '#0ca678', type: 'income' },
  { id: 'side', name: '副业', icon: '💡', color: '#4263eb', type: 'income' },
]

function load() {
  try {
    return JSON.parse(localStorage.getItem(STORAGE_KEY)) ?? {}
  } catch {
    return {}
  }
}

/**
 * 记账本的“领域数据”：记录和分类，以及修改它们的全部操作。
 * 只有这里能改 records / categories，组件拿到的是只读的派生数据和操作函数。
 */
export function useLedger() {
  const saved = load()

  // ---------------- 状态（会被持久化） ----------------
  // 记录只存 categoryId，不存分类名、颜色、收支类型：这些都在分类里，只存一份
  //   { id, amount(分), categoryId, date: 'YYYY-MM-DD', note }
  const records = ref(saved.records ?? [])
  const categories = ref(saved.categories ?? DEFAULT_CATEGORIES)

  // ---------------- 派生 ----------------
  // 按 id 查分类，相当于给外键建了一个索引
  const categoryById = computed(() => Object.fromEntries(categories.value.map((c) => [c.id, c])))
  // 每个分类被多少条记录用到（删除分类时要用）
  const usage = computed(() => {
    const n = {}
    for (const r of records.value) n[r.categoryId] = (n[r.categoryId] ?? 0) + 1
    return n
  })

  // ---------------- 事件 ----------------
  function addRecord(data) {
    records.value.push({ id: crypto.randomUUID(), ...data })
  }
  function updateRecord(id, data) {
    const r = records.value.find((r) => r.id === id)
    if (r) Object.assign(r, data)
  }
  function removeRecord(id) {
    records.value = records.value.filter((r) => r.id !== id)
  }
  function updateCategory(id, patch) {
    const c = categories.value.find((c) => c.id === id)
    if (c) Object.assign(c, patch)
  }
  function removeCategory(id) {
    // 相当于 Django 的 on_delete=PROTECT：还有记录在用，就不许删
    if (usage.value[id]) return false
    categories.value = categories.value.filter((c) => c.id !== id)
    return true
  }

  // ---------------- 副作用：持久化 ----------------
  watch([records, categories], () => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify({
      version: 1,
      records: records.value,
      categories: categories.value,
    }))
  }, { deep: true })

  return {
    records, categories, categoryById, usage,
    addRecord, updateRecord, removeRecord, updateCategory, removeCategory,
  }
}
为什么存一个 version

存在用户浏览器里的数据，你没法像服务器数据库那样统一迁移。将来数据结构变了（比如金额从元改成分），读取时可以根据 version 判断是旧格式，先转换再使用。 这就是前端版的 Django migrations。从第一天起就存上版本号，成本几乎为零。

变更二：删除分类，那它的记录怎么办？

这是一个必须由人做出的业务决定，代码只是执行它。Django 的 on_delete 把选项列得很清楚，前端可以直接借用：

Django含义记账本里的效果
CASCADE连带删除删掉“餐饮”，所有餐饮记录一起消失。危险，用户多半没想到
SET_NULL / SET_DEFAULT改成空或默认值记录归入“未分类”，需要额外设计一个默认分类

第 7 步：收尾

派生链单独放进 useMonthView。它很特别：没有任何自己的状态，输入是几个 ref，输出全是 computed，是一个纯粹的“查询层”： 

import { computed } from 'vue'
import { monthOf } from '../utils/date'

/**
 * 从“全部记录”派生出“当前视图要显示的一切”。
 * 输入是几个 ref（领域数据 + 界面状态），输出全是 computed，没有任何自己的状态。
 */
export function useMonthView({ records, categoryById, month, filterId }) {
  // 1. 本月的记录
  const monthRecords = computed(() => records.value.filter((r) => monthOf(r.date) === month.value))

  // 2. 本月收支合计：收入还是支出由分类决定，记录上不重复存
  const totals = computed(() => {
    let income = 0
    let expense = 0
    for (const r of monthRecords.value) {
      if (categoryById.value[r.categoryId]?.type === 'income') income += r.amount
      else expense += r.amount
    }
    return { income, expense, balance: income - expense }
  })

  // 3. 本月各分类的支出，从多到少
  const categoryStats = computed(() => {
    const sum = {}
    for (const r of monthRecords.value) {
      if (categoryById.value[r.categoryId]?.type !== 'expense') continue
      sum[r.categoryId] = (sum[r.categoryId] ?? 0) + r.amount
    }
    const total = totals.value.expense || 1
    return Object.entries(sum)
      .map(([id, amount]) => ({ category: categoryById.value[id], amount, ratio: amount / total }))
      .sort((a, b) => b.amount - a.amount)
  })

  // 4. 按分类筛选后的记录
  const visibleRecords = computed(() =>
    filterId.value ? monthRecords.value.filter((r) => r.categoryId === filterId.value) : monthRecords.value)

  // 5. 按天分组，新的日期在前；每组带当天小计
  const dayGroups = computed(() => {
    const groups = new Map()
    for (const r of visibleRecords.value) {
      if (!groups.has(r.date)) groups.set(r.date, { date: r.date, items: [], income: 0, expense: 0 })
      const g = groups.get(r.date)
      g.items.unshift(r) // 同一天里后记的在前
      if (categoryById.value[r.categoryId]?.type === 'income') g.income += r.amount
      else g.expense += r.amount
    }
    return [...groups.values()].sort((a, b) => b.date.localeCompare(a.date))
  })

  return { monthRecords, totals, categoryStats, visibleRecords, dayGroups }
}

  if (confirm('确定删除这条记录吗？')) removeRecord(id)
}

  filterId.value = filterId.value === id ? null : id
}
function onRemoveCategory(id) {
  if (filterId.value === id) filterId.value = null
  removeCategory(id)
}

复盘

判断题

记录上要不要存 type（收入 / 支出）？

不要。收支由分类决定，存在记录上就是冗余，而且可能和分类不一致（“工资”被记成支出）。需要时通过 categoryById[r.categoryId].type 派生。

表单的“支出 / 收入”切换按钮背后的 draft.type，为什么又是状态了？

因为在表单里它是用户的选择，无法从别处算出来：用户可能先点“收入”，还没选分类。同一个概念，在草稿里是状态，在保存后的记录里是派生。判断时要看“在这个位置上，能不能算出来”。

正在编辑时，为什么存 editingId 而不是 editingRecord（记录的副本）？

存副本就有了两份数据，原记录被删除或被修改时，副本不会知道。存 id、再派生出记录，永远指向唯一的真相；记录被删时派生结果自动变成 null，表单自动关闭。

用户想“刷新后停在上次看的月份”，month 要从界面状态改成领域数据吗？

不用改分类，只是改变它的持久化策略：可以单独存进 localStorage，更好的做法是放进 URL（?month=2026-09），这样还能分享链接、能用浏览器后退。界面状态和领域数据的区别在于“和业务有没有关系”，而不在于“存不存”。

本月合计应该基于 visibleRecords 还是 monthRecords？

这是产品决定，不是技术问题。本篇选择基于 monthRecords：筛选只是“在列表里找东西”，不改变“这个月花了多少”。如果产品希望筛选后合计也变，就把 totals 接到 visibleRecords 后面。重要的是在派生链上明确地做出选择。

列表的 v-for 用数组下标做 key 会怎样？

删除中间一条时，后面每一行的下标都变了，Vue 会以为“第 3 行的数据变了”而不是“第 3 行被删了”，于是复用错 DOM。行里有输入框、动画或组件状态时就会错位。key 要用记录自己的 id。

后端出身容易踩的坑

  • 只设计领域数据，忘了界面状态：Django 里它们藏在 request.GET 和 session 里，前端必须明确放在某个组件上。
  • 以为前端可以不讲规范化：“反正是内存里的数组”。冗余一样会造成不一致，而且前端的数据要持久化到用户浏览器里，比服务器更难修复。
  • 用浮点数算钱，用 Date 对象存日期：分别换成整数分和日历字符串。
  • 表单直接绑定数据：有“提交”动作的数据，都需要草稿。
  • 把所有状态都放在顶层组件：草稿这种只有一个组件用的状态，放在那个组件里。顶层组件只放“多个组件都要用”的东西。
本篇新增的方法
  1. 状态分三类：领域数据、界面状态、表单草稿，分别想清楚放在哪、存不存。
  2. 派生数据画成一条链，新需求先找“插在哪一环”。
  3. 前端也规范化：引用用 id，冗余字段删掉，能由关联对象决定的就派生。
  4. 钱用整数分，日期用日历字符串：选择“不会出错”的表示方式。
  5. 有提交动作就用草稿；用 key 重置组件的局部状态。
  6. 涉及删除的关联数据，先做 on_delete 式的业务决定，再写代码。
