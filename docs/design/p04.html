项目 4 · 第二阶段 · 组件设计

搜索自动补全框

前三个项目做的都是“应用”，这一篇做的是一个组件：小商城顶部的搜索框，输入关键字，下面弹出匹配的商品。 它看起来只是一个输入框加一个列表，却是前端里公认最难做对的控件之一：要防抖、要处理请求竞态、要支持键盘、要照顾屏幕阅读器， 而且要设计成别人拿去就能用的样子，后台的“选择商品”“选择城市”也能用它。

本篇目标

  • 设计卡新增第五格：接口。先写用法，再写实现；props / emit / slots 就是组件的函数签名
  • 理解防抖和竞态，并用一个 onCleanup 同时解决
  • 键盘交互也是状态机；高亮项存 key 不存下标
  • 焦点与事件顺序、ARIA combobox 模式、不用 v-html 的高亮
  • Vue 3：作用域插槽、defineModel、useId、useTemplateRef、shallowRef、toValue；用 Vue Test Utils 只通过接口测试组件

Django 对照

Django admin 的 autocomplete_fields 就是这个控件：一个带搜索的下拉框，背后调用 admin 的 JSON 接口。你只需要写一行配置， 因为有人把它做成了可复用的组件，接口就是那几个参数。这一篇站在“写组件的人”这边：怎样设计接口，才能让使用者一行配置就用上，而且各种场景都能用。

第 1 步：需求与草图

需求分三组。前两组是用户看得见的，第三组是给“使用这个组件的程序员”的：

  • 搜索：输入至少 1 个字开始搜索；结果中的关键字高亮；有“搜索中”“没有结果”“出错了（可重试）”三种提示；不要每敲一个字就发一次请求；结果不能和输入对不上
  • 操作：上下键移动高亮项（到头后循环），回车选中，Esc 关闭列表、再按一次清空；鼠标悬停高亮、点击选中；点别处列表关闭；屏幕阅读器能用
  • 复用：既能搜服务器，也能过滤本地数组；每一项长什么样由使用者决定；用 v-model 拿到选中的项

第 2 步：先设计接口

做应用时，设计卡从“状态”开始。做组件时，要先多做一件事：站在使用者的角度，把用法写出来。 还没有一行实现，先假装组件已经存在，写出你希望别人怎么用它： 

<!-- 用法一：搜服务器上的商品，每一项显示图标和价格，选中后跳转 -->
<AutoComplete v-model="product" :search="searchProducts" item-label="name" @select="goToProduct">

    {{ item.emoji }} <HighlightText :text="item.name" :query="query" /> {{ formatCents(item.price) }}
  </template>

写用法的过程，就是在做接口设计。每一个属性都是一个决定：

接口决定为什么
v-model选中的整个对象，没选为 null使用者拿到就能显示、能跳转，不必再按 id 查一次。代价是表单提交时要自己取 .id。（另一种常见设计是 v-model 只存 id，各有取舍，要在文档里写清楚）
search一个函数 (query, { signal }) => 列表或 Promise不设计 options 数组和 url 两个属性：本地过滤就是一个同步函数，远程搜索就是一个异步函数，一个接口覆盖两种用法。组件也不需要知道接口地址、参数格式、鉴权方式，那是使用者的事
itemKey / itemLabel字段名，默认 'id' / 'label'组件不规定数据长什么样，告诉它“哪个字段是唯一标识、哪个字段显示在输入框里”就行
minLength / debounce数字，有合理的默认值大多数人不用改；本地数据把 debounce 设成 0
#item / #empty 插槽作用域插槽，把 item、query、active 交给使用者每一项长什么样千变万化，用插槽而不是 showPrice、showEmoji 这类布尔属性
select 事件用户选中一项时触发v-model 回答“当前值是什么”（状态），select 回答“用户刚刚做了什么”（事件）。跳转页面应该响应动作，而不是监听值的变化
接口设计的三条经验
  1. 先写用法，再写实现。用法写起来别扭，接口就有问题。这时候改，成本为零。
  2. 按“谁知道什么”划分职责。使用者知道数据和业务，组件知道交互细节。组件里出现 fetch('/api/products')，或者使用者要自己处理防抖，都说明边界划错了。
  3. 外观用插槽，行为用 props。布尔属性会随需求不断膨胀（showPrice、showStock、showBadge……），插槽一次解决。
Django 对照

这和你设计一个 Django 模板标签、一个表单 Widget，或者一个 service 函数的签名是同一件事：参数要少而正交、默认值要合理、扩展点（比如 Widget 的 template_name）留给使用者覆盖外观。 作用域插槽最接近 Django 模板里的 {% block %} 覆盖，区别是插槽还能从组件拿到数据（item、query）。

注意 aria-activedescendant：键盘高亮时，焦点始终留在输入框里（用户还要继续打字），只是通过这个属性告诉屏幕阅读器“现在指向的是哪一项”。 所以高亮项是一个纯粹的状态，而不是浏览器的焦点。

第 5 步：逐步实现

5.1 能搜、能选（朴素版）

需求：输入就搜，点击选中→设计卡 v1→代码

“query 变化 → 调用 search”是一个副作用，最直接的写法是 watch：

const query = ref('')
const items = ref([])

watch(query, async (q) => {
  if (q.trim().length < props.minLength) return (items.value = [])
  items.value = await props.search(q.trim())
})

本机测试一切正常。然后在网络面板里把网速调成 “Slow 3G”，快速输入 “erji” 四个字母，会撞上两堵墙。

撞墙一：每敲一个字，发一个请求

防抖（debounce）的规则是：事件发生后先等一段时间，这段时间里又发生了，就重新计时；直到安静下来才真正执行。 它既减少了服务器压力，也避免了结果列表跟着每次按键闪来闪去。

撞墙二：结果和输入对不上

防抖能减少这种情况，但不能消灭它：用户打字慢一点（每个字间隔超过 300ms），请求照样一个接一个发出去。 网络请求的返回顺序没有任何保证，后发的请求可能先回来。这就是竞态（race condition）。 后端也有竞态，但通常是两个请求同时改数据库；前端的竞态是“旧数据覆盖新数据”，表现为界面显示错误的内容。

5.2 一个 onCleanup，同时解决防抖和竞态

问题：请求太多、结果错乱→改副作用格→代码

两个问题看起来不同，本质上却是一件事：关键字一变，上一次的副作用就该作废。 还没到时间的定时器取消掉，就是防抖；已经发出的请求作废掉，就是竞态保护。 回想番茄钟：watch 的 onCleanup 会在“下一次回调执行之前”被调用，正是做这件事的地方： 

import { shallowRef, ref, watch, toValue } from 'vue'

/**
 * 根据关键字搜索，自带防抖和竞态保护。
 * @param query   关键字（ref 或 getter）
 * @param search  (query, { signal }) => Item[] | Promise<Item[]>
 * @returns state  { status: 'idle' | 'loading' | 'success' | 'error', items, error } 以及 retry()
 */
export function useSearch(query, search, { debounce = 300, minLength = 1 } = {}) {
  const state = shallowRef({ status: 'idle', items: [], error: '' })
  const attempt = ref(0) // 点“重试”时加一，让下面的 watch 重新执行

  watch(
    [() => toValue(query).trim(), () => toValue(debounce), () => toValue(minLength), attempt],
    ([q, wait, min], _old, onCleanup) => {
      if (q.length < min) {
        state.value = { status: 'idle', items: [], error: '' }
        return
      }
      // 加载中保留上一次的结果，列表不会闪一下变空
      state.value = { ...state.value, status: 'loading' }

      const ctrl = new AbortController()
      const timer = setTimeout(async () => {
        try {
          const items = await search(q, { signal: ctrl.signal })
          if (!ctrl.signal.aborted) state.value = { status: 'success', items, error: '' }
        } catch (e) {
          if (!ctrl.signal.aborted) state.value = { status: 'error', items: [], error: e.message }
        }
      }, wait)

      // 关键字再变（或组件卸载）时：没到点的定时器取消 = 防抖；已发出的请求作废 = 竞态保护
      onCleanup(() => {
        clearTimeout(timer)
        ctrl.abort()
      })
    },
    { immediate: true },
  )

  return { state, retry: () => attempt.value++ }
}

几个细节：

  • AbortController：浏览器内置的“取消令牌”。把 signal 传给 fetch(url, { signal })，调用 abort() 后请求真的会被取消，连网络流量都省了。 即使 search 函数不支持取消，if (!ctrl.signal.aborted) 这一句也保证了旧结果不会写进状态。
  • 加载中保留旧结果：status 变成 loading 时 items 不清空，列表变淡显示。否则每敲一个字列表就闪一下变空，体验很差。这又是一个需要明确做出的设计决定。
  • shallowRef：state 每次都整体替换，从不修改内部字段，用 shallowRef 就够了，省去把结果数组深层转成响应式的开销。
  • toValue：参数既可以是 ref，也可以是 getter 函数，组合式函数因此更好用。组件里传的是 () => props.debounce，这样 prop 变了也能生效。
  • 重试：attempt 是一个只为“让 watch 再跑一次”而存在的状态，点“重试”时加一。
“取消上一次”是前端最常见的副作用模式

番茄钟里的定时器、这里的搜索请求，以后的 WebSocket 订阅、事件监听，都是同一个模式：副作用跟着某个状态走；状态变了，先清理旧的，再启动新的。 用 watch + onCleanup 写，启动和清理写在一起，永远不会忘。

5.3 键盘：高亮项存 key，不存下标

需求：上下键、回车、Esc→修改设计卡→代码

照着图 4-3 写键盘处理很直接。但设计卡 v1 里的 activeIndex 有个隐患：用户按 ↓ 高亮了第 2 项“运动耳机”，这时新的搜索结果回来了， 列表变了，第 2 项变成了别的商品，高亮却还停在“第 2 个位置”。用户按回车，选中的不是他看到的那一项。

这个问题记账本里见过：引用一个东西，要用它的 id，而不是它的位置。把状态改成 activeKey，下标由它派生：

状态
activeIndex  高亮第几项
activeKey    高亮项的 key（itemKey 字段的值）
派生
activeIndex = items 中 key 等于 activeKey 的下标
（新结果里没有它时，自动为 −1）
事件
↓ / ↑ → 由 activeIndex 算出下一个下标，
        activeKey = 那一项的 key
副作用
不变
const activeKey = ref(null)
const activeIndex = computed(() => items.value.findIndex((it) => keyOf(it) === activeKey.value))

function move(delta) {
  if (!open.value) return void (open.value = true)
  const n = items.value.length
  if (!n) return
  const i = activeIndex.value
  const next = i === -1 ? (delta > 0 ? 0 : n - 1) : (i + delta + n) % n
  activeKey.value = keyOf(items.value[next])
}

function onKeydown(e) {
  switch (e.key) {
    case 'ArrowDown':
      e.preventDefault() // 否则光标会跳到行首 / 行尾
      move(1)
      break
    case 'ArrowUp':
      e.preventDefault()
      move(-1)
      break
    case 'Enter':
      if (showList.value && activeIndex.value >= 0) {
        e.preventDefault() // 别让外层表单提交
        choose(items.value[activeIndex.value])
      }
      break
    case 'Escape':
      if (showList.value) open.value = false // 第一次：关列表
      else if (query.value) { query.value = ''; model.value = null } // 第二次：清空
      break
  }
}

注意 preventDefault 的位置：只在组件真正处理了这个按键时才阻止默认行为。没有高亮项时按回车，就让它照常提交外层的表单。 组件不应该吞掉它不处理的事件。

5.4 鼠标与焦点：事件的顺序

需求：点别处关闭、点选项选中→设计卡事件格→代码

“失焦时关闭列表”和“点击选项时选中”分开看都没问题，放在一起就有 bug：点击选项后，什么也没选上，列表直接关了。原因在于浏览器的事件顺序：

在选项的 mousedown 上调用 preventDefault()，浏览器就不会把焦点从输入框移走，blur 不会触发；直接在 mousedown 里完成选择。 好处还有一个：选完之后焦点仍在输入框里，用户可以接着打字。Vue 的写法是 @mousedown.prevent="choose(item)"。

5.5 高亮：返回数据，不返回 HTML

关键字标黄，最容易想到的写法是用正则把关键字替换成 <mark>耳机</mark>，再用 v-html 渲染。不要这样做。 商品名来自服务器，如果某个商品名是 <img src=x onerror=alert(1)>，v-html 就会执行它，这就是 XSS。 另外，关键字里如果有 (、+ 这些正则特殊字符，正则会直接报错。

更好的做法是写一个纯函数，把文本切成“命中 / 未命中”的片段数组，渲染交给模板，Vue 会自动转义：

/**
 * 把文本按关键字切成若干段，标出哪些段是命中的（不区分大小写，所有出现都标出）。
 * 返回数据而不是 HTML 字符串：渲染交给模板，永远不需要 v-html。
 *   splitByQuery('降噪耳机', '耳机') → [{ text: '降噪', hit: false }, { text: '耳机', hit: true }]
 */
export function splitByQuery(text, query) {
  const q = query.trim().toLowerCase()
  if (!q) return [{ text, hit: false }]
  const lower = text.toLowerCase()
  const parts = []
  let from = 0
  for (let i = lower.indexOf(q); i !== -1; i = lower.indexOf(q, from)) {
    if (i > from) parts.push({ text: text.slice(from, i), hit: false })
    parts.push({ text: text.slice(i, i + q.length), hit: true })
    from = i + q.length
  }
  if (from < text.length) parts.push({ text: text.slice(from), hit: false })
  return parts
}

<script setup>
import { computed } from 'vue'
import { splitByQuery } from '../lib/highlight'

const props = defineProps({ text: { type: String, required: true }, query: { type: String, default: '' } })
const parts = computed(() => splitByQuery(props.text, props.query))
</script>

<template>
  <span><template v-for="(p, i) in parts" :key="i"><mark v-if="p.hit">{{ p.text }}</mark><template v-else>{{ p.text }}</template></template></span>
</template>
Django 对照

Django 模板默认自动转义，{{ name }} 里的 < 会变成 &lt;；你只有在写 mark_safe() 或 |safe 时才需要提心吊胆。 Vue 一样：{{ }} 自动转义，v-html 就是 |safe。规则也一样：来自用户或服务器的数据，永远不要拼进 HTML 字符串。

aria-live="polite" 区域liveText“5 个结果，用上下键选择”这类不打断用户的播报

id 用 Vue 3.5 的 useId() 生成：它保证同一页面上多个组件实例的 id 不重复，服务端渲染时前后端生成的 id 也一致。 无障碍属性同样是派生数据，它们和 class 一样由状态决定，不需要额外维护。

5.7 输入框文字和选中值：两份相关的状态

问题：文字和 v-model 对不上→修改第二、三处→代码

补全框天生有两份相关的状态：组件内部的 query（输入框里的字）和外部的 v-model（选中的项）。它们必须保持一致：

  • 用户选中“降噪耳机”后，又把文字改成“降噪”：原来的选择不再成立，onInput 里把 v-model 置为 null。
  • 父组件把 v-model 设成 null（比如点了“清空”）：输入框也要清空。但如果用户正在输入，就不能清掉他的字，所以加了 !open.value 的判断。
watch(model, (m) => {
  if (m) query.value = labelOf(m)
  else if (!open.value) query.value = '' // 用户正在输入时不要清掉他的字
})

还有一个坑，是我写这个示例时自己踩到的：选中一项后，query 被回填成“头戴式耳机”，而 query 一变，搜索的 watch 就又发了一个请求，虽然列表已经关了，根本没人看结果。 问题出在设计卡 v1 的副作用格：“query 变化就搜索”并不准确，应该是“用户在看列表时，按输入的文字搜索”。把搜索的输入改成一个派生数据： 

// 只在列表打开时按输入搜索：选中后回填文字、按 Esc 关闭，都不会再发请求
const searchText = computed(() => (open.value ? query.value : ''))
const { state: result, retry } = useSearch(searchText, (q, opts) => props.search(q, opts), { /* … */ })

列表关闭时 searchText 是空字符串，useSearch 进入 idle，顺带把还在路上的请求也作废了。 给副作用一个精确的输入，比在副作用里写一堆 if 判断更清楚。

第 6 步：需求变更演练

组件的需求变更有一个特别的检验标准：能不能只改使用者的代码，不改组件。

变更一：后台要一个“选择城市”的输入框

城市只有几十个，存在前端，不用请求。组件一行不改，使用者传一个同步的过滤函数，把防抖关掉： 

<script setup>
const city = ref(null)
const searchCities = (q) => CITIES.filter((c) => c.name.includes(q) || c.py.startsWith(q.toLowerCase()))
</script>

<template>
  <AutoComplete v-model="city" :search="searchCities" item-key="code" item-label="name" :debounce="0" />
</template>

这就是第 2 步把 search 设计成“一个函数”的回报：如果当初设计的是 url 属性，现在就得给组件加一个 options 属性和一堆分支。

变更二：每一项要显示图标和价格

同样不改组件。#item 插槽拿到 item、query、active，想怎么画就怎么画（见第 2 步的用法一）。

变更三：输入框为空时，显示“最近搜索”

看起来需要给组件加一个 recent 属性。其实不用：把 minLength 设成 0，组件在聚焦时就会用空字符串调用 search， 使用者在 search 里判断一下，关键字为空就返回最近搜索： 

const search = (q, opts) => (q ? searchProducts(q, opts) : recentPicks.value)
// <AutoComplete :search="search" :min-length="0" … />

示例工程的组件测试里专门有一条用例验证这个用法。接口少而正交，组合起来就能覆盖设计时没想到的需求。

第 7 步：收尾

<script setup>
import { ref, computed, watch, nextTick, useId, useTemplateRef } from 'vue'
import { useSearch } from '../composables/useSearch'
import HighlightText from './HighlightText.vue'

// ================= 接口：先站在使用者的角度设计 =================
const model = defineModel({ default: null }) // 选中的那一项（对象），没选为 null
const props = defineProps({
  search: { type: Function, required: true }, // (query, { signal }) => Item[] | Promise<Item[]>
  itemKey: { type: String, default: 'id' }, // 每一项的唯一标识字段
  itemLabel: { type: String, default: 'label' }, // 显示和回填到输入框的字段
  minLength: { type: Number, default: 1 },
  debounce: { type: Number, default: 300 },
  placeholder: { type: String, default: '' },
})
const emit = defineEmits(['select']) // 用户选中了一项（v-model 之外的“动作”通知）
// 插槽：#item="{ item, query, active }"、#empty="{ query }"

const keyOf = (item) => item[props.itemKey]
const labelOf = (item) => item[props.itemLabel]

// ================= 状态 =================
const query = ref(model.value ? labelOf(model.value) : '') // 输入框里的文字
const open = ref(false) // 用户是否“想看”列表
const activeKey = ref(null) // 键盘 / 鼠标高亮的那一项的 key（存 key 不存下标）

// 只在列表打开时按输入搜索：选中后回填文字、按 Esc 关闭，都不会再发请求
const searchText = computed(() => (open.value ? query.value : ''))
const { state: result, retry } = useSearch(searchText, (q, opts) => props.search(q, opts), {
  debounce: () => props.debounce,
  minLength: () => props.minLength,
})

// ================= 派生 =================
const items = computed(() => result.value.items)
// 新结果里没有原来高亮的那一项时，自动变成 -1，不需要额外同步
const activeIndex = computed(() => items.value.findIndex((it) => keyOf(it) === activeKey.value))
const showList = computed(() => open.value && query.value.trim().length >= props.minLength)
const listId = useId()
const optionId = (i) => `${listId}-${i}`
const activeId = computed(() => (activeIndex.value >= 0 ? optionId(activeIndex.value) : undefined))
// 给屏幕阅读器的播报
const liveText = computed(() => {
  if (!showList.value) return ''
  if (result.value.status === 'success') return items.value.length ? `${items.value.length} 个结果，用上下键选择` : '没有结果'
  if (result.value.status === 'error') return '搜索出错'
  return ''
})

// ================= 事件 =================
function onInput(e) {
  query.value = e.target.value
  open.value = true
  activeKey.value = null
  if (model.value) model.value = null // 文字改了，原来的选择就不再成立
}
function move(delta) {
  if (!open.value) return void (open.value = true)
  const n = items.value.length
  if (!n) return
  const i = activeIndex.value
  const next = i === -1 ? (delta > 0 ? 0 : n - 1) : (i + delta + n) % n
  activeKey.value = keyOf(items.value[next])
}
function choose(item) {
  model.value = item
  query.value = labelOf(item)
  open.value = false
  activeKey.value = null
  emit('select', item)
}
function onKeydown(e) {
  switch (e.key) {
    case 'ArrowDown':
      e.preventDefault() // 否则光标会跳到行首 / 行尾
      move(1)
      break
    case 'ArrowUp':
      e.preventDefault()
      move(-1)
      break
    case 'Enter':
      if (showList.value && activeIndex.value >= 0) {
        e.preventDefault() // 别让外层表单提交
        choose(items.value[activeIndex.value])
      }
      break
    case 'Escape':
      if (showList.value) open.value = false // 第一次：关列表
      else if (query.value) { query.value = ''; model.value = null } // 第二次：清空
      break
  }
}

// ================= 副作用 =================
// 外部改了 v-model（比如父组件点了“清空”）：让输入框跟上
watch(model, (m) => {
  if (m) query.value = labelOf(m)
  else if (!open.value) query.value = '' // 用户正在输入时不要清掉他的字
})
// 键盘高亮的项滚动到可见区域
const listEl = useTemplateRef('list')
watch(activeIndex, async (i) => {
  await nextTick()
  if (i >= 0) listEl.value?.children[i]?.scrollIntoView({ block: 'nearest' })
})
</script>

<template>

    <input :value="query" role="combobox" aria-autocomplete="list" :aria-expanded="showList"
           :aria-controls="listId" :aria-activedescendant="activeId" :placeholder="placeholder"
           autocomplete="off" @input="onInput" @keydown="onKeydown" @focus="open = true" @blur="open = false">
    <span v-if="result.status === 'loading' && showList" class="ac-spin" aria-hidden="true" />

    <div v-show="showList" class="ac-pop">
      <ul :id="listId" ref="list" role="listbox" :class="{ stale: result.status === 'loading' }">
        <!-- mousedown.prevent：阻止输入框失焦，否则 blur 先关掉列表，click 就点空了 -->
        <li v-for="(item, i) in items" :id="optionId(i)" :key="keyOf(item)" role="option"

只通过接口测试组件

组件的测试应该像使用者那样使用它：传 props、模拟输入和按键，检查渲染出来的 DOM 和发出的事件，不读内部变量。 这样重构内部实现（比如把 activeIndex 改成 activeKey）时，测试一条都不用改，反而能证明重构没有破坏行为。 防抖和竞态这类和时间有关的逻辑，用 vi.useFakeTimers() 控制时间，用手动 resolve 的 Promise 控制请求返回的顺序：

const ITEMS = [{ id: 1, label: '苹果' }, { id: 2, label: '香蕉' }, { id: 3, label: '橙子' }]

function setup(search = vi.fn(async () => ITEMS), props = {}) {

}
const flush = async (ms = 300) => {
  await vi.advanceTimersByTimeAsync(ms)
  await nextTick()
}

beforeEach(() => vi.useFakeTimers())
afterEach(() => vi.useRealTimers())

describe('AutoComplete', () => {
  it('防抖：快速输入只在停顿后搜索一次', async () => {
    const { input, search } = setup()
    for (const v of ['苹', '苹果', '苹果汁']) {

    await flush(300)

自己写，还是用现成库

  • 组件库的自动补全：Element Plus 的 ElAutocomplete（自由输入 + 建议）和 ElSelect 的 filterable remote（必须从列表里选），Naive UI 的 NAutoComplete、NSelect 都开箱即用，样式也和整套组件库统一。公司项目里优先用它们。 但要检查它们是否处理了竞态：有些组件只防抖、不作废旧请求，这时你的 search 函数里要自己用 AbortController。
  • 无样式（headless）组件：Reka UI（原 Radix Vue）、Headless UI 的 Combobox 只提供行为和无障碍，外观完全自己写。设计稿和组件库风格差别很大时，这是最好的选择。 它们的接口设计和本篇非常像，读一读它们的文档，会更理解本篇的取舍。
  • 工具函数：VueUse 的 refDebounced、useDebounceFn 可以替代手写的防抖；如果搜索结果需要缓存（同一个关键字不重复请求），用 TanStack Query，第 6 个项目会讲。
  • 值得自己写一遍的原因：防抖、竞态、焦点顺序、ARIA 这四个知识点，换到任何一个“输入 → 异步结果”的场景（筛选、校验用户名、地址联想）都会再遇到。

复盘

判断题

为什么组件的 props 设计成一个 search 函数，而不是 url 字符串？

组件不该知道接口地址、参数格式、鉴权方式、返回数据怎么解析，这些都是使用者的事。一个函数既能包装远程请求，也能是本地过滤，覆盖了两种用法。设计接口时问一句“谁知道这件事”。

有了防抖，还需要处理竞态吗？

需要。防抖只减少请求数量；用户打字稍慢（间隔超过防抖时间），请求照样会一个接一个发出，返回顺序依然没有保证。两者用同一个 onCleanup 解决：取消定时器、作废请求。

高亮项为什么存 activeKey 而不是 activeIndex？

列表会随搜索结果变化，下标指向的东西会变；key 指向的永远是同一项。新结果里没有这一项时，由 key 派生的下标自动变成 −1，不需要写任何同步代码。

为什么选项用 @mousedown.prevent 而不是 @click？

点击选项时，输入框的 blur 发生在 click 之前，blur 关闭了列表，click 就落空了。在 mousedown 上阻止默认行为，输入框不会失焦，直接完成选择，焦点也留在输入框里。

使用者要在选中后跳转页面，应该 watch v-model 还是监听 select 事件？

监听 select。v-model 的变化不一定来自用户的选择（比如父组件自己赋值、用户改文字时被置为 null），跳转应该响应“用户做了选择”这个动作。值是状态，动作是事件，不要用监听状态来模拟事件。

为什么测试里不直接读组件内部的 query、activeKey？

那是实现细节。测试应该像使用者一样只通过接口（props、DOM、事件）交互，这样重构内部时测试不用改，还能证明行为没变。本篇把 activeIndex 改成 activeKey 时，测试一条都没动。

后端出身容易踩的坑

  • 默认请求按顺序返回：同步代码里“先调用先返回”，网络请求不是。凡是“输入 → 请求 → 显示”的地方，都要想一想竞态。
  • 组件知道得太多：在组件里写死接口地址、数据字段。组件的边界是“交互”，业务留给使用者。
  • 用布尔属性扩展外观：需求一多就失控，用插槽。
  • 只考虑鼠标：键盘和屏幕阅读器用户同样是用户，很多公司的产品有无障碍合规要求。
  • 用 v-html 拼 HTML：和 Django 里滥用 |safe 一样危险。
本篇新增的方法
  1. 设计组件先写用法：接口是第五个格子，而且是第一个要填的格子。
  2. 按“谁知道什么”划分组件和使用者的职责；外观用插槽，行为用 props。
  3. “上一次的副作用作废”：防抖、竞态、订阅，都用 watch + onCleanup。
  4. 给副作用一个精确的输入（派生数据），而不是在副作用里堆判断。
  5. 引用列表里的一项，存 key 不存下标。
  6. 交互控件先查 ARIA 模式，无障碍属性也是由状态派生的。
  7. 组件只通过接口测试；时间和顺序用假定时器、手动 Promise 控制。

练习

  1. 中文输入法：用拼音输入法打“耳机”时，拼写过程中的 “er”“erji” 也会触发搜索。监听 compositionstart / compositionend，拼写过程中不更新 searchText。这需要一个新状态吗？它属于哪一格？
  2. 结果缓存：同一个关键字 1 分钟内不重复请求。缓存应该放在组件里、useSearch 里，还是使用者的 search 函数里？为什么？
  3. 多选：做一个“选择多个标签”的版本，选中的项显示成输入框前面的小标签，退格键删除最后一个。v-model 变成什么？哪些逻辑可以复用 useSearch？
  4. 受控的 query：有的使用者想拿到输入框的文字（比如回车时跳到搜索结果页）。设计一个 v-model:query，想一想它和内部的 query 状态是什么关系。
