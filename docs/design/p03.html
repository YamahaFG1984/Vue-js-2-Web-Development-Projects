项目 3 · 第一阶段 · 状态思维

购物车

从这一篇开始进入“小商城”业务场景。购物车是电商里最经典的功能，也是第一个跨页面的状态： 顶部的角标、商品列表、商品详情、购物车页、结算页，五个地方都要读写同一份数据。 这一篇要回答三个问题：跨页面的状态放在哪？购物车里该存什么、不该存什么？前端算出来的金额，能不能直接拿去收钱？

本篇目标

  • 判断状态的作用范围：组件内、父子之间、还是全局共享
  • 分清意图和事实：购物车存引用，订单存快照
  • 把业务计算写成纯函数，并用单元测试守住它
  • 以服务器为准：前端的金额只是预览，提交时由服务器重新核算
  • Vue 生态：Vue Router（路由参数、props: true、导航守卫）、Pinia（setup store、store 之间互相使用）、Vitest

先看成品

这是一个真正带路由和 Pinia 的迷你商城（用的是内存路由，所以上面那条“地址栏”是模拟的）。试试这个流程： 加几件商品 → 去购物车改数量、取消勾选、输入优惠码 SAVE15 → 点右边的“服务器给咖啡壶涨价” → 去结算提交，看看会发生什么。

Django 对照

Django 里做购物车，经典写法是把它存在 request.session['cart'] 里，再包一个 Cart(request) 类，任何视图都能用。 session 里存的也只是 {product_id: quantity}，显示时再查 Product 拿价格；下单时，OrderItem 把当时的价格存成一个字段。 这一篇的设计和它一模一样，只是“session”换成了前端的 Pinia store 和 localStorage。

第 1 步：需求与草图

  • 商品列表：每个商品可以直接“加入购物车”；售罄的不能加；顶部角标显示购物车里一共几件
  • 商品详情：选数量后加入购物车，数量不能超过库存
  • 购物车：修改数量、删除、勾选要结算的商品、全选；满 99 元包邮，否则运费 10 元
  • 结算：确认商品和金额，提交订单；成功后从购物车移除已购买的商品
  • 刷新页面、关掉浏览器再打开，购物车还在

第 3 步：状态放在哪

按前两篇的做法，购物车放在 App 上，再用 props 往下传。画出来就会发现走不通：

中间的“模块级 ref”值得多说一句：把 const items = ref([]) 写在组合式函数外面（模块顶层），所有调用这个函数的组件拿到的就是同一个 ref。 小项目里这完全能用，很多人也确实这么写。Pinia 本质上就是把这个做法规范化了，并补上了它的几个短板。 而且 Pinia 的 setup store 写法和组合式函数几乎一模一样，你在番茄钟、记账本里写的 usePomodoro、useLedger，换个外壳就是 store。

store 不是“放所有状态的地方”

有了 store，很容易把什么都往里放。规则不变：只有跨页面、跨组件树共享的状态才进 store。 详情页选的数量、优惠码输入框的草稿、结算页的提交状态，都只属于各自的组件，放进 store 反而要操心“离开页面时要不要清空”。

于是这个应用有两个 store：

  • catalog：商品目录。它是服务器数据在前端的缓存，有“加载中 / 成功 / 失败”几种状态。
  • cart：购物车。它是用户在这台设备上的数据，要持久化到 localStorage；计算金额时要查 catalog，所以 cart store 会使用 catalog store。

5.1 路由：一个应用，多个“页面”

需求：列表、详情、购物车、结算四个页面→路由表→代码

单页应用里的“页面”只是组件：地址变了，<RouterView> 换一个组件来显示，浏览器并不会真的重新加载。路由表就是前端的 urls.py： 

import { createRouter, createWebHistory } from 'vue-router'
import { useCartStore } from './stores/cart'
import ProductList from './views/ProductList.vue'
import ProductDetail from './views/ProductDetail.vue'
import CartView from './views/CartView.vue'
import CheckoutView from './views/CheckoutView.vue'

export const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/', name: 'home', component: ProductList },
    // props: true 把路由参数 id 作为 prop 传给组件，组件不必知道自己被路由使用
    { path: '/product/:id', name: 'product', component: ProductDetail, props: true },
    { path: '/cart', name: 'cart', component: CartView },
    {
      path: '/checkout',
      name: 'checkout',
      component: CheckoutView,
      // 路由守卫：没有可结算的商品就不让进，类似 Django 视图开头的 redirect
      beforeEnter: () => {
        const cart = useCartStore()
        if (!cart.checkoutLines.length) return { name: 'cart' }
      },
    },
  ],
})

详情页里，“当前是哪个商品”不是状态，而是由路由参数和商品目录派生出来的：

这是一个重要的认识：URL 也是一种状态，而且是最特别的一种。它能被收藏、分享、刷新后保留，浏览器的前进后退会改变它。 详情页如果把“当前商品”另存一个 ref，就要操心它和地址栏同步；直接从参数派生，就不会有这个问题。第 6 个项目（后台数据表格）会把这个思路用到极致。

5.2 撞墙：状态要跨页面共享

问题：五个地方要用购物车→改变状态的位置→代码

图 3-2 已经说明了 props 走不通。换成 Pinia：在 main.js 里装上，然后用 defineStore 定义 store。 setup store 的函数体和组合式函数一样：ref 是状态，computed 是派生（Pinia 叫 getter），普通函数是事件（Pinia 叫 action），最后 return 出去。 

import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'
import { router } from './router'
import './styles.css'

createApp(App)
  .use(createPinia()) // 先装 Pinia：路由守卫里要用 store
  .use(router)
  .mount('#app')

import { defineStore } from 'pinia'
import { ref, computed } from 'vue'
import { fetchProducts } from '../api/shop'

// 商品目录：服务器数据在前端的一份缓存
export const useCatalogStore = defineStore('catalog', () => {
  const products = ref([])
  const status = ref('idle') // 'idle' | 'loading' | 'ready' | 'error'
  const error = ref('')

  const byId = computed(() => Object.fromEntries(products.value.map((p) => [p.id, p])))

  async function load() {
    status.value = 'loading'
    try {
      products.value = await fetchProducts()
      status.value = 'ready'
    } catch (e) {
      error.value = e.message
      status.value = 'error'
    }
  }

  return { products, status, error, byId, load }
})

status 又是一个状态机：'idle' | 'loading' | 'ready' | 'error'。服务器数据天生就有这几种状态，界面要为每一种都准备好显示什么。 任何组件里调用 useCatalogStore()，拿到的都是同一个 store： 

<script setup>

const cart = useCartStore()

不要直接解构 store

const { count } = useCartStore() 会丢失响应性：解构出来的只是那一刻的值，以后不会更新。 要么像上面这样整体使用 cart.count，要么用 storeToRefs(cart) 解构状态和 getter（action 可以直接解构）。

5.3 购物车里存什么：意图和事实

问题：价格存在哪→改设计卡→代码

回到第 4 步的伏笔。v1 在购物车条目里抄了一份 name 和 price。设想：用户周一把咖啡壶加进购物车，当时 129 元；周三商家调价到 139 元； 周五用户打开购物车，看到的还是 129 元，结算时却发现要付 139 元（或者更糟：系统按 129 元收了钱）。

可订单里明明就是要存价格的。区别在哪？

这和番茄钟的“存事实，不存结果”是同一条原则的另一面：订单的价格是一个已经发生的事实，必须原样保留，否则改价会篡改历史账单； 而购物车只是一个意图，“我想买两个 p1”，此刻价格多少应该随时去查。Django 里，OrderItem 有自己的 price 字段， 而 session 里的购物车只存 product_id 和数量，道理完全相同。

派生
lines = cartItems 逐项拼上 catalog 里的商品（相当于 JOIN）
每行的 problem：已下架 / 已售罄 / 库存不足
subtotal 改为基于 lines 里商品的当前价格

数量调节器是一个可复用的小组件，用 defineModel 实现 v-model，并负责把输入限制在 min 到 max 之间：

<script setup>
const qty = defineModel({ type: Number, required: true })
const props = defineProps({
  min: { type: Number, default: 1 },
  max: { type: Number, default: Infinity },
})

function set(n) {
  if (Number.isFinite(n)) qty.value = Math.min(props.max, Math.max(props.min, Math.round(n)))
}
</script>

<template>

5.4 金额：写成纯函数

需求：小计、运费、合计→派生格→代码

金额计算会在好几个地方用到：购物车页、结算页，还有服务器下单时核算。如果写成 store 里的一个 computed，它就和 store 绑死了。 更好的做法是写成一个纯函数：输入商品行，输出各项金额；不读响应式数据，不改任何东西。store 里的 computed 只负责调用它： 

// 纯函数：输入商品行和优惠码，输出各项金额（单位：分）。
// 不读任何响应式数据、不改任何东西，所以可以在购物车、结算页、服务器、单元测试里随处复用。

export const COUPONS = {
  SAVE15: { label: '满 100 减 15', min: 10000, discount: () => 1500 },
  VIP90: { label: '9 折，最多减 50 元', min: 0, discount: (subtotal) => Math.min(5000, Math.round(subtotal * 0.1)) },
}
export const FREE_SHIPPING_MIN = 9900 // 满 99 包邮（按优惠后的金额算）
export const SHIPPING_FEE = 1000

/**
 * @param {{ price: number, qty: number }[]} lines
 * @param {string} [couponCode]
 */
export function priceOrder(lines, couponCode = '') {
  const subtotal = lines.reduce((sum, l) => sum + l.price * l.qty, 0)

  const coupon = COUPONS[couponCode]
  let discount = 0
  let shortfall = 0 // 还差多少能用券
  if (coupon) {
    if (subtotal >= coupon.min) discount = Math.min(subtotal, coupon.discount(subtotal))
    else shortfall = coupon.min - subtotal
  }

  const afterDiscount = subtotal - discount
  const shipping = lines.length === 0 || afterDiscount >= FREE_SHIPPING_MIN ? 0 : SHIPPING_FEE
  return { subtotal, discount, shortfall, shipping, total: afterDiscount + shipping }
}

纯函数最大的好处是好测。不需要浏览器、不需要挂载组件，给输入、断言输出：

import { describe, it, expect } from 'vitest'
import { priceOrder } from './pricing'

const coffee = { price: 12900, qty: 1 }
const notebook = { price: 1990, qty: 2 }

describe('priceOrder', () => {
  it('空购物车一切为 0，也不收运费', () => {
    expect(priceOrder([])).toEqual({ subtotal: 0, discount: 0, shortfall: 0, shipping: 0, total: 0 })
  })

  it('不满 99 收 10 元运费', () => {
    expect(priceOrder([notebook])).toMatchObject({ subtotal: 3980, shipping: 1000, total: 4980 })
  })

  it('满减券：达到门槛才减', () => {
    expect(priceOrder([coffee], 'SAVE15')).toMatchObject({ discount: 1500, total: 11400 })
    expect(priceOrder([notebook], 'SAVE15')).toMatchObject({ discount: 0, shortfall: 6020 })
  })

  it('打折券四舍五入到分，并且有封顶', () => {
    expect(priceOrder([{ price: 1999, qty: 1 }], 'VIP90').discount).toBe(200) // 199.9 分 → 200 分
    expect(priceOrder([{ price: 89900, qty: 1 }], 'VIP90').discount).toBe(5000)
  })

  it('包邮按优惠后的金额判断', () => {
    // 108 元，减 15 后 93 元，不再包邮
    expect(priceOrder([{ price: 10800, qty: 1 }], 'SAVE15')).toMatchObject({ shipping: 1000, total: 10300 })
  })

  it('无效的优惠码当作没有', () => {
    expect(priceOrder([coffee], 'NOPE')).toMatchObject({ discount: 0, total: 12900 })
  })
})

5.5 勾选与全选

需求：勾选要结算的商品、全选→设计卡→代码

每一项“勾没勾”是状态，存在条目的 selected 上。（它算领域数据还是界面状态？各大电商的做法是把勾选状态也保存下来，换台设备打开还是勾着的，所以这里把它当作购物车数据的一部分。） “全选框勾没勾”则是派生：当且仅当每一项都勾上了。点击全选框是一个事件，它把所有条目设成同一个值： 

const allSelected = computed(() => items.value.length > 0 && items.value.every((i) => i.selected))

function toggleAll() {
  const next = !allSelected.value // 先算出目标值，再统一设置
  for (const i of items.value) i.selected = next
}

为什么要先存 next？如果在循环里每次都读 !allSelected.value，第一项改完之后 allSelected 的值就变了，后面几项会得到相反的结果。 这和番茄钟 finish() 里“先读 nextPhase 再改 completed”是同一个坑：派生数据会在同一个函数里立刻变化。

5.6 结算：以服务器为准

需求：提交订单→推翻第二处→代码

v1 的事件格写的是“把 total 发给服务器下单”。如果你在 Django 里看到一个表单把价格放在隐藏字段 <input type="hidden" name="price"> 里提交， 而视图直接拿它来扣款，你一定会拦下来：用户打开开发者工具就能把价格改成 1 分钱。前端算出来的金额同理，只是给用户看的预览。

正确的分工是：

  • 前端只提交“买什么、买几个、用什么券”，另外附上它显示给用户的金额 expectedTotal；
  • 服务器用自己的价格和库存重新算一遍；如果和 expectedTotal 不一致，说明前端的商品目录过时了，拒绝下单；
  • 前端收到拒绝，重新拉取商品目录，让用户看到新金额后再确认。

注意图里那一句“购物车只存 id，金额自动按新价重算”。这正是 5.3 节规范化的回报：处理“价格变了”这种情况，前端只需要重新拉一次商品目录，一行修正金额的代码都不用写。 如果购物车里抄了价格，这里就要逐条去改。

结算页的提交过程又是一个状态机：idle → submitting → done | failed。用一个 state 表示，按钮的禁用、文字、错误提示都从它派生： 

<script setup>
import { ref } from 'vue'
import { useCartStore } from '../stores/cart'
import { useCatalogStore } from '../stores/catalog'
import { submitOrder } from '../api/shop'
import { priceOrder } from '../lib/pricing'
import { formatCents } from '../lib/money'
import PriceSummary from '../components/PriceSummary.vue'

const cart = useCartStore()
const catalog = useCatalogStore()

// 提交过程是一个状态机：
//   { status: 'idle' } | { status: 'submitting' } | { status: 'done', order } | { status: 'failed', message }
const state = ref({ status: 'idle' })

async function placeOrder() {
  if (state.value.status === 'submitting') return // 防止重复提交
  state.value = { status: 'submitting' }
  const items = cart.checkoutLines.map((l) => ({ productId: l.productId, qty: l.qty }))
  try {
    const order = await submitOrder({ items, couponCode: cart.couponCode, expectedTotal: cart.summary.total }, priceOrder)
    cart.removePurchased(order.lines.map((l) => l.productId))
    state.value = { status: 'done', order }
  } catch (e) {
    // 价格或库存变了：重新拉商品目录。购物车只存了 id，所以所有金额会自动按新价格重算
    if (e.code === 'PRICE_CHANGED' || e.code === 'OUT_OF_STOCK' || e.code === 'NOT_FOUND') await catalog.load()
    const hint = e.code === 'PRICE_CHANGED' ? '，已更新为最新价格，请确认后重新提交' : ''
    state.value = { status: 'failed', message: e.message + hint }
  }
}
</script>

<template>
  <section v-if="state.status === 'done'" class="panel done">
    <h1>下单成功</h1>
    <p>订单号 #{{ state.order.id }}</p>
    <ul>
      <!-- 订单显示的是快照价格：以后商品改价，这里不会变 -->
      <li v-for="l in state.order.lines" :key="l.productId">{{ l.emoji }} {{ l.name }} × {{ l.qty }}　{{ formatCents(l.price * l.qty) }}</li>
    </ul>
    <p>实付 <b>{{ formatCents(state.order.total) }}</b></p>
    <RouterLink to="/">继续购物</RouterLink>
  </section>

  <section v-else class="checkout">
    <h1>确认订单</h1>
    <ul class="lines plain">
      <li v-for="l in cart.checkoutLines" :key="l.productId">
        {{ l.product.emoji }} {{ l.product.name }} × {{ l.qty }}<span>{{ formatCents(l.product.price * l.qty) }}</span>
      </li>
    </ul>
    <p v-if="!cart.checkoutLines.length" class="muted">没有可结算的商品了，<RouterLink to="/cart">回购物车</RouterLink></p>
    <PriceSummary :summary="cart.summary" />
    <p v-if="state.status === 'failed'" class="warn" role="alert">{{ state.message }}</p>

  </section>
</template>

/**
 * 下单。服务器不相信客户端算的金额：它用自己的价格和库存重新算一遍，
 * 和客户端看到的金额（expectedTotal）不一致就拒绝。
 */
export async function submitOrder({ items, couponCode, expectedTotal }, priceOrder) {
  await delay(600)
  const lines = []
  for (const { productId, qty } of items) {
    const p = db.products.find((p) => p.id === productId)
    if (!p) throw Object.assign(new Error('商品已下架'), { code: 'NOT_FOUND', productId })
    if (p.stock < qty) throw Object.assign(new Error(`「${p.name}」库存不足`), { code: 'OUT_OF_STOCK', productId })
    lines.push({ productId, name: p.name, emoji: p.emoji, price: p.price, qty })
  }
  // 真实项目里服务器用自己的代码计算；这里为了演示，复用同一个纯函数
  const summary = priceOrder(lines, couponCode)
  if (summary.total !== expectedTotal) {
    throw Object.assign(new Error('商品价格有变动'), { code: 'PRICE_CHANGED', total: summary.total })
  }
  for (const l of lines) db.products.find((p) => p.id === l.productId).stock -= l.qty
  // 订单里的价格是“下单那一刻”的快照，以后商品改价也不影响
  return { id: db.nextOrder++, lines, ...summary, createdAt: new Date().toISOString() }
}

变更二：库存不足、售罄、下架

购物车里的商品，几天后再看可能已经卖完或下架了。直觉的做法是写一个 watch：发现库存不够，就自动把数量改小，或者把条目删掉。不要这样做。

  • 自动修改用户的数据，用户会困惑：“我明明加了 3 个，怎么变成 1 个了？”
  • 商品目录还在加载时，所有商品都“找不到”，自动删除会把购物车清空。
  • “状态变了就去改另一个状态”的 watch，会让数据流变得难以追踪。

更好的做法是：问题是派生出来的，修正由用户的事件完成。lines 里每一行都带一个 problem（只在商品目录加载完成后才判断）， 有问题的行标红、不参与结算，用户自己决定是减少数量还是删除。checkoutLines 天然排除了它们，合计也就自动正确了。

变更三：多个标签页同步

用户在两个标签页里都打开了商城，在一个里加了商品，另一个的角标没变。localStorage 被修改时，浏览器会在其他同源标签页里触发 storage 事件，监听它，再从存储里重新读一次就行： 

// App.vue

onUnmounted(() => window.removeEventListener('storage', onStorage))

因为购物车的所有读写都经过 cart store 这一个入口，同步只需要在一处替换 items，角标、列表、金额全部自动更新。 如果购物车数据散落在各个组件里，这个需求会难得多。

第 7 步：收尾

import { defineStore } from 'pinia'
import { ref, computed, watch } from 'vue'
import { useCatalogStore } from './catalog'
import { priceOrder, COUPONS } from '../lib/pricing'

const STORAGE_KEY = 'cart-v1'

function load() {
  try {
    return JSON.parse(localStorage.getItem(STORAGE_KEY)) ?? {}
  } catch {
    return {}
  }
}

export const useCartStore = defineStore('cart', () => {
  const catalog = useCatalogStore() // 一个 store 可以直接使用另一个 store
  const saved = load()

  // ---------------- 状态 ----------------
  // 只存“想买什么、买几个、勾没勾”，不存名称和价格：那些以商品目录为准
  const items = ref(saved.items ?? []) // [{ productId, qty, selected }]
  const couponCode = ref(saved.couponCode ?? '')

  // ---------------- 派生 ----------------
  // 购物车条目 + 商品目录 = 可以显示的商品行（相当于一次 JOIN）
  const lines = computed(() => items.value.map((item) => {
    const product = catalog.byId[item.productId] ?? null
    let problem = ''
    if (catalog.status === 'ready') {
      if (!product) problem = '商品已下架'
      else if (product.stock === 0) problem = '已售罄'
      else if (product.stock < item.qty) problem = `库存仅剩 ${product.stock} 件`
    }
    return { ...item, product, problem }
  }))
  const count = computed(() => items.value.reduce((n, i) => n + i.qty, 0))
  const allSelected = computed(() => items.value.length > 0 && items.value.every((i) => i.selected))
  // 真正要结算的：勾选了、商品信息已加载、而且没有问题
  const checkoutLines = computed(() => lines.value.filter((l) => l.selected && l.product && !l.problem))
  const summary = computed(() =>
    priceOrder(checkoutLines.value.map((l) => ({ price: l.product.price, qty: l.qty })), couponCode.value))
  const coupon = computed(() => COUPONS[couponCode.value] ?? null)

  // ---------------- 事件 ----------------
  const find = (productId) => items.value.find((i) => i.productId === productId)
  const qtyOf = (productId) => find(productId)?.qty ?? 0

  function add(productId, qty = 1) {
    const stock = catalog.byId[productId]?.stock ?? 0
    const item = find(productId)
    if (item) item.qty = Math.min(stock, item.qty + qty)
    else if (stock > 0) items.value.push({ productId, qty: Math.min(stock, qty), selected: true })
  }
  function setQty(productId, qty) {
    const item = find(productId)
    if (item) item.qty = Math.max(1, qty)
  }
  function remove(productId) {
    items.value = items.value.filter((i) => i.productId !== productId)
  }
  function toggle(productId) {
    const item = find(productId)
    if (item) item.selected = !item.selected
  }
  function toggleAll() {
    const next = !allSelected.value // 先算出目标值，再统一设置
    for (const i of items.value) i.selected = next
  }
  function applyCoupon(code) {
    const c = code.trim().toUpperCase()
    if (!COUPONS[c]) return false
    couponCode.value = c
    return true
  }
  function clearCoupon() {
    couponCode.value = ''
  }
  function removePurchased(productIds) {
    items.value = items.value.filter((i) => !productIds.includes(i.productId))
    couponCode.value = '' // 优惠券用掉了
  }
  // 其他标签页改了购物车：用存储里的新值替换内存里的
  function syncFromStorage() {
    const s = load()
    items.value = s.items ?? []
    couponCode.value = s.couponCode ?? ''
  }

  // ---------------- 副作用：持久化 ----------------
  watch([items, couponCode], () => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify({ version: 1, items: items.value, couponCode: couponCode.value }))
  }, { deep: true })

  return {
    items, couponCode,
    lines, count, allSelected, checkoutLines, summary, coupon,
    qtyOf, add, setQty, remove, toggle, toggleAll, applyCoupon, clearCoupon, removePurchased, syncFromStorage,
  }
})

export { STORAGE_KEY as CART_STORAGE_KEY }

上线清单

从这一篇开始，每个业务组件都附一份“上线前要检查什么”。演示能跑和能上线之间，差的就是这些：

方面检查项
空、加载、出错空购物车有引导；商品目录加载中有占位、失败能重试；购物车先于目录渲染时不报错、不误判“已下架”
金额全程整数分；显示统一用一个格式化函数；priceOrder 有单元测试；服务器重新核算
提交防重复提交（按钮禁用 + 函数开头检查状态）；价格、库存变化时给出明确提示；网络失败可重试
边界数量不能小于 1、不能超过库存、输入非数字时恢复原值；直接访问 /checkout 有守卫
无障碍加减按钮有 aria-label；勾选框有可读的标签；角标数量变化用 aria-live 播报；错误提示用 role="alert"
持久化存储里带 version；读取失败时降级为空购物车而不是白屏；多标签页同步
测试纯函数单测；一条端到端测试走完“加购 → 改数量 → 用券 → 改价 → 提交”

自己写，还是用现成库

  • 持久化：本篇在 store 里手写了一个 watch，十几行就够了，也看得清原理。如果项目里有很多 store 需要持久化，可以用 pinia-plugin-persistedstate，在 store 上加一个 persist 选项即可。
  • 数量调节器、复选框：Element Plus 的 ElInputNumber、Naive UI 的 NInputNumber 已经处理好了键盘、长按、精度等细节，公司项目直接用。自己写一遍的价值在于明白 v-model 组件是怎么回事。
  • 购物车列表：电商的购物车页面通常有强烈的设计风格，一般基于组件库的基础组件自己组装，而不是套一个现成的“购物车组件”。
  • 金额计算：一定自己写，并且写成纯函数加测试。这是业务规则，没有通用的库能替你决定“包邮按优惠前还是优惠后算”。如果涉及汇率、多币种，再考虑 dinero.js 这类专门处理金额的库。

判断题

详情页上“选几件”的数量，要不要放进 cart store？

不要。它只属于详情页，离开页面就没有意义了。放进 store 反而要操心“换一个商品时要不要重置”。只有跨页面、跨组件树共享的状态才进 store。

购物车要不要存商品价格？订单呢？

购物车不存：它是还没发生的意图，价格以商品目录为准。订单要存：它是已经发生的事实，下单那一刻的价格必须原样保留，以后改价不能篡改历史。

前端已经算好了合计，下单时服务器为什么还要再算一遍？

两个原因：前端的商品目录可能过时（价格、库存变了）；前端的任何数据都能被用户篡改。前端的金额只是预览，服务器的金额才算数。expectedTotal 的作用是让服务器发现“用户看到的和实际的不一样”，从而拒绝并让用户确认。

发现某件商品库存不足，为什么不用 watch 自动把购物车里的数量改小？

自动改用户的数据会让人困惑；商品目录未加载时会误判；而且“状态变了就去改另一个状态”会让数据流难以追踪。把问题作为派生数据显示出来，修正交给用户的操作。

const { count, add } = useCartStore() 有什么问题？

count 是 getter，解构后只是那一刻的数字，不会再更新；add 是函数，解构没问题。要解构状态和 getter，用 storeToRefs(store)。

详情页的“当前商品”为什么用 computed 从路由参数派生，而不是在 onMounted 里查出来存进 ref？

从详情页 A 点到详情页 B 时，Vue Router 会复用同一个组件实例，onMounted 不会再执行，ref 里还是 A。从 props.id 派生则永远和地址栏一致。URL 是状态，别再复制一份。

后端出身容易踩的坑

  • 相信前端算的金额：前端的一切都可以被篡改，金额、库存、权限，最终都要由服务器判定。
  • 把服务器数据当成前端自己的数据：商品目录只是一份缓存，随时可能过时。要想清楚什么时候刷新、发现过时后怎么办。
  • 所有状态都塞进 store：store 是给共享状态用的，局部状态留在组件里。
  • 业务计算散落在组件里：抽成纯函数，才能复用、才能测试。
  • 用 watch 修补数据：问题用派生数据暴露，修正交给事件。
本篇新增的方法
  1. 给每份状态问一句“谁在用”：组件内、父子共用、跨页面，分别放在组件、父组件、store。
  2. 区分意图和事实：意图存引用、以最新数据为准；事实存快照、永不改变。
  3. 业务计算写成纯函数，响应式代码只负责准备输入；用测试记录业务决定。
  4. 服务器数据是缓存：设计好加载状态、过时后如何发现、如何刷新。
  5. 前端的金额只是预览，以服务器为准。
  6. URL 也是状态：能从路由派生的，不另存一份。

练习

  1. 降价提醒：购物车里的商品如果比加入时降价了，显示“比加入时降了 ¥10”。这需要在条目上记什么？它算意图还是事实？会不会破坏“购物车不存价格”的原则？
  2. 定时刷新目录：用户在购物车页停留超过 5 分钟，自动重新拉一次商品目录。这是副作用，它的启动和清理分别放在哪里？离开购物车页时要停吗？
  3. 登录后合并购物车：未登录时购物车存在本地，登录后要和服务器上的购物车合并，同一商品数量相加。设计卡哪几格要变？冲突（合并后超过库存）怎么处理？
  4. 给 CheckoutView 写端到端测试：用 Playwright 模拟“改价后提交被拒、确认后成功”。（提示：示例工程的“模拟服务器”面板就是为此准备的。）
