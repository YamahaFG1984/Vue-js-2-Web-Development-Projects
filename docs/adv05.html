AI 应用前端：流式聊天界面

如今很多应用都内置了一个 AI 助手。它的界面看似简单，就是一个聊天框，但要做好并不容易：回答要一个字一个字地流出来， 用户要能随时停止，Markdown 和代码要安全地渲染，滚动要跟得上又不能打扰用户往上翻。 本章用 Vue 3 做一个完整的流式聊天界面，后端用轻量的 Hono 框架调用 DeepSeek API。第 8 章学过的 SSE，在这里会派上大用场。

本章目标

  • 理解 AI 应用的基本架构，以及为什么 API 密钥绝不能放在前端
  • 理解流式输出的价值，以及 SSE 数据是怎么一块一块到达的
  • 用 Hono 写一个流式转发接口：调用 DeepSeek、翻译事件格式、客户端断开时停止生成
  • 把 API 密钥放进 .env 并加入 .gitignore
  • 用 fetch + ReadableStream 读取流，写一个 useChat 组合式函数，并展示模型的“思考过程”
  • 用 AbortController 实现“停止生成”
  • 安全地渲染流式 Markdown：节流、markdown-it、DOMPurify
  • 处理聊天界面的细节：自动滚动、回车发送与中文输入法、无障碍

整体架构

⚠ API 密钥永远不能出现在前端代码里

第 4 章讲过：所有 VITE_ 开头的环境变量都会被原样打包进 JS 文件，任何人打开开发者工具都能看到。 一旦泄露，别人就能用你的账户无限调用、产生费用。所以一定要有一个自己的后端：密钥只放在服务器的 .env 文件里（并加入 .gitignore），并且在这里做登录校验和限流（比如每个用户每分钟最多 10 次）。

为什么要流式输出

大模型生成一段长回答可能要十几秒甚至更久。如果等它全部生成完再一次性返回，用户会盯着转圈图标干等。 流式输出则是模型每生成一小段文字就立刻发过来，用户不到一秒就能看到第一个字，然后边生成边阅读：

传输格式就是第 8 章的 SSE：服务器保持连接不关闭，每次写一段 event: …\ndata: …\n\n。 不过第 8 章用的 EventSource 只能发 GET 请求，而聊天需要用 POST 把整段对话发过去，所以前端要改用 fetch 自己读取响应流。

后端：用 Hono 转发 DeepSeek 的流

后端我们用 Hono。它是一个很小的 Web 框架，路由写法和 Express 很像，但基于浏览器同款的 Request / Response 标准， 同一份代码可以跑在 Node.js、Bun、Deno 和 Cloudflare Workers 上。它还自带了我们正需要的 SSE 工具 streamSSE。 模型用 DeepSeek，它的接口与 OpenAI 格式兼容，用普通的 fetch 就能调用，不需要额外的 SDK。

⚠ 密钥一旦提交，就当它已经泄露

git 会永久保存历史，删掉文件再提交一次并不能把密钥从历史里抹去，GitHub 上的公开仓库还会被机器人在几分钟内扫描到。 如果不小心提交了，第一件事是到 DeepSeek 控制台作废这个密钥、换一个新的，然后再清理历史。

上游的格式和我们的格式

DeepSeek 返回的也是 SSE，但每一条都是一大段 JSON，而且推理模型会先流出“思考过程”（reasoning_content），再流出正式回答（content），最后是一个不是 JSON 的 [DONE]。 服务器把它翻译成我们自己定义的、更简单的几种事件，这样前端完全不用关心用的是哪家模型：

完整的服务器代码

解析上游 SSE 用的正是下一节要写的 readSSE()，前后端共用一个解析函数：

import { Hono } from 'hono'
import { serve } from '@hono/node-server'
import { streamSSE } from 'hono/streaming'
import { zValidator } from '@hono/zod-validator'
import { z } from 'zod'
import { readSSE } from '../src/lib/readSSE.js'

const API_KEY = process.env.DEEPSEEK_API_KEY       // 用 node --env-file=.env 启动时读入
if (!API_KEY) throw new Error('缺少 DEEPSEEK_API_KEY，请在 .env 中配置')

const SYSTEM_PROMPT = '你是一个友好的 Vue 助教。用简体中文回答，适当使用 Markdown 和代码块。'

// 只接受 user / assistant 交替出现、以 user 结尾的纯文本消息
const ChatBody = z.object({
  messages: z
    .array(z.object({
      role: z.enum(['user', 'assistant']),
      content: z.string().min(1).max(8000),
    }))
    .min(1)
    .max(50)
    .refine(
      (ms) => ms.every((m, i) => m.role === (i % 2 === 0 ? 'user' : 'assistant')) && ms.at(-1).role === 'user',
      '消息必须以 user 开始、交替出现、以 user 结束',
    ),
})

const app = new Hono()

app.post(
  '/api/chat',
  zValidator('json', ChatBody, (result, c) => {
    if (!result.success) return c.json({ message: '消息格式不正确' }, 400)
  }),
  async (c) => {
    const { messages } = c.req.valid('json')
    const upstreamAbort = new AbortController()

    const upstream = await fetch('https://api.deepseek.com/chat/completions', {
      method: 'POST',
      headers: { Authorization: `Bearer ${API_KEY}`, 'Content-Type': 'application/json' },
      body: JSON.stringify({
        model: 'deepseek-flash',
        stream: true,
        reasoning_effort: 'low',                   // 聊天场景少想一点，回答更快
        stream_options: { include_usage: true },   // 最后一块附带 token 用量
        messages: [{ role: 'system', content: SYSTEM_PROMPT }, ...messages],
      }),
      signal: upstreamAbort.signal,
    })

    if (!upstream.ok) {
      console.error('DeepSeek 返回错误', upstream.status, await upstream.text())
      const message = upstream.status === 429 ? '请求太频繁，请稍后再试' : 'AI 服务暂时不可用'
      return c.json({ message }, 502)              // 不把上游的错误细节暴露给前端
    }

    return streamSSE(
      c,
      async (stream) => {
        // 浏览器断开（用户点了停止或关掉页面）→ 中止对 DeepSeek 的请求，不再产生费用
        stream.onAbort(() => upstreamAbort.abort())

        let finishReason = null
        let usage = null
        for await (const { data } of readSSE(upstream.body)) {
          if (data === '[DONE]') break
          const chunk = JSON.parse(data)
          const choice = chunk.choices?.[0]
          if (choice?.delta?.reasoning_content) {
            await stream.writeSSE({ event: 'reasoning', data: JSON.stringify({ text: choice.delta.reasoning_content }) })
          }
          if (choice?.delta?.content) {
            await stream.writeSSE({ event: 'delta', data: JSON.stringify({ text: choice.delta.content }) })
          }
          if (choice?.finish_reason) finishReason = choice.finish_reason
          if (chunk.usage) usage = chunk.usage
        }
        await stream.writeSSE({ event: 'done', data: JSON.stringify({ finishReason, usage }) })
      },
      // 第三个参数：流式过程中出错时调用
      async (err, stream) => {
        if (upstreamAbort.signal.aborted) return   // 是我们主动中止的，不算错误
        console.error(err)
        await stream.writeSSE({ event: 'error', data: JSON.stringify({ message: '生成失败，请稍后重试' }) })
      },
    )
  },
)

serve({ fetch: app.fetch, port: 3000 })

读取流：前后端共用的解析器

不管是服务器读 DeepSeek，还是浏览器读我们的服务器，fetch 返回的 response.body 都是一个 ReadableStream，可以一块一块地读。但要注意： 网络传输的“块”和 SSE 的“事件”并不对齐。一个块里可能有半个事件，也可能有好几个事件，所以必须自己做缓冲： 

// 把一个 SSE 响应体变成异步迭代器：for await (const { event, data } of readSSE(body))
// data 是原始字符串，由调用者决定怎么解析（DeepSeek 最后会发一个非 JSON 的 [DONE]）
export async function* readSSE(body) {
  const reader = body.pipeThrough(new TextDecoderStream()).getReader()   // 字节 → 文本
  let buffer = ''
  while (true) {
    const { value, done } = await reader.read()
    if (done) return
    buffer += value.replaceAll('\r\n', '\n')
    let end
    while ((end = buffer.indexOf('\n\n')) !== -1) {      // 找到一个完整事件
      const raw = buffer.slice(0, end)
      buffer = buffer.slice(end + 2)
      let event = 'message'
      const data = []
      for (const line of raw.split('\n')) {
        if (line.startsWith('event:')) event = line.slice(6).trim()
        else if (line.startsWith('data:')) data.push(line.slice(5).trimStart())
        // 以冒号开头的是注释（比如保活用的 ": keep-alive"），忽略
      }
      if (data.length) yield { event, data: data.join('\n') }
    }
  }
}

这个函数在两个地方都会用到：服务器用它解析 DeepSeek 的流，浏览器用它解析我们服务器的流。所以它不擅自 JSON.parse， 而是把 data 原样交给调用者。按照 SSE 规范，一个事件可以有多行 data:，要用换行拼起来；以冒号开头的行是注释，服务器有时用它保持连接不断。

✓ 为什么用 TextDecoderStream

一个汉字在 UTF-8 里占 3 个字节，网络块可能恰好在一个汉字中间断开。如果每块单独用 new TextDecoder().decode(chunk) 解码，就会出现乱码“�”。 TextDecoderStream 会自动保留不完整的字节，等下一块到达再拼起来解码。

useChat：聊天的状态与逻辑

把所有聊天逻辑封装进一个组合式函数。先看它的状态变化：

import { ref, computed } from 'vue'
import { readSSE } from '@/lib/readSSE'

export function useChat(endpoint = '/api/chat') {
  const messages = ref([]) // { id, role, content, reasoning?, stopped?, truncated?, error? }
  const status = ref('idle') // 'idle' | 'streaming' | 'error'
  const isStreaming = computed(() => status.value === 'streaming')
  let controller = null

  // 发给服务器的历史：只保留 role 和 content（思考过程不回传）。
  // 出错或还没输出正文就被停止的回复，连同它前面的提问一起跳过，保证 user / assistant 严格交替
  const history = () => {
    const result = []
    for (const { role, content, error } of messages.value) {
      if (role === 'assistant' && (!content || error)) { result.pop(); continue }
      result.push({ role, content })
    }
    return result
  }

  async function run() {
    const body = JSON.stringify({ messages: history() })
    messages.value.push({ id: crypto.randomUUID(), role: 'assistant', content: '', reasoning: '' })
    // 注意：从响应式数组里取出来的是代理，修改它才会触发更新（第 9 章）
    const reply = messages.value.at(-1)

    controller = new AbortController()
    status.value = 'streaming'
    try {
      const res = await fetch(endpoint, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body,
        signal: controller.signal,
      })
      if (!res.ok) throw new Error((await res.json().catch(() => null))?.message || `HTTP ${res.status}`)

      for await (const { event, data } of readSSE(res.body)) {
        const payload = JSON.parse(data)
        if (event === 'reasoning') reply.reasoning += payload.text
        else if (event === 'delta') reply.content += payload.text
        else if (event === 'error') throw new Error(payload.message)
        else if (event === 'done' && payload.finishReason === 'length') reply.truncated = true
      }
      status.value = 'idle'
    } catch (err) {
      if (err.name === 'AbortError') { // 用户主动停止，不算错误
        reply.stopped = true
        status.value = 'idle'
      } else {
        reply.error = err.message
        status.value = 'error'
      }
    } finally {
      controller = null
    }
  }

  function send(text) {
    if (!text.trim() || isStreaming.value) return
    messages.value.push({ id: crypto.randomUUID(), role: 'user', content: text.trim() })
    return run()
  }

  function stop() {
    controller?.abort() // fetch 中断 → 连接关闭 → 服务器 onAbort → 中止对 DeepSeek 的请求
  }

  function retry() {
    if (messages.value.at(-1)?.error) messages.value.pop() // 去掉出错的那条回复
    return run()
  }

  return { messages, status, isStreaming, send, stop, retry }
}

几个值得注意的地方：

  • 停止的链路：stop() 一行代码就串起了整条链路。controller.abort() 让 fetch 的读取抛出 AbortError， 同时浏览器关闭连接；Hono 的 stream.onAbort 随之触发，中止服务器对 DeepSeek 的请求。
  • 思考过程：reasoning 事件追加到 reply.reasoning，只用于展示，history() 不会把它发回服务器。
  • 历史必须交替：如果模型还在思考时用户就点了停止，这条回复的正文是空的。只把它过滤掉的话，历史里会出现两条连续的 user 消息， 被服务器的校验拒绝。所以 history() 遇到没有有效正文的回复时，连同它前面的提问一起跳过。

安全地渲染 Markdown

模型的回答是 Markdown 文本，需要转成 HTML 再用 v-html 显示。这里有两个问题：安全和性能。

⚠ v-html 是 XSS 的入口

模型的输出会受用户输入影响，甚至可能被网页内容、文档里藏着的指令（提示词注入）诱导，输出 <img src=x onerror="偷走 cookie"> 这样的代码。 所以要两道防线：markdown-it 默认 html: false，原始 HTML 会被转义；渲染结果再经过 DOMPurify 清理一遍。 

import MarkdownIt from 'markdown-it'
import DOMPurify from 'dompurify'

// 模块级单例，所有消息共用一个实例
const md = new MarkdownIt({ html: false, linkify: true, breaks: true })

export function renderMarkdown(text) {
  return DOMPurify.sanitize(md.render(text))
}

<script setup>
import { computed, toRef } from 'vue'
import { refThrottled } from '@vueuse/core'
import { renderMarkdown } from '@/lib/markdown'

const props = defineProps({ message: Object, streaming: Boolean })

// 内容每 80ms 最多重新解析一次；最后一次变化保证会被渲染
const content = refThrottled(toRef(() => props.message.content), 80)
const html = computed(() => renderMarkdown(content.value))
</script>

<template>
  <div v-if="message.role === 'user'" class="msg user">{{ message.content }}</div>
  <div v-else class="msg assistant">
    <!-- 思考过程：还没开始回答时展开，开始回答后自动收起 -->
    <details v-if="message.reasoning" class="reasoning" :open="streaming && !message.content">
      <summary>{{ streaming && !message.content ? '思考中…' : '思考过程' }}</summary>
      <p>{{ message.reasoning }}</p>
    </details>
    <div v-html="html" />
    <span v-if="streaming" class="cursor" aria-hidden="true" />
    <small v-if="message.stopped" class="note">已停止生成</small>
    <small v-if="message.truncated" class="note">回答过长，已被截断</small>
    <small v-if="message.error" class="note error">{{ message.error }}</small>
  </div>
</template>

思考过程放在原生的 <details> 里：模型还在思考、正文没出来时展开，让用户知道“它在干活”；正文开始输出后自动收起，想看可以再点开。 思考过程是纯文本，用 {{ }} 插值即可。

✓ 代码高亮放到最后

代码高亮（比如 Shiki）比较耗时，而且流式过程中代码块经常是不完整的。可以只在这条消息生成结束后再做高亮， 并用动态 import('shiki') 按需加载，不影响首屏体积。用户消息和思考过程用 {{ }} 插值显示，Vue 会自动转义，不需要 v-html。

自动滚动：跟随，但不强迫

新文字到达时应该自动滚到底部，但如果用户正往上翻看之前的内容，就不能把他拽回来。规则是：只有当用户本来就在底部附近时才自动滚动： 

import { useTemplateRef, watch, nextTick } from 'vue'
import { useScroll } from '@vueuse/core'

const list = useTemplateRef('list')
const { arrivedState } = useScroll(list, { offset: { bottom: 60 } })

watch(() => messages.value.at(-1)?.content, async () => {
  if (!arrivedState.bottom) return          // 用户在往上翻，不打扰
  await nextTick()                          // 等新内容渲染出来（第 2 章）
  list.value.scrollTop = list.value.scrollHeight
})

回车发送与中文输入法

这是中文用户最容易遇到的 bug：用拼音输入法打字时，按回车是为了确认候选词，如果此时消息被发出去了，用户会非常恼火。 浏览器在输入法组字期间触发的键盘事件，isComposing 为 true，判断一下即可： 

<textarea v-model="input" @keydown.enter.exact="onEnter" />

<script setup>
function onEnter(e) {
  if (e.isComposing || e.keyCode === 229) return   // 输入法正在组字，交给输入法
  e.preventDefault()                               // 阻止换行
  submit()
}
// Shift+Enter 不匹配 .exact，会保留默认的换行行为
</script>

其他值得做的细节

细节做法
读屏软件消息列表用 role="log"；生成中设置 aria-busy="true"，避免逐字朗读，结束后再朗读完整回答
保存对话把 messages 放进 Pinia，用第 6 章的持久化插件存到 localStorage，或者保存到服务器
复制和重新生成每条回复加“复制”按钮（navigator.clipboard.writeText）和“重新生成”（删掉最后一条回复再 run()）
长对话对话越长，每次请求发送的内容越多、费用越高。限制保留的轮数，或在服务器端对早期内容做摘要。done 事件里的 usage 可以用来统计 token 用量
防止重复提交生成期间禁用发送；服务器端按用户限流
🔎 现成的封装

理解了原理之后，也可以使用社区的封装来省去样板代码，例如 Vercel AI SDK 提供的 Vue 绑定（@ai-sdk/vue），它把消息状态、流式解析、停止和重试都包好了。 用 Nuxt 的话，后端接口可以直接写在 server/api/chat.post.js 里（第 7 章）；本章的 Hono 代码也几乎不用改就能部署到 Cloudflare Workers 这类边缘平台。无论用什么封装，本章的几个要点都不变： 密钥在服务端、流要能中止、Markdown 要清理、输入法要处理。

主题要点
架构浏览器 → 自己的服务器（密钥、校验、限流）→ DeepSeek API；密钥放 .env 并加入 .gitignore，绝不进前端
后端Hono + zValidator 校验；fetch DeepSeek 并用 readSSE 解析；streamSSE 翻译成 reasoning / delta / done；onAbort 时中止上游
读取流fetch + TextDecoderStream + 按空行切分的缓冲区，包装成异步迭代器，前后端共用
useChatmessages + status 状态机；修改响应式代理上的回复；AbortController 停止；历史保持严格交替
Markdown节流 → markdown-it（html: false）→ DOMPurify → v-html
体验在底部才自动滚动；isComposing 处理输入法；role="log" + aria-busy

动手练习

  1. 运行仓库里的 examples/ch13-ai-chat（按 README 配好 .env），打开开发者工具的 Network 面板，观察 /api/chat 响应是怎么一段一段到达的。
  2. 在 stream.onAbort 里打印日志，点“停止”后确认服务器确实中止了对 DeepSeek 的请求。
  3. 在页面上加一个开关，让用户在 deepseek-flash 和 deepseek-v4-pro 之间切换（服务器端要用 Zod 校验只允许这两个值）；再用 done 事件里的 usage 显示本次用掉的 token 数。
  4. 给每条回复加“复制”和“重新生成”按钮。
  5. 把对话保存到 Pinia 并持久化，刷新页面后对话还在；再做一个侧边栏，支持多个会话切换。
  6. 生成结束后用 Shiki 给代码块加上高亮，并在代码块右上角加一个“复制代码”按钮。
  7. 把第 5 章客服中心的“常见问题”页改成一个 AI 助手：在系统提示词里放入 FAQ 内容，让它只根据这些内容回答。
