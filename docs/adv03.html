第 11 章 · 进阶专题

大型项目架构

书里的六个项目都不大，一个 components/ 文件夹就能装下。可是当项目有了几十个页面、上百个组件、好几个人同时开发，甚至几个应用要共享代码时， “文件放哪儿”“谁能引用谁”就成了真正的问题。本章介绍让项目在长大后依然好维护的组织方式：按功能分模块、清晰的依赖方向、 统一的数据层，以及用 pnpm workspace 管理多个应用和一个共享组件库。

本章目标

  • 理解“按类型组织”和“按功能组织”的区别，学会划分功能模块
  • 给模块定下依赖规则，并用 ESLint 自动检查
  • 让每个功能模块自己注册路由，用 import.meta.glob 自动收集
  • 区分“服务端状态”和“客户端状态”，用 TanStack Query 管理请求数据
  • 用 pnpm workspace + Turborepo 搭建 monorepo
  • 用 Vite 库模式构建一个组件库，生成类型声明，并用 Changesets 发布版本

项目长大以后

先回忆第 5 章客服中心的目录。它是按文件类型组织的：所有组件放一起，所有组合式函数放一起。项目小的时候很直观，但功能一多：

想下线一个功能，却要在五六个文件夹里分别找它的文件，还怕漏掉。

按功能组织

解决办法是把同一个功能相关的所有文件放在一起，形成一个功能模块（feature module）：

src/ ├── app/ # 应用外壳：只做“组装” │ ├── main.js │ ├── router.js # 收集各功能的路由 │ └── layouts/ ├── features/ │ ├── tickets/ │ │ ├── components/ │ │ ├── composables/ │ │ ├── api.js # 这个功能的接口 │ │ ├── store.js # 这个功能的 Pinia store（如果需要） │ │ ├── routes.js # 这个功能的路由 │ │ └── index.js # 公开出口：别的模块只能从这里引用 │ ├── auth/ │ └── blog/ └── shared/ # 与业务无关、谁都能用 ├── ui/ # 基础组件（第 10 章） ├── composables/ # useDebouncedRef、useMediaQuery… ├── api/http.js # 统一的请求客户端 └── utils/

依赖方向：只能“向下”引用

光分文件夹还不够，关键是定下谁可以引用谁。规则很简单：上层可以引用下层，下层不能引用上层，同层的功能模块之间尽量不直接引用。

功能模块的 index.js 只导出别人需要的东西，内部文件可以随便重构：

export { useUserStore } from './store'
export { default as UserMenu } from './components/UserMenu.vue'
export { routes } from './routes'
// LoginForm.vue、api.js 等内部细节不导出

规则写在文档里迟早会被打破，最好交给 ESLint 自动检查。用内置的 no-restricted-imports 就能做到大部分：

import pluginVue from 'eslint-plugin-vue'

export default [
  ...pluginVue.configs['flat/recommended'],
  {
    // 禁止深入别的功能模块内部，只能用它的 index.js
    files: ['src/**/*.{js,ts,vue}'],
    rules: {
      'no-restricted-imports': ['error', {
        patterns: [{ group: ['@/features/*/*'], message: '请从功能模块的 index.js 导入' }],
      }],
    },
  },
  {
    // shared 不能依赖任何业务代码
    files: ['src/shared/**'],
    rules: {
      'no-restricted-imports': ['error', {
        patterns: [{ group: ['@/features/*', '@/app/*'], message: 'shared 不能依赖业务代码' }],
      }],
    },
  },
]
🔎 想要更完整的规范？

社区有一套叫 Feature-Sliced Design 的方法论，把层次进一步细分为 app / pages / widgets / features / entities / shared， 并配有 eslint-plugin-boundaries 等工具强制执行。大团队可以参考，小团队用上面三层就够了，重要的是规则一致。

每个功能自己注册路由

路由表是最容易变成“大杂烩”的文件。让每个功能模块导出自己的路由（全部懒加载），app/router.js 用 Vite 的 import.meta.glob 自动收集， 新增一个功能就不用再改中心文件了： 

export const routes = [
  {
    path: '/tickets',
    component: () => import('./components/TicketsLayout.vue'),
    meta: { private: true },
    children: [
      { path: '', name: 'tickets', component: () => import('./components/Tickets.vue') },
      { path: ':id', name: 'ticket', component: () => import('./components/Ticket.vue'), props: true },
    ],
  },
]

import { createRouter, createWebHistory } from 'vue-router'

// eager: true —— 立即导入这些 routes.js（它们很小，组件本身仍是懒加载的）
const modules = import.meta.glob('../features/*/routes.js', { eager: true })
const featureRoutes = Object.values(modules).flatMap((m) => m.routes)

export const router = createRouter({
  history: createWebHistory(),
  routes: [
    { path: '/', name: 'home', component: () => import('./pages/Home.vue') },
    ...featureRoutes,
    { path: '/:pathMatch(.*)*', component: () => import('./pages/NotFound.vue') },
  ],
})

数据层：服务端状态和客户端状态

第 5、6 章里，我们把从服务器拿来的数据（工单列表、帖子）放进了 Pinia 或组件的 ref，自己处理加载中、错误和刷新。 项目大了以后会发现，这类数据有很多共性问题：缓存、去重（两个组件同时请求同一份数据）、过期后重新获取、窗口重新聚焦时刷新、分页…… 它们和“侧边栏是否展开”这种纯前端状态是两种完全不同的东西：

先写一个统一的请求客户端，所有功能的接口都通过它发请求，这样认证头、错误处理、基础地址只需要写一次：

export class HttpError extends Error {
  constructor(status, body) { super(body?.message || `HTTP ${status}`); this.status = status; this.body = body }
}

export async function http(path, { body, ...options } = {}) {
  const res = await fetch(import.meta.env.VITE_API_BASE + path, {
    credentials: 'include',
    headers: { 'Content-Type': 'application/json', ...options.headers },
    body: body ? JSON.stringify(body) : undefined,
    ...options,
  })
  const data = res.status === 204 ? null : await res.json().catch(() => null)
  if (!res.ok) throw new HttpError(res.status, data)
  return data
}

import { http } from '@/shared/api/http'

export const ticketsApi = {
  list: (page) => http(`/tickets?page=${page}`),
  get: (id) => http(`/tickets/${id}`),
  create: (data) => http('/tickets', { method: 'POST', body: data }),
}

然后用 TanStack Query 把接口包成组合式函数。注意查询键里可以直接放 ref，页码变了会自动重新请求：

import { useQuery, useMutation, useQueryClient } from '@tanstack/vue-query'
import { ticketsApi } from '../api'

export function useTickets(page) {
  return useQuery({
    queryKey: ['tickets', page],             // page 是 ref，变化时自动重新获取
    queryFn: () => ticketsApi.list(page.value),
    staleTime: 30_000,                       // 30 秒内认为数据是新鲜的，不重复请求
    placeholderData: (prev) => prev,         // 翻页时先保留上一页，避免闪烁
  })
}

export function useCreateTicket() {
  const queryClient = useQueryClient()
  return useMutation({
    mutationFn: ticketsApi.create,
    // 成功后让所有工单列表缓存失效，自动重新获取
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['tickets'] }),
  })
}

<script setup>
import { ref } from 'vue'
import { useTickets } from '../composables/useTickets'

const page = ref(1)
const { data, isPending, isError, error, isFetching } = useTickets(page)
</script>

<template>
  <p v-if="isPending">加载中…</p>
  <p v-else-if="isError">出错了：{{ error.message }}</p>
  <template v-else>
    <TicketCard v-for="t in data.items" :key="t.id" :ticket="t" />
    <button :disabled="page === 1" @click="page--">上一页</button>
    <button @click="page++">下一页</button>
    <small v-if="isFetching">更新中…</small>
  </template>
</template>

只需要在 main.js 里 app.use(VueQueryPlugin)。对比第 5 章手写的 useFetch，缓存、去重、后台刷新、重试都免费得到了。

✓ Pinia Colada

Pinia 团队也推出了专门处理异步数据的 Pinia Colada，API 和思路与 TanStack Query 很接近，基于 Pinia 实现、与 Pinia DevTools 集成。 已经重度使用 Pinia 的项目可以考虑它。用 Nuxt 的话，内置的 useFetch / useAsyncData 已经覆盖了大部分需求。

Monorepo：多个应用共享代码

当公司有了“用户端网站”和“管理后台”两个应用，它们想共用同一套按钮、同一套请求工具、同一份 ESLint 配置时， 把它们放在一个仓库里统一管理会方便得多。这就是 monorepo。用 pnpm workspace 就能轻松实现：

my-company/ ├── pnpm-workspace.yaml ├── package.json # 根：只放 turbo、changesets 等工具 ├── turbo.json ├── apps/ │ ├── web/ # Vite + Vue 应用 │ └── admin/ └── packages/ ├── ui/ # @acme/ui ├── utils/ # @acme/utils └── config/ # 共享的 eslint、tsconfig 
packages:
  - 'apps/*'
  - 'packages/*'

{
  "name": "web",
  "private": true,
  "dependencies": {
    "vue": "^3.5.0",
    "@acme/ui": "workspace:*",
    "@acme/utils": "workspace:*"
  }
}

workspace:* 告诉 pnpm：“用仓库里的这个包”，pnpm 会创建一个软链接，所以修改 packages/ui 的源码，应用里马上生效。常用命令：

pnpm install                         # 在根目录安装所有包的依赖
pnpm --filter web dev                # 只在 web 应用里运行 dev
pnpm --filter @acme/ui add dayjs     # 给某个包加依赖
pnpm -r build                        # 在所有包里运行 build（按依赖顺序）

Turborepo：只构建变化了的部分

包多了以后，每次都全部构建很慢。Turborepo 知道包之间的依赖关系，会按正确顺序并行执行任务，并缓存结果： 某个包和它的依赖没有变化，就直接复用上次的输出。 

{
  "$schema": "https://turborepo.com/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "dev": { "cache": false, "persistent": true },
    "test": { "dependsOn": ["^build"] },
    "lint": {}
  }
}

"^build" 的意思是“先构建我依赖的包”。运行 pnpm turbo build，第二次没有改动时几乎瞬间完成。

构建并发布组件库

在 monorepo 内部，应用可以直接引用 packages/ui 的源码。但如果要把组件库发布到 npm 给其他仓库使用，就需要把它构建成标准的 JS 包，并附上类型声明。 Vite 的库模式专门做这件事： 

export { default as AcmeButton } from './Button.vue'
export { default as AcmeDialog } from './Dialog.vue'
export * from './composables/useMenu'

import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import dts from 'vite-plugin-dts'
import { fileURLToPath } from 'node:url'

export default defineConfig({
  plugins: [vue(), dts({ rollupTypes: true })],    // 生成合并后的 index.d.ts
  build: {
    lib: {
      entry: fileURLToPath(new URL('./src/index.ts', import.meta.url)),
      formats: ['es'],
      fileName: 'index',
      cssFileName: 'style',
    },
    rollupOptions: {
      external: ['vue'],     // 不把 vue 打包进来，使用者自己的 vue 会被复用
    },
  },
})

{
  "name": "@acme/ui",
  "version": "0.1.0",
  "type": "module",
  "files": ["dist"],
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
    "./style.css": "./dist/style.css"
  },
  "sideEffects": ["**/*.css"],
  "peerDependencies": { "vue": "^3.5.0" },
  "scripts": { "build": "vite build" }
}
⚠ vue 必须是 peerDependency

如果把 vue 放进 dependencies 并打包进组件库，使用者的应用里就会出现两份 Vue。 两份 Vue 各有一套响应式系统和 provide/inject，会出现 “inject() can only be used inside setup” 之类莫名其妙的错误。 所以要设为 external + peerDependencies，让使用者提供 Vue。

用 Changesets 管理版本

每次改动组件库时，记录一个“变更集”说明改了什么、属于哪种版本升级（遵循语义化版本：修复 patch、新功能 minor、不兼容 major）：

  1. pnpm changeset：交互式选择改动的包和升级类型，写一句说明，生成 .changeset/xxx.md，随代码一起提交；
  2. pnpm changeset version：汇总所有变更集，更新各包的版本号和 CHANGELOG.md；
  3. pnpm changeset publish：把版本号变了的包发布到 npm。这一步通常交给第 7 章的 CI 流水线（官方有现成的 GitHub Action）。

代码规范：让多人协作不打架

工具作用在 monorepo 里
ESLint（flat config）+ eslint-plugin-vue发现错误写法、强制模块边界放在 packages/config，各包 import 后再扩展
Prettier统一格式，不再争论分号和缩进根目录一份配置
vue-tsc类型检查（第 4 章）每个包 "typecheck": "vue-tsc --noEmit"，交给 Turborepo 并行跑
lint-staged + simple-git-hooks提交前只检查改动的文件根目录配置
Vitest workspace一条命令跑所有包的测试根目录 vitest.config 的 projects
★ 不要过早设计

本章的东西都是为“大”准备的。一个人做的小项目，用第 4 章的结构就很好；有了三五个功能模块再改成按功能组织；真的出现第二个应用时再上 monorepo。 结构应该跟着痛点走，而不是跟着想象走。

小结

主题要点
目录按功能组织：app/、features/*、shared/
依赖规则只向下引用；跨功能只经 index.js；用 no-restricted-imports 检查
路由每个功能导出 routes，import.meta.glob 自动收集，组件懒加载
数据层统一 http 客户端；服务端状态用 TanStack Query，客户端状态用 Pinia
Monorepopnpm workspace + workspace:*；Turborepo 按依赖顺序执行并缓存
组件库Vite 库模式、vue 设为 external 和 peerDependency、exports 字段、vite-plugin-dts、Changesets
