像用户一样测试

Testing Library 的核心理念是：测试越像用户使用软件的方式，就越能给你信心。所以它不鼓励你检查组件内部的状态或实现细节， 而是按用户能感知的方式找元素（“一个叫‘添加’的按钮”），模拟用户的操作（点击、输入），再断言用户能看到的结果：

第一个组件测试

export default function BaseButton({ icon, badge = null, disabled = false, onClick, children }) {
  return (
    <button className="base-button" disabled={disabled} onClick={onClick}>
      {icon && <i className="material-icons icon">{icon}</i>}
      <span className="content">{children}</span>
      {badge !== null && <div className="button-badge"><span>{badge}</span></div>}
    </button>
  )
}

测试纯逻辑：最简单也最划算

reducer、Zustand store、工具函数都是普通的 JS，测试它们不需要渲染任何东西。比如购物车 store：

import { beforeEach, test, expect } from 'vitest'
import { useCartStore } from './cart.js'

beforeEach(() => {
  useCartStore.setState({ items: [] })      // 每个测试前重置状态
})

test('重复添加同一件商品时数量累加', () => {
  const { addItem } = useCartStore.getState()
  addItem({ id: 1, price: 2.99 })
  addItem({ id: 1, price: 2.99 })
  expect(useCartStore.getState().items).toEqual([{ id: 1, price: 2.99, count: 2 }])
})
✓ 测试请求：模拟网络

组件里有请求时，不要在测试里真的访问服务器。可以用 vi.spyOn(globalThis, 'fetch') 返回假数据， 或者用 MSW 在网络层拦截请求 —— 后者让测试代码和真实代码完全一致，也可以复用在开发环境里做 mock 服务器。

🔍 快照测试还要不要用？（点击展开）

Vitest 支持 expect(container).toMatchSnapshot()，把渲染出的 HTML 存下来，以后比较。 它写起来容易，但缺点也明显：任何无关紧要的改动都会让快照失败，大家习惯性地 vitest -u 更新，快照就失去了意义。 React 社区更推荐写明确的断言（“按钮被禁用了”“显示了 3”）。快照适合偶尔用在输出稳定、内容很多的场景。

端到端测试：Playwright 与 MSW补充

单元测试验证的是“零件”：一个组件、一个 store。但零件都没问题，组装起来也可能出错 —— 路由配错了、两个组件之间的事件没接上、真实浏览器里样式把按钮挡住了。 端到端（E2E）测试启动真实的浏览器，像用户一样打开页面、点击、输入，验证一整条流程。

Playwright

在项目根目录运行 npm init playwright@latest，再在 package.json 里加上 "test:e2e": "playwright test"。 它会下载 Chromium、Firefox、WebKit 三种浏览器内核，并生成 playwright.config.js 和 e2e/ 目录。 

import { test, expect } from '@playwright/test'

test('把商品加入购物车并去结算', async ({ page }) => {
  await page.goto('/')

  // 找到“蓝色袜子”所在的卡片，点击它的“加入购物车”按钮
  const card = page.locator('.store-item', { hasText: 'Blue Socks' })
  await card.getByRole('button', { name: /加入购物车|Add/ }).click()

  // 购物车角标变成 1
  await expect(page.locator('.cart .button-badge')).toHaveText('1')

  // 去结算页，能看到这件商品
  await page.getByRole('link', { name: /结算|Checkout/ }).click()
  await expect(page).toHaveURL(/checkout/)
  await expect(page.getByText('Blue Socks')).toBeVisible()
})

✓ 写出稳定的 E2E 测试
  • 用 getByRole、getByText、getByLabel 按“用户看到的东西”查找元素，而不是脆弱的 CSS 层级选择器。
  • expect(...).toHaveText() 等断言会自动等待直到条件满足或超时，不要手写 waitForTimeout(1000)。
  • 每个测试互相独立：不依赖上一个测试留下的数据。

MSW：在网络层模拟接口

单元测试和 E2E 测试都会遇到同一个问题：组件要请求后端，测试时后端可能没启动、数据会变、错误情况很难复现。 MSW（Mock Service Worker）在网络层拦截请求并返回你定义的假数据 —— 应用代码完全不用改，它以为自己在和真实服务器说话： 

npm install -D msw

import { http, HttpResponse } from 'msw'

export const handlers = [
  http.get('/api/items', () =>
    HttpResponse.json([
      { id: 1, title: 'Blue Socks', price: 2.99 },
      { id: 2, title: 'Green Socks', price: 3.99 },
    ])
  ),
]

import '@testing-library/jest-dom/vitest'
import { setupServer } from 'msw/node'
import { beforeAll, afterEach, afterAll } from 'vitest'
import { handlers } from '../mocks/handlers'

const server = setupServer(...handlers)
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }))   // 没有模拟的请求直接报错
afterEach(() => server.resetHandlers())
afterAll(() => server.close())

export { server }

import { render, screen } from '@testing-library/react'
import { http, HttpResponse } from 'msw'
import { server } from '../test/setup'

test('加载失败时显示错误信息', async () => {
  // 只在这个测试里，让接口返回 500
  server.use(http.get('/api/items', () => new HttpResponse(null, { status: 500 })))
  render(<PageHome />)
  // findBy* 会等待元素出现（默认最多 1 秒），适合异步加载的内容
  expect(await screen.findByText(/加载失败/)).toBeInTheDocument()
})

按需加载：动态 import

用户一次只用一种语言，没必要把五种语言都打进首屏代码。动态 import() 会让构建工具把被导入的模块拆成独立的文件（chunk），需要时才下载： 

import i18n from 'i18next'
import { initReactI18next } from 'react-i18next'
import LanguageDetector from 'i18next-browser-languagedetector'
import resourcesToBackend from 'i18next-resources-to-backend'

export const langs = ['zh', 'en', 'fr', 'es', 'de']

i18n
  .use(LanguageDetector)        // 根据浏览器语言（navigator.languages）自动选择
  .use(resourcesToBackend(      // 需要哪种语言，就动态 import 哪个文件
    (lng) => import(`./locales/${lng}.json`)
  ))
  .use(initReactI18next)
  .init({
    supportedLngs: langs,
    fallbackLng: 'en',          // 缺翻译时退回英文
    load: 'languageOnly',       // 'zh-CN' 只取 'zh'
  })

export default i18n

import { Suspense } from 'react'
import './i18n.js'

createRoot(document.getElementById('root')).render(
  <Suspense fallback={<div className="loading" />}>   {/* 语言包下载完之前显示 */}
    <App />
  </Suspense>
)

import { useTranslation } from 'react-i18next'

服务端渲染与 Next.js

为什么需要 SSR

到目前为止都是客户端渲染（CSR）：服务器返回一个几乎空白的 HTML，浏览器下载并执行 JS 后内容才出现。 服务端渲染（SSR）是在服务器上先把 React 应用渲染成 HTML 再发给浏览器：

水合（hydration）：浏览器拿到的 HTML 是“死”的，客户端 React 启动后不会重新创建 DOM，而是认领服务器渲染好的 DOM，给它挂上事件处理和状态， 底层用的是 hydrateRoot 而不是 createRoot。

ⓘ 不是所有应用都需要 SSR

后台管理系统、需要登录才能用的工具，用 Vite 做纯客户端应用就好。电商、博客、内容站这类需要被搜索引擎收录的场景才值得上 SSR。 内容基本不变的话，还可以静态生成（SSG）：构建时就把页面渲染成 HTML 文件。

服务端组件：React 19 最重要的新概念

传统 SSR 只是“在服务器上先跑一遍”，所有组件的代码仍然要发到浏览器去水合。React 19 正式加入了服务端组件（Server Components）： 有些组件只在服务器上运行，它们的代码永远不会发给浏览器。

★ 一句话区分

需要交互（状态、事件、浏览器 API）的组件，在文件顶部写 'use client'，它就是客户端组件； 其他组件默认是服务端组件，可以是 async 函数，直接 await 数据。服务端组件可以渲染客户端组件，并把可序列化的数据作为 props 传给它。 原书的 asyncData、手动注入 __INITIAL_STATE__ 这一整套，在这里变成了“组件里直接 await”。

服务端组件需要框架支持。Next.js 的 App Router 是目前最成熟的实现，也是 React 官方文档首推的框架：

import AddToCartButton from './AddToCartButton.jsx'

async function getItem(id) {
  const res = await fetch(`http://localhost:3000/items/${id}`)   // 在服务器上请求，浏览器看不到
  if (!res.ok) return null
  return res.json()
}

// SEO：根据数据生成页面标题和描述

⚠ 写在服务器和浏览器都会运行的代码时
  • 客户端组件也会先在服务器上渲染一次。window、localStorage 只能在 useEffect 或事件处理函数里访问。
  • 服务器和浏览器渲染的结果必须一致，否则会出现“水合不匹配”警告（比如直接在 JSX 里显示 Date.now() 或随机数）。
  • 服务器是多个用户共享的：不要把某个用户的数据放进模块级变量。Zustand 这类模块级 store 在 SSR 中要按请求创建（Zustand 文档有专门的 Next.js 指南）。
✓ 其他选择

React Router 框架模式（原 Remix）同样基于 Vite，提供 SSR、文件路由和 loader/action 数据模型，从第 5 章的数据模式迁移过去很自然。 Next.js 里做国际化通常用 next-intl。

Next.js 深入：Server Actions、缓存与混合渲染补充

Next.js 不只是“能做 SSR 的 React”，它是一个全栈框架：同一个项目里可以写后端接口，表单可以直接调用服务器上的函数。

Route Handlers：写 HTTP 接口

// 文件路径就是路由：GET /api/items
import items from '@/data/items.json'

export async function GET() {
  return Response.json(items)          // 标准的 Web Response
}

export async function GET(request, { params }) {
  const { id } = await params
  const item = items.find((i) => i.id === Number(id))
  if (!item) return Response.json({ message: '商品不存在' }, { status: 404 })
  return Response.json(item)
}

不过在 App Router 里，服务端组件可以直接读数据库或文件，并不需要先绕一圈 HTTP 接口。Route Handler 主要留给“外部要调用的接口”：移动端 App、Webhook、第三方回调。

Server Actions：表单直接调用服务器函数

第 5 章用过 React 19 的 <form action={fn}>。在 Next.js 里，这个 fn 可以是一个只在服务器上运行的函数 —— 用 'use server' 标记后，框架会自动为它生成一个接口，浏览器提交表单时调用它，你不用写 fetch，也不用写路由： 

'use server'

import { revalidatePath } from 'next/cache'
import { db } from '@/lib/db'
import { getCurrentUser } from '@/lib/auth'

export async function addReview(itemId, prevState, formData) {
  const user = await getCurrentUser()                 // 每个 Server Action 都要自己检查权限！
  if (!user) return { error: '请先登录' }

  const text = String(formData.get('text') ?? '').trim()
  if (text.length < 5) return { error: '评价至少 5 个字' }

  await db.review.create({ data: { itemId, userId: user.id, text } })
  revalidatePath(`/item/${itemId}`)                   // 让这个页面的缓存失效，重新渲染出新评价
  return { error: null }
}

'use client'

import { useActionState } from 'react'
import { addReview } from './actions.js'

export default function ReviewForm({ itemId }) {
  // bind 预先填入第一个参数；useActionState 和第 5 章的用法完全一样
  const [state, action, isPending] = useActionState(addReview.bind(null, itemId), { error: null })
  return (
    <form action={action}>
      <textarea name="text" required />
      {state.error && <p className="error">{state.error}</p>}
      <button disabled={isPending}>{isPending ? '提交中…' : '发表评价'}</button>
    </form>
  )
}
⚠ Server Action 就是一个公开接口

虽然写起来像普通函数，但框架会把它暴露为一个 HTTP 端点，攻击者可以绕过你的表单直接调用它、传任意参数。 所以每个 Server Action 都要像写后端接口一样：检查登录和权限、校验输入（第 5 章的 Zod 模式可以直接复用），不要信任 bind 进来的参数。

混合渲染：每个路由选最合适的方式

同一个网站里，不同页面的需求不同：首页几乎不变，适合构建时生成静态 HTML；商品页要 SEO、价格偶尔变，适合定期重新生成； 结算页完全依赖当前用户，每次请求都要现做。Next.js 根据页面用到了什么自动判断，也可以显式声明：

  • 预先生成动态路由：在 app/item/[id]/page.jsx 里导出 generateStaticParams()，返回所有商品 id，构建时就为每个商品生成 HTML。
  • 流式渲染：页面里慢的部分（比如“猜你喜欢”）包进 <Suspense>，页面其余部分先发送，慢的部分准备好后再流过来，不会拖慢整页。
  • 按需失效：数据变化时用 revalidatePath() 或 revalidateTag() 让缓存失效（上面的 Server Action 就是这样做的）。
ⓘ 缓存模型还在演进

Next.js 15 起，fetch 默认不再缓存；Next.js 16 推出了 Cache Components（在 next.config.js 里开启 cacheComponents）， 用 'use cache' 指令显式标记可以缓存的函数或组件，并把静态外壳和动态内容组合在同一个页面里（部分预渲染）。 这一块变化较快，动手前请以 Next.js 官方文档的当前版本为准。

✓ 部署

next build 之后用 next start 运行；部署到 Vercel 最省事。自己用 Docker 部署时，在配置里设置 output: 'standalone'， 构建产物会包含一个最小化的 Node 服务，镜像可以小很多。全部页面都是静态的话，output: 'export' 能输出纯静态站点。

🔍 不用框架手写 SSR（点击展开）

理解原理用。服务器端用 react-dom/server 把组件渲染成 HTML 流，浏览器端用 hydrateRoot 水合：

// server.js（Node）
import { renderToPipeableStream } from 'react-dom/server'

app.get('*', (req, res) => {
  const { pipe } = renderToPipeableStream(<App url={req.url} />, {
    bootstrapScripts: ['/assets/client.js'],
    onShellReady() {
      res.setHeader('Content-Type', 'text/html')
      pipe(res)                     // 流式发送：Suspense 边界外的内容先到
    },
  })
})

// client.jsx（浏览器）
import { hydrateRoot } from 'react-dom/client'
hydrateRoot(document, <App url={location.pathname} />)

真实项目还要处理数据预取、状态序列化、路由、代码分割、开发时热更新……这正是框架存在的意义。Vite 官方文档有一份 SSR 指南，可以作为起点。

持续集成与部署补充

到这里，项目已经有了 lint、类型检查、单元测试、E2E 测试和构建五道工序。靠人记得每次都跑一遍是不现实的。 持续集成（CI）让这些检查在每次推送代码、每次发起 Pull Request 时自动运行；全部通过后再自动部署（CD）。

以 GitHub Actions 为例，在仓库里新建一个工作流文件，就能把 Vite 应用自动部署到 GitHub Pages：

name: CI

on:
  push:
    branches: [master]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: lts/*
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --run                   # --run：执行一次就退出，不进入 watch 模式
      - run: npx playwright install --with-deps chromium
      - run: npm run test:e2e
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist

  deploy:
    needs: test                                   # 测试通过才部署
    if: github.ref == 'refs/heads/master'         # 只有 master 分支才部署
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4
ⓘ 别忘了这两个设置

在仓库 Settings → Pages 里把 Source 改为 “GitHub Actions”；部署在子路径（用户名.github.io/仓库名/）时，在 vite.config.js 里设置 base: '/仓库名/'。 Netlify、Vercel、Cloudflare Pages 则更简单：连接仓库后，它们会自动在每次推送时构建部署，并为每个 PR 生成一个预览地址。

用 Docker 部署到自己的服务器

需要部署到公司服务器时，常见做法是把构建产物和一个 Nginx 打包成 Docker 镜像。注意 SPA 需要配置“找不到文件就返回 index.html”：

# 第一阶段：用 Node 构建
FROM node:lts-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 第二阶段：只把 dist 放进一个很小的 Nginx 镜像
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

server {
  listen 80;
  root /usr/share/nginx/html;

  location / {
    try_files $uri $uri/ /index.html;          # 前端路由的回退
  }

  location /assets/ {
    expires 1y;                                # 带哈希的文件可以永久缓存
    add_header Cache-Control "public, immutable";
  }
}

上线之后：错误监控

第 5 章（下）讲过 createRoot 的错误回调。生产环境里，用户遇到的错误需要被收集起来。以 Sentry 为例： 

import * as Sentry from '@sentry/react'

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,       // 从环境变量读取
  integrations: [Sentry.browserTracingIntegration()],
  tracesSampleRate: 0.1,                       // 采样 10% 的性能数据
})

createRoot(document.getElementById('root'), {
  onUncaughtError: Sentry.reactErrorHandler(),   // 把 React 捕获到的错误交给 Sentry
  onCaughtError: Sentry.reactErrorHandler(),
}).render(<App />)

构建时开启 source map 并上传给 Sentry（它提供 Vite 插件），错误堆栈就能直接显示成源码的文件名和行号，而不是压缩后的一行乱码。
