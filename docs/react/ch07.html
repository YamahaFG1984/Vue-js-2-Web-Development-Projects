代码检查：ESLint

自动检查代码问题的过程叫 lint。用 Vite 模板创建的项目已经带好了 ESLint 9 的扁平配置 eslint.config.js，结构大致如下（具体写法以生成的文件为准）： 

import js from '@eslint/js'
import globals from 'globals'
import reactHooks from 'eslint-plugin-react-hooks'
import reactRefresh from 'eslint-plugin-react-refresh'
import { defineConfig, globalIgnores } from 'eslint/config'

export default defineConfig([
  globalIgnores(['dist']),
  {
    files: ['**/*.{js,jsx}'],
    extends: [
      js.configs.recommended,                // JS 通用规则：未定义的变量、未使用的变量……
      reactHooks.configs.flat.recommended,   // Hooks 规则（含 React Compiler 相关检查）
      reactRefresh.configs.vite,             // 保证 Fast Refresh 正常工作
    ],
    languageOptions: {
      globals: globals.browser,
      parserOptions: { ecmaFeatures: { jsx: true } },
    },
  },
])

⚠ 不要随手关掉 exhaustive-deps

像用户一样测试

Testing Library 的核心理念是：测试越像用户使用软件的方式，就越能给你信心。所以它不鼓励你检查组件内部的状态或实现细节， 而是按用户能感知的方式找元素（“一个叫‘添加’的按钮”），模拟用户的操作（点击、输入），再断言用户能看到的结果：

第一个组件测试

export default function BaseButton({ icon, badge = null, disabled = false, onClick, children }) {
  return (
    <button className="base-button" disabled={disabled} onClick={onClick}>
      {icon && <i className="material-icons icon">{icon}</i>}
      <span className="content">{children}</span>
      {badge !== null && <div className="button-badge"><span>{badge}</span></div>}
    </button>
  )
}

import { describe, test, expect, vi } from 'vitest'
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import BaseButton from './BaseButton.jsx'

describe('BaseButton', () => {
  test('点击时调用 onClick', async () => {
    const user = userEvent.setup()
    const onClick = vi.fn()                           // 一个“间谍”函数，记录自己被调用的情况

    render(<BaseButton onClick={onClick}>添加商品</BaseButton>)
    await user.click(screen.getByRole('button', { name: /添加商品/ }))

    expect(onClick).toHaveBeenCalledTimes(1)
  })

  test('disabled 时不可点击', async () => {
    const user = userEvent.setup()
    const onClick = vi.fn()

    render(<BaseButton disabled onClick={onClick}>添加商品</BaseButton>)
    const button = screen.getByRole('button')
    await user.click(button)

    expect(button).toBeDisabled()
    expect(onClick).not.toHaveBeenCalled()
  })

  test('显示角标', () => {
    render(<BaseButton badge={3}>购物车</BaseButton>)
    expect(screen.getByText('3')).toBeInTheDocument()
  })
})

测试纯逻辑：最简单也最划算

reducer、Zustand store、工具函数都是普通的 JS，测试它们不需要渲染任何东西。比如购物车 store：

import { beforeEach, test, expect } from 'vitest'
import { useCartStore } from './cart.js'

beforeEach(() => {
  useCartStore.setState({ items: [] })      // 每个测试前重置状态
})

test('重复添加同一件商品时数量累加', () => {
  const { addItem } = useCartStore.getState()
  addItem({ id: 1, price: 2.99 })
  addItem({ id: 1, price: 2.99 })
  expect(useCartStore.getState().items).toEqual([{ id: 1, price: 2.99, count: 2 }])
})
✓ 测试请求：模拟网络

组件里有请求时，不要在测试里真的访问服务器。可以用 vi.spyOn(globalThis, 'fetch') 返回假数据， 或者用 MSW 在网络层拦截请求 —— 后者让测试代码和真实代码完全一致，也可以复用在开发环境里做 mock 服务器。

🔍 快照测试还要不要用？（点击展开）

Vitest 支持 expect(container).toMatchSnapshot()，把渲染出的 HTML 存下来，以后比较。 它写起来容易，但缺点也明显：任何无关紧要的改动都会让快照失败，大家习惯性地 vitest -u 更新，快照就失去了意义。 React 社区更推荐写明确的断言（“按钮被禁用了”“显示了 3”）。快照适合偶尔用在输出稳定、内容很多的场景。

按需加载：动态 import

用户一次只用一种语言，没必要把五种语言都打进首屏代码。动态 import() 会让构建工具把被导入的模块拆成独立的文件（chunk），需要时才下载： 

import i18n from 'i18next'
import { initReactI18next } from 'react-i18next'
import LanguageDetector from 'i18next-browser-languagedetector'
import resourcesToBackend from 'i18next-resources-to-backend'

export const langs = ['zh', 'en', 'fr', 'es', 'de']

i18n
  .use(LanguageDetector)        // 根据浏览器语言（navigator.languages）自动选择
  .use(resourcesToBackend(      // 需要哪种语言，就动态 import 哪个文件
    (lng) => import(`./locales/${lng}.json`)
  ))
  .use(initReactI18next)
  .init({
    supportedLngs: langs,
    fallbackLng: 'en',          // 缺翻译时退回英文
    load: 'languageOnly',       // 'zh-CN' 只取 'zh'
  })

export default i18n

import { Suspense } from 'react'
import './i18n.js'

createRoot(document.getElementById('root')).render(
  <Suspense fallback={<div className="loading" />}>   {/* 语言包下载完之前显示 */}
    <App />
  </Suspense>
)

在组件中使用

import { useTranslation } from 'react-i18next'
import { useNavigate } from 'react-router'
import { langs } from '../i18n.js'
import BaseButton from './BaseButton.jsx'

export default function PageLocale() {
  const { t, i18n } = useTranslation()
  const navigate = useNavigate()

  return (
    <main className="page-locale">
      <h1>{t('change-lang')}</h1>
      <div className="locales">
        {langs.map((lang) => (
          <div key={lang} className="locale">
            <BaseButton
              className={lang === i18n.resolvedLanguage ? 'selected' : ''}
              onClick={() => i18n.changeLanguage(lang)}   // 首次切换时会去下载语言包
            >
              {t(`lang.${lang}`)}
            </BaseButton>
          </div>
        ))}
      </div>
      <BaseButton className="secondary" onClick={() => navigate(-1)}>{t('back')}</BaseButton>
    </main>
  )
}
✓ 价格和日期也要本地化

不同地区的货币和数字格式不同。直接用浏览器的 Intl： new Intl.NumberFormat(i18n.resolvedLanguage, { style: 'currency', currency: 'CNY' }).format(price)。 i18next 也内置了基于 Intl 的格式化，可以写在翻译字符串里："{{price, currency(CNY)}}"。

服务端渲染与 Next.js

为什么需要 SSR

到目前为止都是客户端渲染（CSR）：服务器返回一个几乎空白的 HTML，浏览器下载并执行 JS 后内容才出现。 服务端渲染（SSR）是在服务器上先把 React 应用渲染成 HTML 再发给浏览器：

水合（hydration）：浏览器拿到的 HTML 是“死”的，客户端 React 启动后不会重新创建 DOM，而是认领服务器渲染好的 DOM，给它挂上事件处理和状态， 底层用的是 hydrateRoot 而不是 createRoot。

ⓘ 不是所有应用都需要 SSR

后台管理系统、需要登录才能用的工具，用 Vite 做纯客户端应用就好。电商、博客、内容站这类需要被搜索引擎收录的场景才值得上 SSR。 内容基本不变的话，还可以静态生成（SSG）：构建时就把页面渲染成 HTML 文件。

服务端组件：React 19 最重要的新概念

传统 SSR 只是“在服务器上先跑一遍”，所有组件的代码仍然要发到浏览器去水合。React 19 正式加入了服务端组件（Server Components）： 有些组件只在服务器上运行，它们的代码永远不会发给浏览器。

★ 一句话区分

需要交互（状态、事件、浏览器 API）的组件，在文件顶部写 'use client'，它就是客户端组件； 其他组件默认是服务端组件，可以是 async 函数，直接 await 数据。服务端组件可以渲染客户端组件，并把可序列化的数据作为 props 传给它。 原书的 asyncData、手动注入 __INITIAL_STATE__ 这一整套，在这里变成了“组件里直接 await”。

用 Next.js 实现

服务端组件需要框架支持。Next.js 的 App Router 是目前最成熟的实现，也是 React 官方文档首推的框架： 

npx create-next-app@latest e-shop-next
cd e-shop-next
npm run dev        # http://localhost:3000
e-shop-next/ ├── next.config.js └── app/ # App Router：文件夹即路由 ├── layout.jsx # 根布局（服务端组件） ├── page.jsx # → / ├── checkout/ │ └── page.jsx # → /checkout └── item/ └── [id]/ ├── page.jsx # → /item/:id └── loading.jsx # 加载中的界面（自动包一层 Suspense）
import AddToCartButton from './AddToCartButton.jsx'

async function getItem(id) {
  const res = await fetch(`http://localhost:3000/items/${id}`)   // 在服务器上请求，浏览器看不到
  if (!res.ok) return null
  return res.json()
}

// SEO：根据数据生成页面标题和描述
export async function generateMetadata({ params }) {
  const { id } = await params
  const item = await getItem(id)
  return { title: item?.title, description: `购买 ${item?.title}` }
}

export default async function ItemPage({ params }) {
  const { id } = await params
  const item = await getItem(id)
  if (!item) return <p>商品不存在</p>

  return (
    <main className="store-item">
      <img src={item.img} alt={item.title} />
      <h1>{item.title}</h1>
      <p className="price">¥{item.price}</p>
      {/* 只有这个按钮需要交互，是客户端组件 */}
      <AddToCartButton item={{ id: item.id, title: item.title, price: item.price }} />
    </main>
  )
}

⚠ 写在服务器和浏览器都会运行的代码时
  • 客户端组件也会先在服务器上渲染一次。window、localStorage 只能在 useEffect 或事件处理函数里访问。
  • 服务器和浏览器渲染的结果必须一致，否则会出现“水合不匹配”警告（比如直接在 JSX 里显示 Date.now() 或随机数）。
  • 服务器是多个用户共享的：不要把某个用户的数据放进模块级变量。Zustand 这类模块级 store 在 SSR 中要按请求创建（Zustand 文档有专门的 Next.js 指南）。
✓ 其他选择

React Router 框架模式（原 Remix）同样基于 Vite，提供 SSR、文件路由和 loader/action 数据模型，从第 5 章的数据模式迁移过去很自然。 Next.js 里做国际化通常用 next-intl。

🔍 不用框架手写 SSR（点击展开）

理解原理用。服务器端用 react-dom/server 把组件渲染成 HTML 流，浏览器端用 hydrateRoot 水合：

// server.js（Node）
import { renderToPipeableStream } from 'react-dom/server'

app.get('*', (req, res) => {
  const { pipe } = renderToPipeableStream(<App url={req.url} />, {
    bootstrapScripts: ['/assets/client.js'],
    onShellReady() {
      res.setHeader('Content-Type', 'text/html')
      pipe(res)                     // 流式发送：Suspense 边界外的内容先到
    },
  })
})

// client.jsx（浏览器）
import { hydrateRoot } from 'react-dom/client'
hydrateRoot(document, <App url={location.pathname} />)

真实项目还要处理数据预取、状态序列化、路由、代码分割、开发时热更新……这正是框架存在的意义。Vite 官方文档有一份 SSR 指南，可以作为起点。
