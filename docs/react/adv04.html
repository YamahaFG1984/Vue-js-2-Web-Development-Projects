跨端：PWA、移动端与桌面端

我们写的 React 应用本质上是一堆 HTML、CSS 和 JS。浏览器能运行它，手机 App 里的 WebView 也能运行它，桌面程序里的 WebView 同样可以。 本章介绍三种把 React 应用带出浏览器标签页的方式：能安装、能离线的 PWA，打包成 iOS / Android 应用的 Capacitor， 以及打包成 Windows / macOS / Linux 桌面程序的 Tauri。你学过的 React 知识一点都不用变。 最后还会介绍 React 独有的另一条路：用 React Native 写真正的原生界面。

本章目标

  • 了解几种跨端方案的原理和取舍：PWA、Capacitor、Tauri、Electron
  • 用 vite-plugin-pwa 让第 2 章的笔记本可以安装、可以离线使用
  • 理解 Service Worker 的几种缓存策略，并处理“有新版本”的更新提示
  • 用 Capacitor 把应用打包成手机 App，调用相机和定位等原生能力
  • 用 Tauri 2 把应用打包成桌面程序，从前端调用 Rust 命令
  • 用“适配器”组织平台相关代码，让一份代码跑在所有平台上
  • 了解 React Native 和 Expo：什么时候该用原生界面代替 WebView

★ 先从 PWA 开始

PWA 成本最低，几乎只是加一个插件。很多“要不要做个 App”的需求，其实一个可以添加到主屏幕、能离线打开的 PWA 就能满足。 确实需要上架应用商店或者用到浏览器拿不到的原生能力时，再考虑 Capacitor 或 Tauri。

PWA：让网站像 App 一样

PWA（Progressive Web App，渐进式 Web 应用）不是某个框架，而是一组浏览器能力的组合。核心是两个文件：

📄

Web App Manifest

一个 JSON 文件，描述应用名、图标、主题色、启动方式。有了它，浏览器才会提示“安装”。

⚙

Service Worker

运行在页面之外的一段脚本，能拦截网络请求、管理缓存，让应用在离线时也能打开。

给笔记本加上 vite-plugin-pwa

第 2 章的笔记本把数据存在 localStorage 里，天生适合离线使用。把它改成 Vite 项目后（第 4 章的方式），安装插件：

npm i -D vite-plugin-pwa

import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import { VitePWA } from 'vite-plugin-pwa'

export default defineConfig({
  plugins: [
    react(),
    VitePWA({
      registerType: 'prompt',              // 有新版本时提示用户，而不是悄悄替换
      includeAssets: ['favicon.svg'],
      manifest: {
        name: 'Markdown 笔记本',
        short_name: '笔记本',
        theme_color: '#087ea4',
        background_color: '#ffffff',
        display: 'standalone',             // 安装后没有浏览器地址栏，像原生 App
        icons: [
          { src: 'pwa-192.png', sizes: '192x192', type: 'image/png' },
          { src: 'pwa-512.png', sizes: '512x512', type: 'image/png' },
          { src: 'pwa-512.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' },
        ],
      },
      workbox: {
        globPatterns: ['**/*.{js,css,html,svg,png,woff2}'],   // 构建产物全部预缓存
      },
    }),
  ],
})

构建后，插件会生成 manifest.webmanifest 和 sw.js，并自动在 HTML 里注册。用 npm run build && npm run preview 打开，Chrome 地址栏右侧会出现“安装”图标；在开发者工具 Application 面板勾选 Offline 再刷新，页面依然能打开。

⚠ Service Worker 只在 HTTPS 下工作

localhost 是例外，开发时可以用。部署时 GitHub Pages、Netlify、Vercel 都默认提供 HTTPS。开发环境默认不启用 SW，要调试可以在插件选项里设置 devOptions: { enabled: true }。

缓存策略

Service Worker 拦截到一个请求后，要决定“先看缓存还是先问网络”。不同的资源适合不同的策略：

构建产物默认已经预缓存了。对运行时才请求的资源（比如接口、第三方图片），在 workbox.runtimeCaching 里按 URL 指定策略：

workbox: {
  globPatterns: ['**/*.{js,css,html,svg,png,woff2}'],
  runtimeCaching: [
    {
      urlPattern: ({ url }) => url.pathname.startsWith('/api/'),
      handler: 'NetworkFirst',
      options: { cacheName: 'api', networkTimeoutSeconds: 3, expiration: { maxEntries: 50 } },
    },
    {
      urlPattern: ({ request }) => request.destination === 'image',
      handler: 'StaleWhileRevalidate',
      options: { cacheName: 'images', expiration: { maxEntries: 100, maxAgeSeconds: 7 * 24 * 3600 } },
    },
  ],
},

“有新版本”提示

Service Worker 的更新有个容易让人困惑的地方：你部署了新版本，用户打开页面时，新的 SW 会被下载，但旧 SW 仍在控制页面， 直到所有标签页关闭。registerType: 'prompt' 让我们自己决定何时切换。插件为 React 提供了一个 Hook： 

import { useRegisterSW } from 'virtual:pwa-register/react'

export default function UpdatePrompt() {
  const {
    needRefresh: [needRefresh, setNeedRefresh],      // 返回 [值, setter]，和 useState 一样
    offlineReady: [offlineReady, setOfflineReady],
    updateServiceWorker,
  } = useRegisterSW()

  if (!needRefresh && !offlineReady) return null
  const close = () => { setNeedRefresh(false); setOfflineReady(false) }

  return (
    <div className="toast" role="status">
      <span>{needRefresh ? '有新版本可用' : '已可以离线使用'}</span>
      {needRefresh && <button onClick={() => updateServiceWorker(true)}>更新</button>}
      <button onClick={close}>关闭</button>
    </div>
  )
}

再写一个 useOnline()（用第 6 章的 useSyncExternalStore 订阅 online / offline 事件）， 可以在离线时显示一个小标记，并把“同步到服务器”之类的操作排队，等恢复网络后再执行。

ⓘ iOS 上的 PWA

iPhone 上需要用 Safari 的“分享 → 添加到主屏幕”来安装，没有自动的安装提示。从 iOS 16.4 起，添加到主屏幕的 PWA 也能接收推送通知。 不同浏览器对 PWA 各项能力的支持程度不一，用到某个 API 前先查一下兼容性。

Capacitor：打包成手机 App

Capacitor 把你的 dist/ 放进一个原生的 iOS / Android 工程里，用系统的 WebView 显示，并提供一座桥： JS 调用插件方法，桥把调用转给原生代码（Swift / Kotlin），结果再传回来。

添加到现有项目

  1. 安装并初始化： 
    npm i @capacitor/core
npm i -D @capacitor/cli
npx cap init "地图博客" com.example.geoblog --web-dir dist
  2. 添加平台（需要本机装好 Android Studio；iOS 需要 macOS + Xcode）： 
    npm i @capacitor/android @capacitor/ios
npx cap add android
npx cap add ios
  3. 每次改完前端代码：构建，然后同步到原生工程，再用 IDE 打开运行： 
    npm run build
npx cap sync          # 复制 dist/ 并更新原生插件
npx cap open android  # 在 Android Studio 里点运行

调用原生能力

第 6 章的地图博客需要“在我的位置发帖”。在 App 里，用定位插件拿到更准确的位置；用相机插件给帖子拍照：

npm i @capacitor/geolocation @capacitor/camera
npx cap sync

import { Capacitor } from '@capacitor/core'
import { Geolocation } from '@capacitor/geolocation'
import { Camera, CameraResultType, CameraSource } from '@capacitor/camera'

export async function getMyPosition() {
  const { coords } = await Geolocation.getCurrentPosition({ enableHighAccuracy: true })
  return { lat: coords.latitude, lng: coords.longitude }
}

export async function takePhoto() {
  const photo = await Camera.getPhoto({
    resultType: CameraResultType.Uri,   // 返回一个可以直接放进 <img src> 的地址
    source: CameraSource.Prompt,        // 让用户选择拍照还是从相册选
    quality: 80,
  })
  return photo.webPath
}

export const isNativeApp = Capacitor.isNativePlatform()

这些官方插件在浏览器里也有 Web 实现（定位用浏览器的 Geolocation API，相机弹出文件选择），所以同一份代码在网页和 App 里都能跑。 需要原生权限的插件，记得按插件文档在 Info.plist（iOS）和 AndroidManifest.xml（Android）里声明权限说明。

✓ 想要原生的外观？试试 Ionic React

Capacitor 只负责“装进 App”和“调用原生能力”，界面还是你自己写的。如果希望列表、标签栏、页面切换动画都像原生 App， 可以使用同一团队的 Ionic React 组件库（@ionic/react），它会根据平台自动切换 iOS / Material 风格。 如果连“原生的外观”都不够，而是要原生的性能和手感，就该看本章最后的 React Native 了。

Tauri：打包成桌面程序

Tauri 用操作系统自带的 WebView（Windows 的 WebView2、macOS 的 WKWebView、Linux 的 WebKitGTK）显示界面，后端是一个小巧的 Rust 程序。 和自带完整 Chromium 的 Electron 相比，安装包可以小一个数量级。Tauri 2 还加入了 iOS / Android 支持和更细粒度的权限系统。

给 Vite 项目加上 Tauri

先按 Tauri 官方文档安装 Rust 和各平台依赖，然后在项目根目录：

npm i -D @tauri-apps/cli
npx tauri init         # 生成 src-tauri/ 目录，按提示填写 dev 地址和 dist 目录
npx tauri dev          # 启动 Vite 并打开桌面窗口，支持热更新
npx tauri build        # 生成 .msi / .dmg / .deb 等安装包

从 React 调用 Rust

前端拿到桌面能力有两种途径：自己写的 Rust 命令，以及官方插件。先看前者：用 #[tauri::command] 标记一个 Rust 函数（这里是统计字数），前端用 invoke 调用它。后者用来把笔记导出成真正的 .md 文件：

#[tauri::command]
fn word_count(text: &str) -> usize {
    text.split_whitespace().count()
}

#[cfg_attr(mobile, tauri::mobile_entry_point)]
pub fn run() {
    tauri::Builder::default()
        .plugin(tauri_plugin_dialog::init())
        .plugin(tauri_plugin_fs::init())
        .invoke_handler(tauri::generate_handler![word_count])
        .run(tauri::generate_context!())
        .expect("启动失败");
}

import { invoke } from '@tauri-apps/api/core'
import { save } from '@tauri-apps/plugin-dialog'
import { writeTextFile } from '@tauri-apps/plugin-fs'

export const countWords = (text) => invoke('word_count', { text })

export async function exportNote(note) {
  const path = await save({ defaultPath: `${note.title}.md`, filters: [{ name: 'Markdown', extensions: ['md'] }] })
  if (path) await writeTextFile(path, note.content)
}

文件对话框和文件读写用的是官方插件（npm i @tauri-apps/plugin-dialog @tauri-apps/plugin-fs，并在 Cargo.toml 里加上对应的 Rust 依赖， npx tauri add dialog 可以一步完成）。Tauri 2 默认不给前端任何权限，要在 capabilities 文件里明确声明： 

{
  "identifier": "default",
  "windows": ["main"],
  "permissions": ["core:default", "dialog:allow-save", "fs:allow-write-text-file"]
}
ⓘ 为什么要声明权限

桌面程序能访问用户的整个文件系统。如果应用加载的某个第三方脚本被篡改，权限越大，造成的破坏越大。 “默认什么都不允许，用到什么声明什么”是 Tauri 的安全设计；fs 插件还可以进一步限定只能访问某些目录。具体的权限名称以插件文档为准。

平台相关代码怎么组织

同一个应用要跑在网页、手机和桌面上，“保存笔记”“获取位置”在每个平台的实现都不一样。不要在组件里到处写 if (isTauri) … else if (isNative) …， 而是定义一个统一的接口，每个平台各写一份适配器： 

import { Capacitor } from '@capacitor/core'

// Tauri 2 会在 window 上注入 __TAURI_INTERNALS__
const isTauri = '__TAURI_INTERNALS__' in window
const isNative = Capacitor.isNativePlatform()

// 动态导入：每个平台只加载自己的实现，网页版不会打包 Tauri 的代码
const load = isTauri ? () => import('./desktop.js')
  : isNative ? () => import('./native.js')
  : () => import('./web.js')

let impl
export async function getPlatform() {
  impl ??= await load()
  return impl
}

export async function exportNote(note) {
  const url = URL.createObjectURL(new Blob([note.content], { type: 'text/markdown' }))
  const a = Object.assign(document.createElement('a'), { href: url, download: `${note.title}.md` })
  a.click()
  URL.revokeObjectURL(url)
}

三个文件导出同样名字、同样参数的函数，组件里只写 (await getPlatform()).exportNote(note)。 如果某个平台的代码依赖很重，也可以结合第 4 章的环境变量，用 vite build --mode desktop 在构建时就确定平台。

另一条路：React Native 与 Expo

前面三种方案都是“把网页装进壳里”，界面最终还是 WebView 里的 HTML。React 还有一条独特的路：React Native。 它用同样的组件、状态、Hooks 写法，但渲染出来的是真正的原生控件（iOS 的 UIView、Android 的 View），而不是 DOM。 第 9 章说过，React 的核心只负责“算出元素树、比较差异”，最后由谁去修改界面是可以替换的 —— react-dom 改 DOM，React Native 改原生视图。

用 Expo 起步是官方推荐的方式，它包办了原生工程配置、常用原生模块和云端构建：

npx create-expo-app@latest notebook-app
cd notebook-app
npx expo start          # 用手机上的 Expo Go 扫码，立即在真机上看到效果

import { useState } from 'react'
import { View, Text, TextInput, Pressable, FlatList, StyleSheet } from 'react-native'
import { useNotesStore } from '../stores/notes'      // 和网页版共用的 Zustand store

export default function Notes() {
  const notes = useNotesStore((s) => s.notes)
  const addNote = useNotesStore((s) => s.addNote)
  const [title, setTitle] = useState('')

  return (
    <View style={styles.page}>
      <TextInput style={styles.input} value={title} onChangeText={setTitle} placeholder="新笔记标题" />
      <Pressable style={styles.button} onPress={() => { addNote(title); setTitle('') }}>
        <Text style={styles.buttonText}>添加</Text>
      </Pressable>
      {/* FlatList 自带虚拟化，只渲染屏幕上的行（第 8 章的虚拟滚动） */}
      <FlatList data={notes} keyExtractor={(n) => n.id}
                renderItem={({ item }) => <Text style={styles.item}>{item.title}</Text>} />
    </View>
  )
}

const styles = StyleSheet.create({
  page: { flex: 1, padding: 16, gap: 8 },
  input: { borderWidth: 1, borderColor: '#ccc', borderRadius: 8, padding: 10, fontSize: 16 },
  button: { backgroundColor: '#087ea4', borderRadius: 8, padding: 12, alignItems: 'center' },
  buttonText: { color: '#fff', fontWeight: '600' },
  item: { paddingVertical: 12, borderBottomWidth: StyleSheet.hairlineWidth },
})
能复用的要重写的
组件的写法、Hooks、状态管理（Zustand）、TanStack Query、Zod 校验、业务逻辑和工具函数所有界面：没有 div、span、CSS 文件；用 View、Text 和 StyleSheet（类似 CSS 的 Flexbox 子集）
TypeScript 类型、接口层（fetch 照常可用）路由（Expo Router / React Navigation）、存储（localStorage 换成 AsyncStorage / SQLite）
★ 怎么选

以内容和表单为主、已经有网页版的应用，Capacitor 能用最小的代价上架；对滚动流畅度、手势、相机、动画要求高的消费级 App，React Native 的体验明显更好。 很多团队的做法是：把业务逻辑放进 monorepo 的共享包（第 11 章），网页版用 react-dom，App 用 React Native，各自写界面。 社区也有 react-native-web、Tamagui 等方案尝试让一份界面代码同时跑在两边，但会带来额外的约束。
