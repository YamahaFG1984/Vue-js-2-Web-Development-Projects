AI 应用前端：流式聊天界面

如今很多应用都内置了一个 AI 助手。它的界面看似简单，就是一个聊天框，但要做好并不容易：回答要一个字一个字地流出来， 用户要能随时停止，Markdown 和代码要安全地渲染，滚动要跟得上又不能打扰用户往上翻。 本章用 React 19 做一个完整的流式聊天界面，后端用轻量的 Hono 框架调用 DeepSeek API。第 8 章学过的 SSE，在这里会派上大用场。

本章目标

  • 理解 AI 应用的基本架构，以及为什么 API 密钥绝不能放在前端
  • 理解流式输出的价值，以及 SSE 数据是怎么一块一块到达的
  • 用 Hono 写一个流式转发接口：调用 DeepSeek、翻译事件格式、客户端断开时停止生成
  • 把 API 密钥放进 .env 并加入 .gitignore
  • 用 fetch + ReadableStream 读取流，写一个 useChat 自定义 Hook，并展示模型的“思考过程”
  • 用 AbortController 实现“停止生成”
  • 安全地渲染流式 Markdown：节流、markdown-it、DOMPurify
  • 处理聊天界面的细节：自动滚动、回车发送与中文输入法、无障碍

整体架构

⚠ API 密钥永远不能出现在前端代码里

第 4 章讲过：所有 VITE_ 开头的环境变量都会被原样打包进 JS 文件，任何人打开开发者工具都能看到。 一旦泄露，别人就能用你的账户无限调用、产生费用。所以一定要有一个自己的后端：密钥只放在服务器的 .env 文件里（并加入 .gitignore），并且在这里做登录校验和限流（比如每个用户每分钟最多 10 次）。

为什么要流式输出

大模型生成一段长回答可能要十几秒甚至更久。如果等它全部生成完再一次性返回，用户会盯着转圈图标干等。 流式输出则是模型每生成一小段文字就立刻发过来，用户不到一秒就能看到第一个字，然后边生成边阅读：

传输格式就是第 8 章的 SSE：服务器保持连接不关闭，每次写一段 event: …\ndata: …\n\n。 不过第 8 章用的 EventSource 只能发 GET 请求，而聊天需要用 POST 把整段对话发过去，所以前端要改用 fetch 自己读取响应流。

后端：用 Hono 转发 DeepSeek 的流

后端我们用 Hono。它是一个很小的 Web 框架，路由写法和 Express 很像，但基于浏览器同款的 Request / Response 标准， 同一份代码可以跑在 Node.js、Bun、Deno 和 Cloudflare Workers 上。它还自带了我们正需要的 SSE 工具 streamSSE。 模型用 DeepSeek，它的接口与 OpenAI 格式兼容，用普通的 fetch 就能调用，不需要额外的 SDK。

⚠ 密钥一旦提交，就当它已经泄露

git 会永久保存历史，删掉文件再提交一次并不能把密钥从历史里抹去，GitHub 上的公开仓库还会被机器人在几分钟内扫描到。 如果不小心提交了，第一件事是到 DeepSeek 控制台作废这个密钥、换一个新的，然后再清理历史。

上游的格式和我们的格式

DeepSeek 返回的也是 SSE，但每一条都是一大段 JSON，而且推理模型会先流出“思考过程”（reasoning_content），再流出正式回答（content），最后是一个不是 JSON 的 [DONE]。 服务器把它翻译成我们自己定义的、更简单的几种事件，这样前端完全不用关心用的是哪家模型：

完整的服务器代码

解析上游 SSE 用的正是下一节要写的 readSSE()，前后端共用一个解析函数：

import { Hono } from 'hono'
import { serve } from '@hono/node-server'
import { streamSSE } from 'hono/streaming'
import { zValidator } from '@hono/zod-validator'
import { z } from 'zod'
import { readSSE } from '../src/lib/readSSE.js'

const API_KEY = process.env.DEEPSEEK_API_KEY       // 用 node --env-file=.env 启动时读入
if (!API_KEY) throw new Error('缺少 DEEPSEEK_API_KEY，请在 .env 中配置')

const SYSTEM_PROMPT = '你是一个友好的 React 助教。用简体中文回答，适当使用 Markdown 和代码块。'

// 只接受 user / assistant 交替出现、以 user 结尾的纯文本消息
const ChatBody = z.object({
  messages: z
    .array(z.object({
      role: z.enum(['user', 'assistant']),
      content: z.string().min(1).max(8000),
    }))
    .min(1)
    .max(50)
    .refine(
      (ms) => ms.every((m, i) => m.role === (i % 2 === 0 ? 'user' : 'assistant')) && ms.at(-1).role === 'user',
      '消息必须以 user 开始、交替出现、以 user 结束',
    ),
})

const app = new Hono()

app.post(
  '/api/chat',
  zValidator('json', ChatBody, (result, c) => {
    if (!result.success) return c.json({ message: '消息格式不正确' }, 400)
  }),
  async (c) => {
    const { messages } = c.req.valid('json')
    const upstreamAbort = new AbortController()

    const upstream = await fetch('https://api.deepseek.com/chat/completions', {
      method: 'POST',
      headers: { Authorization: `Bearer ${API_KEY}`, 'Content-Type': 'application/json' },
      body: JSON.stringify({
        model: 'deepseek-flash',
        stream: true,
        reasoning_effort: 'low',                   // 聊天场景少想一点，回答更快
        stream_options: { include_usage: true },   // 最后一块附带 token 用量
        messages: [{ role: 'system', content: SYSTEM_PROMPT }, ...messages],
      }),
      signal: upstreamAbort.signal,
    })

    if (!upstream.ok) {
      console.error('DeepSeek 返回错误', upstream.status, await upstream.text())
      const message = upstream.status === 429 ? '请求太频繁，请稍后再试' : 'AI 服务暂时不可用'
      return c.json({ message }, 502)              // 不把上游的错误细节暴露给前端
    }

    return streamSSE(
      c,
      async (stream) => {
        // 浏览器断开（用户点了停止或关掉页面）→ 中止对 DeepSeek 的请求，不再产生费用
        stream.onAbort(() => upstreamAbort.abort())

        let finishReason = null
        let usage = null
        for await (const { data } of readSSE(upstream.body)) {
          if (data === '[DONE]') break
          const chunk = JSON.parse(data)
          const choice = chunk.choices?.[0]
          if (choice?.delta?.reasoning_content) {
            await stream.writeSSE({ event: 'reasoning', data: JSON.stringify({ text: choice.delta.reasoning_content }) })
          }
          if (choice?.delta?.content) {
            await stream.writeSSE({ event: 'delta', data: JSON.stringify({ text: choice.delta.content }) })
          }
          if (choice?.finish_reason) finishReason = choice.finish_reason
          if (chunk.usage) usage = chunk.usage
        }
        await stream.writeSSE({ event: 'done', data: JSON.stringify({ finishReason, usage }) })
      },
      // 第三个参数：流式过程中出错时调用
      async (err, stream) => {
        if (upstreamAbort.signal.aborted) return   // 是我们主动中止的，不算错误
        console.error(err)
        await stream.writeSSE({ event: 'error', data: JSON.stringify({ message: '生成失败，请稍后重试' }) })
      },
    )
  },
)

serve({ fetch: app.fetch, port: 3000 })

读取流：前后端共用的解析器

不管是服务器读 DeepSeek，还是浏览器读我们的服务器，fetch 返回的 response.body 都是一个 ReadableStream，可以一块一块地读。但要注意： 网络传输的“块”和 SSE 的“事件”并不对齐。一个块里可能有半个事件，也可能有好几个事件，所以必须自己做缓冲： 

// 把一个 SSE 响应体变成异步迭代器：for await (const { event, data } of readSSE(body))
// data 是原始字符串，由调用者决定怎么解析（DeepSeek 最后会发一个非 JSON 的 [DONE]）
export async function* readSSE(body) {
  const reader = body.pipeThrough(new TextDecoderStream()).getReader()   // 字节 → 文本
  let buffer = ''
  while (true) {
    const { value, done } = await reader.read()
    if (done) return
    buffer += value.replaceAll('\r\n', '\n')
    let end
    while ((end = buffer.indexOf('\n\n')) !== -1) {      // 找到一个完整事件
      const raw = buffer.slice(0, end)
      buffer = buffer.slice(end + 2)
      let event = 'message'
      const data = []
      for (const line of raw.split('\n')) {
        if (line.startsWith('event:')) event = line.slice(6).trim()
        else if (line.startsWith('data:')) data.push(line.slice(5).trimStart())
        // 以冒号开头的是注释（比如保活用的 ": keep-alive"），忽略
      }
      if (data.length) yield { event, data: data.join('\n') }
    }
  }
}

这个函数在两个地方都会用到：服务器用它解析 DeepSeek 的流，浏览器用它解析我们服务器的流。所以它不擅自 JSON.parse， 而是把 data 原样交给调用者。按照 SSE 规范，一个事件可以有多行 data:，要用换行拼起来；以冒号开头的行是注释，服务器有时用它保持连接不断。

✓ 为什么用 TextDecoderStream

一个汉字在 UTF-8 里占 3 个字节，网络块可能恰好在一个汉字中间断开。如果每块单独用 new TextDecoder().decode(chunk) 解码，就会出现乱码“�”。 TextDecoderStream 会自动保留不完整的字节，等下一块到达再拼起来解码。

useChat：聊天的状态与逻辑

把所有聊天逻辑封装进一个自定义 Hook。先看它的状态变化：

import { useState, useRef } from 'react'
import { readSSE } from '@/lib/readSSE'

// 发给服务器的历史：只保留 role 和 content（思考过程不回传）。
// 出错或还没输出正文就被停止的回复，连同它前面的提问一起跳过，保证 user / assistant 严格交替
function toHistory(messages) {
  const result = []
  for (const { role, content, error } of messages) {
    if (role === 'assistant' && (!content || error)) { result.pop(); continue }
    result.push({ role, content })
  }
  return result
}

export function useChat(endpoint = '/api/chat') {
  const [messages, setMessages] = useState([]) // { id, role, content, reasoning?, stopped?, truncated?, error? }
  const [status, setStatus] = useState('idle') // 'idle' | 'streaming' | 'error'
  const controllerRef = useRef(null)

  // 只替换最后一条（正在生成的回复），前面的消息对象保持不变 → memo 过的 ChatMessage 不会重新渲染
  const updateReply = (change) =>
    setMessages((list) => [...list.slice(0, -1), { ...list.at(-1), ...change(list.at(-1)) }])

  async function run(conversation) {
    const body = JSON.stringify({ messages: toHistory(conversation) })
    setMessages([...conversation, { id: crypto.randomUUID(), role: 'assistant', content: '', reasoning: '' }])

    const controller = new AbortController()
    controllerRef.current = controller
    setStatus('streaming')
    try {
      const res = await fetch(endpoint, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body,
        signal: controller.signal,
      })
      if (!res.ok) throw new Error((await res.json().catch(() => null))?.message || `HTTP ${res.status}`)

      for await (const { event, data } of readSSE(res.body)) {
        const payload = JSON.parse(data)
        // 用更新函数：每一块都基于最新的回复追加（第 2 章的“状态是快照”）
        if (event === 'reasoning') updateReply((r) => ({ reasoning: r.reasoning + payload.text }))
        else if (event === 'delta') updateReply((r) => ({ content: r.content + payload.text }))
        else if (event === 'error') throw new Error(payload.message)
        else if (event === 'done' && payload.finishReason === 'length') updateReply(() => ({ truncated: true }))
      }
      setStatus('idle')
    } catch (err) {
      if (err.name === 'AbortError') { // 用户主动停止，不算错误
        updateReply(() => ({ stopped: true }))
        setStatus('idle')
      } else {
        updateReply(() => ({ error: err.message }))
        setStatus('error')
      }
    } finally {
      controllerRef.current = null
    }
  }

  function send(text) {
    if (!text.trim() || status === 'streaming') return
    return run([...messages, { id: crypto.randomUUID(), role: 'user', content: text.trim() }])
  }

  function stop() {
    controllerRef.current?.abort() // fetch 中断 → 连接关闭 → 服务器 onAbort → 中止对 DeepSeek 的请求
  }

  function retry() {
    // 去掉出错的那条回复，用剩下的对话重新请求
    return run(messages.at(-1)?.error ? messages.slice(0, -1) : messages)
  }

  return { messages, status, isStreaming: status === 'streaming', send, stop, retry }
}

几个值得注意的地方：

  • 停止的链路：stop() 一行代码就串起了整条链路。controller.abort() 让 fetch 的读取抛出 AbortError， 同时浏览器关闭连接；Hono 的 stream.onAbort 随之触发，中止服务器对 DeepSeek 的请求。AbortController 放在 useRef 里，因为它不需要显示在界面上（第 2 章）。
  • 每一块都用更新函数：流式数据一秒钟可能来几十块，而且都发生在 await 之后。如果写 setMessages([...messages, …])，读到的是发起请求那一刻的快照， 后面的块会互相覆盖。updateReply 总是基于最新的列表追加（第 9 章的更新队列）。
  • 只替换最后一条：每来一块就生成一个新数组和一条新的回复对象，前面的消息对象原样保留。配合下一节 memo 过的 ChatMessage，历史消息不会跟着重新渲染。
  • 历史必须交替：如果模型还在思考时用户就点了停止，这条回复的正文是空的。只把它过滤掉的话，历史里会出现两条连续的 user 消息， 被服务器的校验拒绝。所以 toHistory() 遇到没有有效正文的回复时，连同它前面的提问一起跳过；思考过程（reasoning）也不会发回服务器。

安全地渲染 Markdown

模型的回答是 Markdown 文本，需要转成 HTML 再用 dangerouslySetInnerHTML 显示。这里有两个问题：安全和性能。

⚠ dangerouslySetInnerHTML 是 XSS 的入口

模型的输出会受用户输入影响，甚至可能被网页内容、文档里藏着的指令（提示词注入）诱导，输出 <img src=x onerror="偷走 cookie"> 这样的代码。 所以要两道防线：markdown-it 默认 html: false，原始 HTML 会被转义；渲染结果再经过 DOMPurify 清理一遍。 

import MarkdownIt from 'markdown-it'
import DOMPurify from 'dompurify'

// 模块级单例，所有消息共用一个实例
const md = new MarkdownIt({ html: false, linkify: true, breaks: true })

export function renderMarkdown(text) {
  return DOMPurify.sanitize(md.render(text))
}

import { memo, useDeferredValue, useMemo } from 'react'
import { renderMarkdown } from '@/lib/markdown'

// memo：只有正在生成的最后一条消息会重新渲染，前面的消息 props 没变，直接跳过
export default memo(function ChatMessage({ message, streaming }) {
  // 低优先级地解析 Markdown：内容来得太快时，React 会跳过中间版本，只渲染最新的（第 9 章）
  const content = useDeferredValue(message.content)
  const html = useMemo(() => renderMarkdown(content), [content])

  if (message.role === 'user') return <div className="msg user">{message.content}</div>

  const thinking = streaming && !message.content
  return (
    <div className="msg assistant">
      {/* 思考过程：还没开始回答时展开，开始回答后自动收起 */}
      {message.reasoning && (
        <details className="reasoning" open={thinking}>
          <summary>{thinking ? '思考中…' : '思考过程'}</summary>
          <p>{message.reasoning}</p>
        </details>
      )}
      <div dangerouslySetInnerHTML={{ __html: html }} />
      {streaming && <span className="cursor" aria-hidden="true" />}
      {message.stopped && <small className="note">已停止生成</small>}
      {message.truncated && <small className="note">回答过长，已被截断</small>}
      {message.error && <small className="note error">{message.error}</small>}
    </div>
  )
})

思考过程放在原生的 <details> 里：模型还在思考、正文没出来时展开，让用户知道“它在干活”；正文开始输出后自动收起，想看可以再点开。 思考过程和用户消息都是纯文本，用 JSX 的 {…} 插值即可，React 会自动转义。

ⓘ 为什么用 useDeferredValue，而不是自己写节流

每来一块都重新解析整段 Markdown，回答越长越费时。手写节流（比如每 80ms 最多解析一次）是一个办法； React 的做法是 useDeferredValue：输入框、光标这些紧急更新先完成，Markdown 渲染作为低优先级任务在后台进行， 新的块到达时还没渲染完的旧版本会被直接丢弃 —— 第 9 章并发渲染演示的就是这件事。它要配合 memo 才有效，否则父组件的每次渲染都会把它带上。

✓ 代码高亮放到最后

代码高亮（比如 Shiki）比较耗时，而且流式过程中代码块经常是不完整的。可以只在这条消息生成结束后再做高亮， 并用动态 import('shiki') 按需加载，不影响首屏体积。

自动滚动：跟随，但不强迫

新文字到达时应该自动滚到底部，但如果用户正往上翻看之前的内容，就不能把他拽回来。规则是：只有当用户本来就在底部附近时才自动滚动： 

const listRef = useRef(null)      // 可滚动的容器
const innerRef = useRef(null)     // 里面装消息的元素，它的高度会随内容增长
const stickRef = useRef(true)     // 用户是否停在底部附近（不需要渲染，所以用 ref）

function handleScroll() {
  const el = listRef.current
  stickRef.current = el.scrollHeight - el.scrollTop - el.clientHeight < 60
}

useEffect(() => {
  // 内容高度一变（新的字、Markdown 延迟渲染完成）就检查是否要滚到底
  const observer = new ResizeObserver(() => {
    if (stickRef.current) listRef.current.scrollTop = listRef.current.scrollHeight
  })
  observer.observe(innerRef.current)
  return () => observer.disconnect()
}, [])

<div ref={listRef} className="chat-list" role="log" aria-busy={isStreaming} onScroll={handleScroll}>
  <div ref={innerRef}>{/* 消息列表 */}</div>
</div>

为什么不在 useEffect(() => …, [lastMessage.content]) 里滚动？因为 Markdown 用了 useDeferredValue，真正的 DOM 可能在下一次低优先级提交时才更新， 那时这个 effect 已经跑过了。ResizeObserver 直接观察“内容高度变了”这个结果，不管它是哪次渲染造成的。

回车发送与中文输入法

这是中文用户最容易遇到的 bug：用拼音输入法打字时，按回车是为了确认候选词，如果此时消息被发出去了，用户会非常恼火。 浏览器在输入法组字期间触发的键盘事件，isComposing 为 true，判断一下即可： 

function handleKeyDown(e) {
  if (e.key !== 'Enter' || e.shiftKey) return                  // Shift+Enter 保留默认的换行
  if (e.nativeEvent.isComposing || e.keyCode === 229) return   // 输入法正在组字，交给输入法
  e.preventDefault()                                           // 阻止换行
  submit()
}

<textarea value={input} onChange={(e) => setInput(e.target.value)} onKeyDown={handleKeyDown} />

注意 isComposing 在原生事件上：React 的合成事件要通过 e.nativeEvent 读取。keyCode === 229 是给部分旧浏览器的兜底。

🔎 现成的封装

理解了原理之后，也可以使用社区的封装来省去样板代码，例如 Vercel AI SDK 的 useChat（@ai-sdk/react），它把消息状态、流式解析、停止和重试都包好了。 用 Next.js 的话，后端接口可以写成 Route Handler（app/api/chat/route.js，第 7 章），Hono 应用也可以直接挂在 Route Handler 里；本章的 Hono 代码也几乎不用改就能部署到 Cloudflare Workers 这类边缘平台。无论用什么封装，本章的几个要点都不变： 密钥在服务端、流要能中止、Markdown 要清理、输入法要处理。
