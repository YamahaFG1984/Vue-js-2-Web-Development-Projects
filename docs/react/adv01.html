深入渲染原理

前面八章一直在用 useState、useEffect、memo。状态一变界面就更新，但很多规则看起来像“咒语”： Hooks 不能写在 if 里、状态是快照、key 要稳定、effect 在渲染之后运行…… 本章我们拆开这些咒语：先用 100 多行代码亲手写一个迷你 React，再对照真实的 React（Fiber、并发渲染、React Compiler）， 你会发现每一条规则背后都有一个很朴素的原因。

本章目标

  • 理解“渲染”的本质：调用组件函数，得到一棵描述界面的普通对象树
  • 亲手实现 createElement、useState、useEffect 和一个简单的调和（diff）过程
  • 从实现上理解 Hooks 的规则、状态快照、批处理和 key
  • 理解 Fiber 架构：为什么渲染可以被打断，而提交不能
  • 用 useTransition、useDeferredValue 区分紧急更新和非紧急更新
  • 知道 React Compiler 做了什么，以及它依赖的“React 规则”
ⓘ 本章适合谁

学完前八章、能熟练写组件之后再来读。本章的迷你 React 不需要在项目里使用，它的目的是帮你建立正确的心智模型： 以后遇到“为什么这里没更新”“为什么 effect 跑了两次”“为什么输入框卡”之类的问题，你能自己推理出答案。

渲染 = 调用函数，得到一棵对象树

先回到最基本的问题：JSX 是什么？编译之后，每个标签都变成一次函数调用，返回一个普通的 JavaScript 对象，叫做元素（element）：

你写的 JSX
function Counter() {
  const [count, setCount] = useState(0)
  return (
    <button onClick={() => setCount(count + 1)}>
      点了 {count} 次
    </button>
  )
}
渲染时实际得到的
// <Counter /> 被“渲染”= Counter() 被调用，返回：
{
  type: 'button',
  props: {
    onClick: () => setCount(0 + 1),
    children: ['点了 ', 0, ' 次'],
  },
}

元素只是一份描述：“这里应该有一个按钮，文字是这样”。它不是 DOM，创建它也很便宜。 React 的工作分成两步：先调用所有组件函数，得到一棵新的元素树（渲染）；再和上一次的树比较，只把差异应用到真实 DOM 上（提交）。第 4 章的“触发 → 渲染 → 提交”说的就是这个。

动手写一个迷你 React

下面用不到 120 行代码，实现一个能跑起来的迷你 React：元素、函数组件、useState、useEffect、批处理和最简单的 diff。页面下方的演示就运行在它上面，没有使用真正的 React。

第 1 步：createElement

// JSX 编译后调用的函数：把标签变成一个普通对象
export function h(type, props, ...children) {
  return {
    type,
    props: {
      ...props,
      // 把文字也包装成元素，方便统一处理；false / null 不渲染（这就是 {ok && <X />} 能用的原因）
      children: children.flat()
        .filter((c) => c != null && c !== false)
        .map((c) => typeof c === 'object' ? c : { type: 'TEXT', props: { nodeValue: String(c), children: [] } }),
    },
  }
}

第 2 步：Hooks 存在哪里

函数组件每次渲染都会被重新调用，函数里的局部变量每次都是新的。那 useState 记住的值放在哪里？ 答案是：React 为每个组件实例准备了一个列表，按 Hook 的调用顺序依次存放。第一次调用 useState 用第 0 格，第二次用第 1 格…… 

let current = null          // 正在渲染的组件实例：{ hooks: [], index: 0 }

export function useState(initial) {
  const inst = current
  const i = inst.index++                       // 第几个 Hook？完全靠调用顺序
  if (!(i in inst.hooks)) {
    inst.hooks[i] = { value: typeof initial === 'function' ? initial() : initial, queue: [] }
  }
  const hook = inst.hooks[i]
  // 处理排队的更新：值或更新函数（第 2 章的 setX(prev => …)）
  for (const update of hook.queue) {
    hook.value = typeof update === 'function' ? update(hook.value) : update
  }
  hook.queue = []
  const setState = (update) => {
    hook.queue.push(update)     // 不立刻修改，只是排队
    scheduleRender()            // 预约一次渲染
  }
  return [hook.value, setState]  // 返回的是这一刻的值：快照
}
★ Hooks 的规则就是从这里来的

“只在组件顶层调用 Hooks，不要放在条件、循环或嵌套函数里”—— 因为 React 没有给 Hook 起名字，只认顺序。 每次渲染调用 Hook 的顺序必须完全一样，否则第 N 个 Hook 就会拿到别人的数据。eslint-plugin-react-hooks 的 rules-of-hooks 规则就是在静态检查这件事。 （React 19 的 use() 是例外：它不占格子，所以可以写在 if 里。）

第 3 步：批处理——为什么连续 set 只渲染一次

let scheduled = false

function scheduleRender() {
  if (scheduled) return            // 已经预约过了，这次不再重复预约
  scheduled = true
  queueMicrotask(() => {           // 等当前这段同步代码（比如整个点击处理函数）跑完
    scheduled = false
    renderRoot()                   // 统一渲染一次，期间处理所有排队的更新
  })
}

现在第 2 章那两条“咒语”都有了解释：状态是快照，因为 useState 返回的是渲染那一刻的 hook.value，setState 只是往队列里放东西； 更新函数能累加，因为队列里的函数会被依次调用，每一个都拿到上一个的结果。

第 4 步：调和——比较新旧两棵树

渲染出新的元素树后，要和上一次的树比较，决定怎么改 DOM。完整的树比较算法复杂度是 O(n³)，React 用了两个假设把它降到 O(n)：

  1. 同一位置、类型相同：保留 DOM 节点（和组件的状态），只更新变化的属性，再继续比较子节点。
  2. 类型不同：整棵子树直接销毁重建，里面所有组件的状态都会丢失，不再往下比较。
  3. 列表：只按位置比较会把“删掉第一项”误认为“每一项都变了”，所以需要 key 告诉 React 谁是谁。
function patch(parent, oldNode, newNode, index = 0) {
  if (!oldNode) {                                      // 新增
    parent.appendChild(createDom(newNode))
  } else if (!newNode) {                               // 删除
    parent.removeChild(oldNode.dom)
  } else if (oldNode.type !== newNode.type) {          // 类型变了：整棵替换
    parent.replaceChild(createDom(newNode), oldNode.dom)
  } else {                                             // 类型相同：复用 DOM，只改差异
    newNode.dom = oldNode.dom
    updateProps(newNode.dom, oldNode.props, newNode.props)
    const a = oldNode.props.children, b = newNode.props.children
    for (let i = a.length - 1; i >= b.length; i--) {  // 多出来的旧子节点：从后往前删
      newNode.dom.removeChild(a[i].dom)
    }
    for (let i = 0; i < b.length; i++) {             // 其余按位置逐个比较（新增的追加在末尾）
      patch(newNode.dom, a[i], b[i], i)
    }
  }
}

我们的迷你版本只实现了按位置比较（没有 key），真实的 React 会先按 key 建立对应关系，再决定移动、新增还是删除。 这也解释了第 3 章、第 5 章反复用到的技巧：改变 key 就能“重置”一个组件，因为 key 不同在 React 眼里就是另一个元素。

第 5 步：useEffect——提交之后再运行

let pendingEffects = []

export function useEffect(callback, deps) {
  const inst = current
  const i = inst.index++
  const old = inst.hooks[i]
  // 没有依赖数组：每次都运行；有：任何一项变了（Object.is 比较）才运行
  const changed = !old || !deps || deps.some((d, k) => !Object.is(d, old.deps[k]))
  inst.hooks[i] = { deps, cleanup: old?.cleanup }
  if (changed) {
    pendingEffects.push(() => {
      old?.cleanup?.()                         // 先清理上一次的
      inst.hooks[i].cleanup = callback()       // 再运行这一次的，保存新的清理函数
    })
  }
}

function renderRoot() {
  const newTree = expand(rootElement)          // 调用所有组件函数（渲染阶段）
  patch(container, oldTree, newTree)           // 修改 DOM（提交阶段）
  oldTree = newTree
  pendingEffects.forEach((run) => run())       // DOM 已经更新完，现在才运行 effect
  pendingEffects = []
}

依赖数组的比较用的是 Object.is：每次渲染都新建的对象或函数放进依赖数组，effect 就会每次都运行 —— 这正是第 4 章 useCallback、useMemo 要解决的问题。 完整的迷你 React 还有 expand（递归调用组件函数，给每个组件实例分配 hooks 列表）和“组件消失时运行所有清理函数”，见页面底部演示的源代码。

真实的 React：Fiber

我们的迷你 React 有一个致命问题：renderRoot 是一口气递归到底的。如果组件树很大，一次渲染要 200 毫秒，这 200 毫秒里浏览器完全无法响应用户输入，页面就卡住了。 React 16 引入的 Fiber 架构解决的正是这个问题：把渲染工作拆成一个个小单元，可以暂停、可以让出主线程、可以丢弃重来。

🧩

fiber 节点

每个组件 / 元素对应一个对象，保存类型、props、hooks 链表（就是我们的 hooks 数组）、对应的 DOM、要做的修改。

⏳

渲染阶段可中断

每处理一个 fiber 就检查一下“时间片用完没有”。用完了就把主线程还给浏览器，下一帧再接着做。

⚡

提交阶段不可中断

DOM 修改必须一次做完，否则用户会看到改了一半的界面。所以 effect、ref 都在提交之后统一处理。

⚠ 所以组件必须是纯函数

渲染阶段可能被打断后重来、可能被执行多次（Strict Mode 在开发时故意调用两次就是在模拟这一点）。 如果你在组件函数体里修改外部变量、发请求、操作 DOM，这些副作用就会发生多次或发生在不该发生的时候。 副作用只能放在事件处理函数和 effect 里 —— 它们只在提交之后运行一次。

并发渲染：区分紧急和不紧急

有了可以中断的渲染，React 18 起就能给更新分优先级（内部叫 lanes）。 打字、点击这类紧急更新要立刻反映到屏幕上；根据输入过滤一个大列表、切换标签页的内容这类过渡更新晚一点没关系，而且如果用户又输入了新字符，旧的渲染可以直接丢弃。

写法上有两个 Hook：

import { useState, useDeferredValue, useTransition, memo } from 'react'

// ① useDeferredValue：我控制不了更新从哪来，但可以让“用到它的部分”慢半拍
function Search() {
  const [text, setText] = useState('')
  const deferredText = useDeferredValue(text)       // 紧急渲染时还是旧值，后台再用新值渲染一次
  const stale = text !== deferredText
  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <div style={{ opacity: stale ? 0.5 : 1 }}>
        <SlowList text={deferredText} />              {/* 必须 memo，否则紧急渲染时也会重新渲染它 */}
      </div>
    </>
  )
}
const SlowList = memo(function SlowList({ text }) { /* 渲染很多行…… */ })

// ② useTransition：更新是我发起的，可以直接把它标记为“过渡”
function Tabs() {
  const [tab, setTab] = useState('home')
  const [isPending, startTransition] = useTransition()
  return <button onClick={() => startTransition(() => setTab('reports'))}>
    报表 {isPending && '…'}
  </button>
}

ⓘ 并发不是多线程

JavaScript 还是单线程的。“并发”指的是 React 可以同时准备多个版本的界面，并在它们之间切换、丢弃。 真正耗时的计算（比如解析一个 10MB 的文件）不会因此变快，那应该交给 Web Worker。

React Compiler 做了什么

第 4 章说过，父组件渲染时子组件默认都会渲染，手动优化要用 memo、useMemo、useCallback，写起来繁琐还容易漏掉依赖。 React Compiler 在构建时分析每个组件，自动插入缓存。它编译后的代码大致是这样的：

你写的
function TodoList({ todos, filter }) {
  const visible = todos.filter(
    (t) => t.status === filter
  )
  return <List items={visible} />
}
编译后（示意）
function TodoList({ todos, filter }) {
  const $ = _c(3)              // 这个组件的缓存格子
  let el
  if ($[0] !== todos || $[1] !== filter) {
    const visible = todos.filter(…)
    el = <List items={visible} />
    $[0] = todos; $[1] = filter; $[2] = el
  } else {
    el = $[2]                  // 输入没变：直接复用上次的元素
  }
  return el
}

编译器能这样做，前提是你的代码遵守 React 的规则：组件和 Hook 是纯的（相同输入得到相同输出）、props 和 state 不可变、Hooks 只在顶层调用。 一旦你直接修改了 props 里的对象，编译器以为“引用没变就是没变”的假设就被打破了。所以前面强调的“不可变更新”在编译器时代更加重要。 编译器发现某个组件违反规则时，会跳过这个组件而不是编译出错误的代码；eslint-plugin-react-hooks 的新版本里也包含了这些检查。

✓ “撕裂”是什么

并发渲染可以暂停。如果渲染到一半时，一个外部 store 的值变了，前半部分组件读到旧值、后半部分读到新值，同一屏上就会显示不一致的数据 —— 这叫撕裂（tearing）。 useSyncExternalStore 会在提交前检查快照有没有变，有变化就同步地重新渲染，保证一致。这就是第 6 章 Zustand、第 8 章 Meteor 都要基于它的原因。

小结

概念一句话
元素JSX 编译成描述界面的普通对象，创建很便宜
渲染 / 提交渲染是调用组件函数、比较新旧树（纯计算）；提交才修改 DOM、运行 effect
Hooks 的存储每个组件实例一个列表，按调用顺序取用 → 只能在顶层调用
状态快照useState 返回渲染时的值；setState 只是入队并预约渲染
批处理多次 set 合并成一次渲染；更新函数在队列里依次执行
调和同类型复用、不同类型重建、列表靠 key；改 key 可以重置组件
Fiber渲染拆成可暂停的小单元，双缓冲；提交一次完成
并发useTransition / useDeferredValue：非紧急更新可被打断、丢弃
React Compiler构建时自动缓存计算和元素；依赖纯函数和不可变数据

动手练习

  1. 给迷你 React 加上 useRef：它就是一个永远返回同一个 { current } 对象的 Hook（提示：只在第一次创建时放进 hooks 列表）。
  2. 实现 useMemo(fn, deps)：和 useEffect 一样比较依赖，但在渲染时同步计算并缓存结果。
  3. 给迷你 React 的列表比较加上 key：先用 Map 按 key 找到旧节点，复用它的 DOM，再用 insertBefore 调整顺序。
  4. 把 scheduleRender 里的 queueMicrotask 换成同步调用 renderRoot()，在演示里点“+3（更新函数）”，观察日志里渲染了几次。
